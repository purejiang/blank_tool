# 04 开发指南

面向 Blanks 仓库的实际开发手册。命令、路径、约定均已对照 `AGENTS.md`、`package.json`、`tsconfig.json` 与源码核实。

## 常用命令

```bash
npm run dev          # 启动开发模式（node scripts/dev.mjs 包装 vite；vite-plugin-electron 自动拉起 Electron 主进程/preload）
npm run doctor       # 自检 Electron 能否在本机跑起来（--version + 最小探针 App；失败退出码 1）
npm run lint         # vue-tsc --noEmit --pretty false（非 ESLint，是 Vue 类型检查）
npm run typecheck    # vue-tsc --noEmit（带详细输出）
npm run test         # vitest run（仅跑 TS 单测 + 集成测试）
npm run test:watch   # vitest 监听模式
npm run test:coverage
npm run check        # lint && typecheck && test（提交前快速门禁）
npm run check:full   # check + pytest 契约/单测 + node:test 契约 + Playwright e2e（提交前全面门禁）
npm run build:win    # node scripts/build.mjs --win（mac/linux 同理）
npm run release      # 一键发版（流程见 .agents/rules/RELEASE_GUIDE.md）
```

Dev server 监听 `http://localhost:3000`（strictPort，端口被占直接失败）。Vite 的 `root` 是 `src/`，不是项目根。

### Electron 起不来时怎么判断

`npm run dev` 由 `scripts/dev.mjs` 包装（它自己 spawn `node_modules/vite/bin/vite.js`），退出时会解释失败原因。最常见的失败形态是**构建成功、Electron 被拉起后立刻退出**，终端里表现为：

```
✓ 678 modules transformed.
../dist/main/main.js  1,424.10 kB │ gzip: 311.21 kB
built in 2271ms.
ERROR: The process "18468" not found.          ← 不是 vite 的报错
```

这行 `ERROR: The process "NNNN" not found.` 是 **vite-plugin-electron 的清理噪音**：它在 Electron 退出时用 `process.electronApp.once('exit', process.exit)` 连带结束 vite，随后 `treeKillSync()` 用 `taskkill /pid <已死 PID>` 清理，taskkill 往 stderr 打的这句话就成了唯一线索（源码见 `node_modules/vite-plugin-electron/dist/index.mjs`）。**它等价于"Electron 启动即退出"**，而不是 vite 构建失败。

另有一类失败长得完全不像报错，但同样让 App 起不来：**Electron 起来了，却在加载期写不了自己的用户数据目录**，终端里是

```
App threw an error during load
Error: EPERM: operation not permitted, open 'C:\Users\<user>\AppData\Roaming\blanks\app-config.json.tmp-07613300040ab940'
    ... ElectronStore._write ... new Conf ... new ElectronStore      ← 模块加载期，还没进 app.whenReady()
```

`electron-store` 在 `src/main/stores/appStore.ts` **模块加载期**就要写 `app-config.json`，而 `write-file-atomic` 的写法是「写 tmp 再 rename」。此时 vite **不会**退出（Electron 卡在错误对话框上），所以看不到 `taskkill` 那行；`npm run doctor` 的探针 App 会在 Electron 进程内复现这一项。

**这个 EPERM 已实测到根因（与本仓库代码无关）**：在 Electron 进程里，文件**读得到、写不了** —— 新建 / 覆盖 / 追加 / `openSync('w')` / `mkdirSync` / `renameSync` **全部 EPERM**，连 `%TEMP%`、`C:\Windows\Temp`、`%LOCALAPPDATA%` 也一样（所以不是某个目录的 ACL）；而**同样的操作从 `node.exe` / PowerShell 做（同一用户、同一目录、同一父进程）全部成功**。把 electron.exe 复制到别的目录、加不加 `--no-sandbox`、甚至 `ELECTRON_RUN_AS_NODE=1`（同一镜像但不启动 Chromium）跑纯 Node 脚本 —— 一样写不了。**结论：限制挂在 `electron.exe` 这个镜像上，是某个安全产品在按"只读容器/沙箱"运行它**（另一档表现是直接把进程在启动时打断，即下面第 2 项的 `0x80000003`）。Chromium 连自己的 profile / 缓存都建不出来，所以 App 必挂，改工程代码没有任何用。

已实测**无效**的绕法（别再试这些）：① 改 App 名 / 包名 / userData 目录（换包名的探针 App 写自己的 `%APPDATA%\blanks-io-probe` 一样 EPERM）；② 把 `electron.exe` 复制/改名成 `blanks-app-probe.exe`（与原名表现完全一致）；③ 不用 App、直接 `ELECTRON_RUN_AS_NODE=1 electron.exe -e "..."` 写 `%TEMP%`（一样 EPERM）。限制不认 App 身份、也不认文件名，只认这个镜像。

先跑 `npm run doctor`（`scripts/doctor.mjs`）：它做两件与业务代码无关的事 —— ① `electron --version`（失败会重试 3 次，因为这在这台机器上是间歇性的）；② 在 `%TEMP%\blanks-electron-probe` 现场生成一个最小 Electron App（包名刻意取 `blanks`，让 userData 落在真实应用同一个 `%APPDATA%\blanks`）并开窗，同时在**它自己的进程内**对 userData 与 `%TEMP%` 各做一次 `写 tmp + rename`。

| doctor 结果 | 含义 | 下一步 |
|---|---|---|
| 两项都 PASS | Electron 正常，问题在工程侧 | 读 `npm run dev` 上方 vite 自己的报错 |
| `--version` 重试 3 次都 FAIL | 这次探测期间 electron.exe 启动即被系统层打断 | 走「机器侧排查」第 2、3 条（代码改不动） |
| `--version` PASS，但探针报 `BLANKS_PROBE_WRITE_FAIL userData` | Electron 能起，但进程内写不了 `%APPDATA%\blanks`（若同时报 `FAIL temp`，就是整个进程被只读/沙箱化） | 按下方「放行 electron.exe 本身」两步 |
| `--version` PASS 但探针开窗失败 | 能起进程、开不出窗口 | 显卡驱动 / GPU、输入法注入、安全软件 |

机器侧症状（都可以在 `npm run doctor` 输出、Windows 事件查看器里看到）：

- `electron --version` 非 0 退出、且没有任何输出（连版本都打印不出来；注意它是**间歇**的，前几分钟失败、后几分钟又能起）；
- 事件日志里有 electron.exe 的崩溃记录：`Get-WinEvent -FilterHashtable @{LogName='Application'; ProviderName='Application Error'} -MaxEvents 30 | Where-Object Message -match 'electron'`（实测过 `0xC0000005` / `0x80000003` / `0xFFFF7003`）；
- 日志里出现 `crashpad_client_win.cc ... not connected`（崩溃处理器连不上，常见于被安全软件拦截或进程被提前打死）。

机器侧排查（**一次只动一项**，每改一项重跑 `npm run doctor` + `npm run dev`）：

0. **放行 electron.exe 本身**（对应探针报 `FAIL userData`）。限制是按镜像生效的，所以要加白名单的是这个可执行文件，而不是某个数据目录：
   - 360 安全卫士 → 木马查杀 → 信任区：加文件 `node_modules\electron\dist\electron.exe`、加目录项目根；再到设置里查「主动防御 / 沙箱（内核驱动 `360Box64.sys`、`360Hvm64.sys`）」是否把 electron.exe 当未知程序收进了只读容器；必要时先临时退出 360 验证一次。
   - 腾讯 iOA「无边界安全系统防护」→ 让 IT 把 `electron.exe` 加白名单，或查它的拦截记录：它的文档保护模块会在 `C:\ProgramData\Tencent\QQPCMgr\Tfsdocpro\` 下留下带时间戳的扫描记录（可用来对账），注入/文件过滤驱动是 `txinjx64_ev.sys` / `TFSFltX64_ev.sys` / `TSSysKit64_EV.sys`。
   - **别用「node / PowerShell 能写同一路径」来否定这一条** —— 实测限制只作用在 electron.exe 上。
1. **重启机器**。内核 hook / 安全软件状态卡死时最有效。
2. **360 主动防御**（`ZhuDongFangYu.exe`）：临时关闭，或把项目根、`node_modules\electron\dist`、`%APPDATA%\blanks`、`%LOCALAPPDATA%\blanks` 加入信任区。
3. **腾讯 iOA**：见上面第 0 条（这一条同时也是 `0x80000003` 那一档的首要嫌疑）。
4. **输入法**：切到微软拼音或退出微信输入法 —— `wetype_tip_core.dll` 会注入 Electron 主进程。
5. `Get-ChildItem -Recurse .\node_modules\electron | Unblock-File`，并在 Windows 安全中心放宽对本地开发目录的 SmartScreen 检查。
6. 以上都无效：这台机器当前无法运行任何 Electron，只能靠 IT 放行或换机开发；**不要**在这上面继续调工程代码。

## 测试体系（五套，注意各自运行器）

| 命令 | 运行器 | 范围 | 配置 |
|---|---|---|---|
| `npm run test` | **vitest** | `tests/unit/**`、`tests/integration/**` | `vitest.config.ts`，环境 `happy-dom` |
| `pytest tests/contracts/` | **pytest**（不在 npm scripts 里） | 后端 handler 契约测试（Python） | `tests/contracts/conftest.py` 自动把 `cli/` 加入 `sys.path` |
| `pytest tests/cli/` | **pytest**（不在 npm scripts 里） | Python 单测（协议类型、端口模型、工具、引擎、环境、CLI） | 根级 `tests/conftest.py` 自动把 `cli/` 加入 `sys.path` |
| `node --test tests/shared-contracts.test.mjs` | **node:test**（不在 npm scripts 里） | 校验 `src/shared/ipc/channels.ts` 与 `pathConfig.ts` 的字符串契约 | 无配置 |
| `npx playwright test` | **Playwright** | `tests/e2e/`（当前无 spec——占位套件已删、推迟到 `/workflows`、`/tasks` 落地；`playwright.config.ts` 设了 `passWithNoTests`，门禁不会挂） | `tests/e2e/playwright.config.ts` |

要点（最容易踩坑）：

- `npm run test` 在 `vitest.config.ts` 里显式 **exclude** 了 `tests/e2e/**` 与 `tests/shared-contracts.test.mjs`，所以它不会跑后两者。
- 改了后端 handler 或 IPC 通道名后，**必须手动跑对应的契约测试**（`pytest tests/contracts/` 与 `node --test tests/shared-contracts.test.mjs`）。
- **改 IPC 通道名必须同步 `tests/shared-contracts.test.mjs`**，否则契约测试会挂。该文件还会校验 `src/shared/ipc/protocol.ts` 的 `ApiMethodMap` 覆盖了后端所有 `API_MAP` 键（100% 覆盖断言）。
- `tests/setup.ts` 给 happy-dom 补了 `localStorage` / `sessionStorage` 桩，单元测试里的 Pinia 持久化依赖它。

`npm run check:full`（`package.json` 的 `check:full` 脚本）串联全部五套测试，适合提交前全面门禁。

## TypeScript 非严格（重要约定）

`tsconfig.json` 显式关闭了 `strict`、`noImplicitAny`、`strictNullChecks`、`noUnusedLocals`、`noUnusedParameters`。**不要**按默认严格模式去"修复"已有代码，也不要在 review 时把 nullable 误判为 bug。新增代码可以写得严格些，但不要大面积重构老代码。

## 路径别名

`@/` → `src/renderer/`，另有 `@components`、`@views`、`@services`、`@stores`、`@composables`、`@utils`、`@assets`（在 `tsconfig.json` 与 `vite.config.ts` 都有定义）。注意 `src/renderer/` 之外的代码（主进程、preload、shared）用相对路径 import。

## 后端开发（Python）

后端入口 `cli/main.py`（stdin/stdout JSON-RPC），配置加载与日志初始化在 `bootstrap()`。仅用标准库，无 `requirements.txt`。

### 新增 handler

在 `cli/app/handlers/` 下新建模块并导出 `API_MAP` 字典，`app/api_handler.py` 会在启动时自动发现（`pkgutil.walk_packages`），**不需要改注册表**：

```python
# cli/app/handlers/example_handler.py
from app.common.decorators import logs_errors, streaming

@logs_errors("ExampleHandler")
def handle_hello(params, stream_handler):
    return {"hello": params.get("name", "world")}

@streaming
@logs_errors("ExampleHandler")
def handle_stream(params, stream_handler):
    # 可多次回调 stream_handler 推流，最终由 ApiHandler 发送 finished: True
    stream_handler({"type": "log", "payload": {"message": "..."}})
    return {"ok": True}

API_MAP = {
    "example.hello": handle_hello,
    "example.stream": handle_stream,
}
```

- 装饰器位于 `cli/app/common/decorators.py`。`@streaming` 标记 handler 在独立线程运行、可多次回包；`@logs_errors("前缀")` 记录未捕获异常但**不吞异常**。
- 流式事件经既有 `stream-event` IPC 通道转发（`src/shared/ipc/channels.ts` 的 `streamEvent`），不需要新增通道。
- handler 抛 `ToolException` / `ToolNotFoundError` / `TimeoutException`（`app/common/exceptions.py`）会被中间层格式化为错误响应。
- **领域存储长这样**：`app/workflow/store.py`（工作流 = 工作流图 + 入参声明）、`app/history/store.py`（运行记录，按上限裁剪）、`app/task/store.py`（任务定义 = 工作流 + 保存的入参，`task.*` 键；与工作流/运行是三件事，别混）。三者都遵循同一套约定：工作流库与任务库以**自动生成的 id** 作文件名（`wf-…` / `tk-…`，一文件一对象，文件名 stem 就是 id；见 [02 §3.5](./02-系统架构.md#35-存储身份id-与显示名分离2026-09-30) 与 `app/ids.py`）、路径校验拒绝路径分隔符与 `..`、`list()` 跳过损坏文件、写盘走 `app/utils/atomic_json.py`（tmp + `os.replace` + Windows 重试）。新增这类"用户数据目录"时，**必须**同时登记进 `app/handlers/cache_handler.py` 的 `_MANAGED_SUBDIRS`（`output.clear` 默认跳过），否则一次"清除存储"就会删掉用户数据。

### 新增工具

两种方式，推荐优先用描述符：

1. **描述符 JSON**（推荐入口：`examples/tools/<domain>/<name>.json`，经工具管理页导入）：声明 name / display_name / type / path / env_deps / validate / version / inputs / outputs，并按需声明 `operations[]`（每个操作含类型化 inputs/outputs + `args_map` 命令映射）。`ToolManager` 自动发现并解析为 `DescriptorTool`。范本见 `examples/tools/android/apktool.json`。
2. **`BuiltinTool` 子类**（`cli/app/tools/builtin/`）：声明 `ports` 属性 + 实现 `execute(inputs, context)`。适合描述符无法表达的逻辑（如内置原子工具 `file.read`、`exec.shell`）。

> **工具二进制由用户自备**：本地 `runtime/` 目录、设置中的自定义工具路径（`tool.set_custom_path`）或系统 PATH 均可；环境二进制可用 `BT_JAVA_BIN` / `BT_PYTHON_BIN` / `BT_NODE_BIN` 等 `env_var_override` 直接覆盖（见 [03-数据模型](./03-数据模型.md#9-环境描述符与解析)）。

**写描述符操作时**：如果某个入参是工具的**产物路径**（典型如 `--out <path>`），给它加 `"direction": "output"`，引擎会自动把绑定值 surface 到节点 outputs，下游可直接 `$nodes.<id>.outputs.<name>` 引用，无需在 outputs 侧再声明一遍。详见 [03-数据模型 §3.1 产物端口](./03-数据模型.md#31-产物端口direction-output)。

### 新增环境

在 `cli/registry/environments/*.json` 写环境描述符，参考 `cli/registry/environments/java.json`（name / display_name / type / binary / version_cmd / version_regex / search_paths / importable / env_var_override）。`EnvironmentRegistry`（`cli/app/env/registry.py`）自动发现并解析。

### 新增工作流

编写 `WorkflowDefinition` JSON，经工作流管理页/编辑器**导入**（或 CLI 直接 `run` 文件路径）使用；示例见 `examples/workflows/android/`。**规划落地后不要再向 `cli/workflows/` 添加内容**（该目录将随领域内容外部化迁出，见 [05-分期开发计划](./05-分期开发计划.md#phase-1-基础模型)）。字段与规则见 [03-数据模型](./03-数据模型.md) 与 `cli/app/workflow/definition.py`：

- 线性模式：控制流只由 `node.next` 决定；分支用 `flow.compare` + `flow.branch` 组合实现（`flow.branch` 的 `true_template` / `false_template` 指向子工作流；这两个端口名**刻意保留旧名**，重命名登记为延后项，见 [09-后端缺口修复与优化方案](./09-后端缺口修复与优化方案.md)）。
- 节点参数支持两种表达式写法（细节见 [03-数据模型](./03-数据模型.md#8-表达式引擎供节点参数使用)）：
  - **整值**：`"$inputs.path"`、`"$nodes.scan.outputs.count"`（保留原类型，用于绑定类型化端口）；
  - **插值**：`"found ${nodes.scan.outputs.count} matches in ${inputs.target}"`（`$${` 转义为字面量 `${`；不带 `${}` 的字符串是纯字面量）。
- 相对路径的锚定顺序（2026-09-30 起，见 [03-数据模型](./03-数据模型.md#21-运行时工作目录work_dir与运行产物目录rundir)）：① 显式传入 `params.work_dir` **最优先**；② **文件目标**（`workflow.execute {path}` / CLI `run <file.json>`）取该 JSON 文件所在目录（`source_dir`）；③ 其余情况（保存的工作流、CLI `run <id|名称>`）落在**本次运行的运行目录** `$rundir` = `<output_dir>/runs/<run slug>`。也就是说保存的工作流其相对路径解析在**自己的运行目录**里，而不是工作流库。
- **产物写 `${rundir}`**（本次运行的 `<output_dir>/runs/<run_id>`），不要把引擎/运行产物写进工作流目录——那里可能是源码树或工作流库（见 [03-数据模型](./03-数据模型.md#21-运行时工作目录work_dir与运行产物目录rundir)）。
- 描述符工具的参数走 `params: {"args": [...]}` 命令列表形式，或 `params: {"operation": ..., ...}` 走统一操作模型（引擎见 `cli/app/workflow/engine.py` 的 `_execute_tool`）。
- 节点失败策略：`on_failure` 取 `"fail"`（默认，终止）/ `"skip"`（跳过继续），`retry` 是失败后的额外尝试次数（0 = 不重试）。
- 用户工作流可另存到 `<output_dir>/workflows`（`BT_WORKFLOWS_DIR` 可覆盖，旧名 `BT_TEMPLATES_DIR` 仍被读取），通过 `workflow.*` handler 管理。

## 渲染层开发（Vue 3 + Pinia + Naive UI）

- **服务层 DI**：`ServiceManager`（`src/renderer/services/ServiceManager.ts`）注册构造函数 + 依赖，首次 `getService()` 时懒加载并调用 `initialize()`。注册点：`src/renderer/App.vue` 的 `registerServices()`。
- **Pinia 持久化**：`src/renderer/main.ts` 注册自定义 localStorage 插件。store 声明 `persist: true` 或 `persist: { key }` 即自动同步 localStorage。
- **调用后端**：经 `window.electronAPI.callBackendApi({ method, params, id })` 走 `call-backend-api` 通道，或封装在 `src/renderer/api/unifiedApi.ts` / 各 Service 里。方法名与参数/返回类型见 `src/shared/ipc/protocol.ts` 的 `ApiMethodMap`。
- **i18n**：改 UI 文案需同步 `src/renderer/i18n/locales/` 下的 `zh-CN.ts` 与 `en-US.ts`（fallback 为 zh-CN）。

## 排障

### (a) `protocol.py` 与 `protocol/` 包同名冲突（当前阻塞项）

**现象**：后端启动即崩溃循环，所有请求被拒，界面提示"后端服务已退出"。后端日志（开发模式 `cli/logs/`，生产在 `LOCALAPPDATA\blanks\logs\`）出现：

```
ImportError: cannot import name 'BackendResponse' from 'app.protocol'
```

**根因**：`cli/app/protocol.py`（消息类：`BackendResponse`、`BackendSuccessPayload`、`BackendErrorPayload`、`BackendStreamEvent`、`BackendApiRequest`、`ErrorCode`）与 `cli/app/protocol/` 包目录同名。Python 导入时**包目录遮蔽同名模块**，于是 `main.py:26` 的 `from app.protocol import ErrorCode` 与 `api_handler.py:19-24` 的 `from app.protocol import (BackendResponse, ...)` 都拿不到消息类，导入期抛错。而 `protocol/__init__.py` 只导出类型系统（`BaseType`、`TypeAnnotation`、`TypeRegistry`、`Port`、`PortSet`），未包含消息类。`cli/cli.py` 也因此在注释里记录了它无法复用 `main.bootstrap`（43~45 行）。

**修法**：把 `protocol.py` 的消息类并入 `protocol/` 包（例如新建 `protocol/messages.py`），并在 `protocol/__init__.py` 统一导出；删除 `protocol.py`；确保 `main.py:26`、`api_handler.py:19-24`、`definition.py:29`、`validation.py:41`、`tools/*`（`descriptor_tool.py`、`builtin/*`）的 import 均可用；加一个导入回归测试。修复后可顺带让 `cli.py` 复用 `main.bootstrap`（去掉内联复制）。详见 [05-分期开发计划#Phase-0](./05-分期开发计划.md#phase-0-稳定性阻塞项)。

**日志位置**：
- 后端日志：开发模式 `cli/logs/`（`BT_LOG_DIR` 未设置时的 fallback；Electron 主进程会注入 `BT_LOG_DIR` 到用户数据目录）。
- Electron 主进程日志：`LOCALAPPDATA\blanks\logs\electron.log`。

### (b) 后端生命周期

- `src/main/python/service.ts`：spawn Python 子进程并注入 `BT_RUNTIME_DIR` / `BT_CACHE_DIR` / `BT_TASKS_DIR` / `BT_OUTPUT_DIR` / `BT_LOG_DIR` / `BT_LOG_LEVEL` 环境变量。`ensurePythonService()` 是懒启动：进程不在/不可写时重新 spawn，**没有自动重启看门狗**，崩溃后需等下一次调用才拉起。
- `src/main/python/stderrCapture.ts`：对 Python stderr 做 200 行环形缓冲；进程崩溃（exit code != 0）或出现 traceback 时把尾部内容经 `log.error` 写入 `electron.log`（取证），诊断页经 `read-electron-log-tail` 通道拉取展示。不再经 IPC 通道实时推送。

### (c) 后端健康检查

`get-backend-health`（`src/main/ipc/electronHandlers.ts:180`）**仅检查进程是否存活**（`proc && !proc.killed && proc.exitCode === null`），不做 stdin 往返探活，也上报不了 pending_requests（恒为 null）。后端进程活着但卡死时，健康检查仍会显示"健康"，排查卡死问题时要结合任务/请求日志。
