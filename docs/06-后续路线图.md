# 06 后续路线图

本文件记录**已确认延后**的功能项：当前不做，但保留设计预留与演进方向。每一项给出简述、价值与大致前置依赖，供排期决策时按优先级取用。

> 与 [05-分期开发计划](./05-分期开发计划.md) 的关系：05 是已排期的近期工作，本文件是明确的"以后再说"清单。

## 一、DAG 条件分支 —— 已由组合原语满足

- **简述**：支持 `if/else` 走向。
- **现状（已落地）**：分支用**组合**实现，不需要 DAG schema：`flow.compare`（比较产出布尔）→ `flow.branch`（真走 `true_template`、假走 `false_template`，缺省则不执行）→ `flow.assert`（整轮门禁）。`condition` / `on_success` / `edges` 这些"存而不用"的字段已从 `WorkflowNode` / `WorkflowDefinition` 中**删除**（见 `cli/app/workflow/definition.py`），老 JSON 里残留的同名键在加载时被忽略。
- **剩余**：真正的"按条件选择后续节点"（图上多出边、跳转而非嵌套子流程）仍延后；真要做时引擎需从"单入口单链"改为"入口集合 + 后继求值"。
- **UI 侧口径（2026-09-21）**：画布**不假装**支持多出边。前端序列化只取每个节点的第一条出边，其余出边会让目标节点失去入边、文档出现多个 entry node，而 `template.save` 走的 `WorkflowDefinition.from_dict` 会直接抛 `ValueError`（`must have exactly one entry node`）—— 所以画布上的分支是**存不下去**，不是"被忽略"。据此编辑器在画布上实时警告、在保存前阻断（契约见 [08](./08-前端页面与功能清单.md) S2「线性模型守卫」）。等本节的 DAG 真落地时，这层守卫随之撤掉。

## 二、DAG 并行执行

- **简述**：多个无依赖的节点同时执行，而不是线性排队。
- **现状**：引擎按 `node.next` 单链顺序执行；schema 中已无 `edges` 预留字段，未来需要新的并行 schema。
- **价值**：下载多个 APK、并行反编译等场景可显著缩短总耗时。
- **前置依赖**：DAG 执行模型（依赖图拓扑排序 + 完成计数）；`TaskManager` 取消语义需覆盖并发节点（当前取消按 run 生效，已能终止子进程）；节点级流式事件需带并发上下文（`run_id` / `node_id` 路径已具备）。`flow.foreach` 目前是顺序循环，若只想要"批量并发"可先给 foreach 加 `concurrency` 参数。

## 三、动态参数数据源绑定

- **简述**：入参下拉的选项来自动态数据源，例如"当前 ADB 设备列表"、"签名配置列表"、"某目录下的文件列表"。
- **现状**：**访谈确认暂不需要**。当前约定是：能作为入参传递的数据就直接传（例如设备序列号由任务页下拉静态提供，或由用户在表单里选）。`options` / `multi` 字段已实现（T2），目前为静态字符串列表。
- **价值**：让"设备选择""签名选择"等高频操作免手输，减少出错。
- **前置依赖**：Phase 1 的 `options` / `multi` 入参模型（已实现，T2）；若未来需要，再扩展为"数据源引用"（`options_from: "adb.devices"` 之类），并让渲染层注册数据源解析器。

## 四、借鉴 n8n / dify 的编辑与运维能力（延后）

以下能力在同类编排产品中常见，本版本明确延后，按价值排序：

| 项 | 简述 | 价值 | 大致前置依赖 |
|---|---|---|---|
| 运行历史 / 执行记录 | 每次工作流运行落库：入参快照、逐节点结果、耗时、错误，支持回看、复跑、按节点排查 | 排查"上次为什么失败"、复现问题、审计 | Phase 3 任务闭环落地后；新增执行记录存储与列表页 |
| 画布编辑体验 | 撤销/重做、快捷键、多选、复制粘贴、自动布局、便签 | 长工作流编辑效率与容错 | vue-flow 已内置部分能力，需封装成编辑器功能层 |
| 增强错误处理 | 每节点超时、失败走错误分支输出 | 网络类节点（下载/安装）更稳 | 引擎已支持 `fail`/`skip` + `retry`（含不可重试错误分类）；每节点超时尚未实现（当前子进程超时固定 10 分钟，取消可强制中断） |
| 工作流版本 / 启停 / 标签 / 搜索 | 模板带版本、`active` 开关、标签过滤、按名称搜索 | 模板多了以后的管理体验 | Phase 2 工作流模块落地后；`template.*` handler 扩展元数据 |

## 五、更远期的设想

- **触发器**：目录监听（新文件落盘自动跑流程）、设备连接触发。价值是"零点击自动化"，但依赖文件监听与设备热插拔事件桥接，且当前任务模型是手动触发，跨度较大 —— 与**定时执行 / 时间段执行 / 监视器**一并见 **§八**（分级、成本与前置缺口都在那里）。
- **凭据 / 密钥保险库**：签名 keystore 密码等敏感信息的安全存储（当前存于应用配置）。价值是安全合规，前置依赖明确的威胁模型与加密方案，暂不排期。
- **官方领域包分发渠道**：领域内容外部化已完成（T21，2026-08-04，见 [05-分期开发计划](./05-分期开发计划.md#phase-1-基础模型)），提供官方分发的领域包（如 Android 工具包一键导入：描述符 + 二进制打包下载，或在线包索引），把"导入示例包"升级为"一键安装领域包"。**新增候选项**，尚未排期。
- **品牌化与设计系统化（候选项，已部分前置）**：本轮界面重设计的视觉体系以用户确认的 Google Stitch 设计稿为准（见 [05-分期开发计划](./05-分期开发计划.md#phase-2-工作流编辑与管理mvp)）；剩余候选为设计 token 化 / 组件规范统一 / 品牌深化，可单独排期，不阻塞功能演进。

## 六、插件系统（已落地，剩余为生命周期增强）

- **现状（已实现）**：manifest 驱动的 native 插件体系已完整落地——入口 `apply(ctx, config)`，加载器 `cli/app/plugins/loader.py`（`shipped-native` 常驻 / `native` 可卸载），注册接缝 `PluginContext.register_tool`；`plugin.list` / `plugin.add` / `plugin.delete` / `plugin.reload` 四个 handler 在线（`plugin.add` 会拒绝重复条目与 shipped 模块）；工具管理页（ToolsPage）提供插件管理 UI。描述符即第二层声明式插件，详见 [plugin-architecture.md](./plugin-architecture.md)。此前的"`run(context, **params)` 形式 + `cli/plugins/` 自动发现"描述对应的是已删除的旧模型，不是现状。
- **剩余工作（未排期）**：插件生命周期增强——按插件查看其注册的工具、失败插件的状态可见性、enable/disable 开关等。
- **价值**：不侵入核心代码即可扩展工具能力。
- **前置依赖**：无。

## 七、模型层延后项（2026-08 界面前端重构盘点新增）

来源：[09-后端缺口修复与优化方案](./09-后端缺口修复与优化方案.md) WP6 的缺口 #10。三项都需要动数据模型或其序列化，收益低于成本，本轮**明确不做**，UI 也不得承诺。

| 项 | 简述 | 现状替代 | 前置依赖 |
|---|---|---|---|
| 节点级超时 | `WorkflowNode` 增加 `timeout` 字段，单节点超时即失败/跳过 | 描述符操作级 `timeout`（`operations[].timeout`）+ CLI 整轮 `run --timeout`；卡死靠取消真正终止进程组 | definition schema + 引擎 + 编辑器序列化三方同步改动 |
| 画布节点坐标持久化 | 保存/恢复节点在画布上的位置 | 重新加载按链式顺序重新堆叠；不承诺"布局保持" | 需扩展 `WorkflowDefinition` 或引入 sidecar 文件（`positions`），并同步 `serializer.ts` |
| 端口默认值 | `Port` 增加 `default`，表单预填 | 工作流 `description` 里说明默认值 | 端口 schema + `PortSet.validate_inputs` + 编辑器/任务表单预填三处改动 |
| 任务的导入导出 | 把任务定义（工作流 + 保存的入参）导出为 JSON / 从 JSON 导入 | 手工重建任务，或直接编辑 `<output>/task_defs/*.json` | 需要决定导出格式与"导入时工作流不存在"的处理；`app/task/store.py` + 一对 `task.export/import` 键 |

> **任务定义已不是延后项**（2026-09-28，WP7 落地）：任务 = 可持久化的执行配置（工作流 + 保存的入参），存储 `<output>/task_defs/`，API 为 `task.list/get/save/delete/execute`，CLI 为 `list-tasks` / `run --task <名称>`。上文"运行历史 / 执行记录"作为任务的可复用配置**已经实现**；仍延后的是它的**导入导出**与**并发互斥**。

> 注：`src/renderer/components/workflow/ioAuthoring.ts` 编辑端口时丢失 `type.subtype` 属于**缺陷**（不是延后项），已修复（WP6，2026-09）：`PortDraft` 现携带 `subtype`，`draftFromPort` → `portFromDraft` 全程保留，面板仍不提供该字段的编辑 UI。

## 八、触发与调度（定时执行 / 时间段执行 / 监视器）——2026-09 盘点新增

**结论：三项都不进当前排期**（要排在 Phase 2/3/4 与 T24 界面前端重构之后）。但三者成本差异很大：**L1 定时执行可随时插队**，因为它不新增运行时。

### 8.1 为什么现在不做

1. **不在关键路径上**：T24 前端重构尚未开工（设计稿未交付），[05-分期开发计划](./05-分期开发计划.md) 的 Phase 2/3/4 也未闭环。
2. **运行时形态不匹配**：Python 后端是"按需拉起、stdin EOF 即退出"的请求-响应进程（`cli/main.py`），Electron 退出它就结束。调度与监视都需要**常驻**：调度线程、事件推送、错过补跑（catch-up）、时区/夏令时语义 —— 这是新增一种运行时形态，不是加几个 handler。
3. **IA 已冻结**：[07-UI设计规范](./07-UI设计规范.md) §1 与 [08-前端页面与功能清单](./08-前端页面与功能清单.md) §2.1 冻结了四模块（工作流 / 任务 / 工具 / 设置）。监视器要独立 UI 就得加第 5 个模块，与冻结契约冲突；未来真要做，**先解冻 IA**。
4. **硬约束**：后端仅标准库 → 没有文件系统事件 API（`watchdog` 是第三方），目录监视只能轮询快照 diff 或 `ctypes` 调平台接口；设备连接触发属 Android 领域内容，与应用"本体零领域内容"的定位冲突，只应作为插件/领域包而非核心能力。

### 8.2 无人值守的前置缺口（与"要不要做定时"无关，建议先做）

| 缺口 | 现状 | 影响 |
|---|---|---|
| **`output/runs/` 没有上限裁剪** | 只有 `history/` 有 `max_runs` / `max_bytes`；`runs/` 产物没有任何自动清理（只能手动 `storage.clear {target:"runs"}`） | 反复运行工作流（**手动跑也一样**）会无限堆积产物 |
| 没有并发互斥 | CLI 每次随机 `run_id`，同一模板可被并发触发（互不冲突，也不互斥） | 定时/重复触发需要"跳过或排队"策略 |
| 应用关闭时没有结果通道 | 只有退出码与 `history`（`history.list` 摘要含 `status`） | 无人值守时无法及时知道失败 |
| `run` 只能 `--input key=value` | 没有 `--input-file` | 文件类/结构化入参不好无人值守地喂 |

### 8.3 分级与交付形态

| 级别 | 内容 | 成本 | 何时做 | 需要动的接口 |
|---|---|---|---|---|
| **L1 定时执行（可插队）** | **不新增运行时**：用 OS 计划任务（Windows `schtasks` / Linux `cron`）调已有的 `cli.py run <模板名> --input k=v --json --run-id <hex>`，或直接 `cli.py run --task <任务名>`（**任务定义 = 工作流 + 保存的入参**，随 WP7 于 2026-09-28 落地，见 [03-数据模型 §6.3](./03-数据模型.md)）。`run` 已支持模板名、重复 `--input`、`--task-id`、`--json`、`--timeout`、`--task`，只差 8.2 的 `--input-file`、互斥与 `runs/` 治理 | 半天～1 天 | 一旦出现真实的"定点跑某个工作流"需求即可单独插队，**不必等 T24** | 无新 IPC；CLI 参数 + 计划任务文档示例 |
| **L2 时间段执行（应用内）** | 若语义只是"在窗口内被触发"，`schtasks /RI`+`/DU` 就能覆盖，仍属 L1；需要"窗口内不重复、错过补跑、跨天/时区、按窗口暂停恢复"时升级为：后端常驻调度 + `schedule.*` API + **任务定义上的启用开关**（WP7 已提供可挂开关的实体，无需再发明"任务"概念） | 数天，成本主要在**语义与状态**，不在代码量 | Phase 3 任务闭环稳定之后 | 新 API 键（必须同步 `src/shared/ipc/protocol.ts` 与 `tests/shared-contracts.test.mjs`）+ IA 内新增"触发器"区块 |
| **L3 监视器** | 目录监视（轮询或平台 API）→ 事件源抽象；设备连接触发只作为插件/领域包。UI 落点需先决定 IA 是否放宽（第 5 模块 或"任务-触发器"子区） | 较大 | 更远期 | 同上 + 常驻事件推送通道（现有 `stream-event` 绑定单次请求，不能直接复用） |

### 8.4 L2 开工前必须先定的语义（先定语义再写代码）

- **窗口**：起止时间（可跨天）、时区、夏令时处理；
- **不重叠**：上一轮还在跑时——跳过 / 排队 / 取消上一轮；
- **补跑（catch-up）**：应用关闭期间错过的触发点补不补、补几轮、算不算同一轮；
- **失败策略**：连续失败 N 次后自动停用并通知；
- **来源可见性**：运行记录里区分"手动 / 定时 / 监视器触发"（当前 `history.source` 记录的是模板名或文件路径，未来可能需要显式触发来源字段）。

## 决策原则

- schema 里不留"存而不用"的字段：用不上的能力就不要出现在模型里（`condition` / `on_success` / `edges` 已按此原则删除，`from_dict` 仍忽略老 JSON 里的同名键，存量文件不会因此加载失败）。
- 排期时优先取"前置依赖最少、对已有用户收益最大"的项（如运行历史），再考虑 DAG 类结构性改动。
