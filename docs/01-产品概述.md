# 01 产品概述

> 本文档面向维护者与后续开发者，描述 Blank Tool 的定位、目标用户、核心使用场景、现有功能模块与技术栈。架构与数据模型的细节见 [02-系统架构.md](./02-系统架构.md) 与 [03-数据模型.md](./03-数据模型.md)。

## 1. 定位

Blank Tool 是一个**本地工作流编排应用**，采用 **Electron + Vue 3 + Python 三进程桌面应用**架构：

- 前端（Renderer）：Vue 3 + Vite + Pinia + Vue Router + Naive UI
- 桌面壳（Main）：Electron 主进程，负责窗口、IPC、Python 子进程管理
- 后端（Backend）：Python 3，通过 stdin/stdout JSON-RPC 与主进程通信

通用模型是**领域无关**的：把本地命令行工具、脚本与运行时封装为**带类型化出入参的工具**，用**线性工作流**编排成可保存、可复用的模板，再在任务中心或无头 CLI（`cli/cli.py`）中执行。核心能力包括工作流引擎、类型化出入参（工具/端口）、模板、任务中心、工作流编辑器，以及工具与环境描述符的自动发现（`cli/registry/tools/*.json`、`cli/registry/environments/*.json`）。

应用本体**不包含任何领域内容**：不内置工作流、不内置工具描述符、不内置二进制。仓库 `examples/` 提供可导入示例包：**通用示例工作流**（`examples/workflows/generic/`，仅用内置原子工具、零外部依赖、导入即跑；已含 `dir-report.json` 目录扫描报告、`text-scanner.json` 文本模式递归搜索）与 **Android 示例包**（工作流 5 个 + 工具描述符 7 个）：工作流经工作流管理页/编辑器导入，描述符经工具管理页导入；二进制（ADB、Apktool、JRE 等）由用户自行准备：本地 `runtime/` 目录、自定义工具路径或系统 PATH。该调整**已决策**，在分期计划中实施（见 [05-分期开发计划.md](./05-分期开发计划.md#phase-1-基础模型)）；当前仓库仍内置 `cli/workflows/` 与 `cli/registry/tools/`，属待迁移的过渡状态。

## 2. 目标用户

通过访谈确认，产品定位为**自用 / 小团队内部工具**，不是面向大众的商业产品。这决定了项目的几个基调：

- 文档与代码注释以"可维护"为目标，实用优先，不做大而全的营销包装；
- 发布以 **Windows 轻量发布**为主（`electron-builder` 的 NSIS 安装包，见 `package.json` 的 `build.win` 配置）；
- 领域二进制**随包不分发**：Android 相关工具（ADB / Apktool / JRE 等）由用户自行提供（本地 `runtime/` 目录、设置中的自定义工具路径或系统 PATH，见 [02-系统架构.md](./02-系统架构.md#5-路径解析)）；通用工作流能力不依赖这些；
- 仓库约定（见根目录 `AGENTS.md`）：TypeScript 不开启严格模式，后端 Python 仅用标准库、无 `requirements.txt`，因此**不要按默认严格风格大面积重构旧代码**。

## 3. 核心使用场景

使用场景本质上就是**工作流模板**：把本地工具封装为带类型化出入参的工具后，任意"多步本地操作"都能编排成一个场景。Android 是**示例场景集**（经 `examples/` 导入使用，导入功能规划中），访谈确认的 4 类场景中 3 类已实现，1 类为规划中。

**Android 示例工作流（经 examples/ 导入，规划中）**：

| # | 场景 | 状态 | 主要落点 |
|---|------|------|----------|
| 1 | **下载 → 分析 → 安装** | 已实现 | 远程下载 APK（流式进度）→ 自动分析 → 安装到设备；工作流示例 `cli/workflows/download-install.json`（规划迁至 `examples/workflows/android/`，改经导入使用） |
| 2 | **反编译 → 修改 → 重编译 → 重签名 → 安装** | 已实现 | Apktool 反编译/重编译 + 签名工具（V2 方案）；工作流示例 `cli/workflows/decompile.json`、`recompile.json`、`sign.json`（规划迁至 `examples/workflows/android/`） |
| 3 | **AAB → APKS → 安装** | 已实现 | bundletool 把 `.aab` 转为 `.apks` 并安装；工作流示例 `cli/workflows/aab-install.json`（规划迁至 `examples/workflows/android/`） |
| 4 | **脚本执行（自检 / 数据分析）** | **规划中** | 复用工作流引擎与内置工具（`shell.exec`、`code.exec` 等），以命令或图形方式执行自检/分析脚本；目前引擎与内置工具已具备基础，面向脚本的完整能力尚未落地 |

在通用能力上，引擎与内置原子工具（`file.read`、`text.replace`、`net.download`、`shell.exec`、`code.exec` 等）已可编排任意本地操作，不限于 Android；导入 `examples/` 的 Android 示例（规划中）后上表场景即可直接运行；另有已就绪的**通用示例工作流**（`examples/workflows/generic/`，仅用内置原子工具、零外部依赖、导入即跑，已提供 `dir-report.json` 与 `text-scanner.json`）可供冷启动直接体验；单选/多选入参、脚本作为工具等为**规划中**（见 [06-后续路线图.md](./06-后续路线图.md)）。

场景 1-3 已分别有对应的**工作流模板 JSON**（现位于 `cli/workflows/`，规划迁移至 `examples/workflows/android/`），可以不经图形界面，通过 `cli/cli.py run` 命令直接执行（详见 [03-数据模型.md](./03-数据模型.md#5-工作流-json-示例)）。

## 4. 现有功能模块

通用核心是**工作流编辑器**与**任务中心**。Android 相关页面（设备管理、APK 工具等）是**已退役模块**（已决策，去向见第 6 节）：应用不保留任何领域专属页面，Android 能力全部通用化——导入 `examples/` 的工作流与工具描述符后，在任务中心与其他任何工作流一样执行。界面按页面划分（`src/renderer/views/`，路由见 `src/renderer/router/modules/`）：

> **重设计（已决策，待实施）**：下表描述的是当前版本的真实形态。其中 任务管理、设备管理、APK 工具 对应的页面（PackagePage / DevicePage）、服务与 store、以及对应后端 handler 均已决策**退役**；重设计后由 工作流 `/workflows`、任务 `/tasks`、工具 `/tools`、设置 `/settings` 四个一级模块取代（结构/交互重设计；视觉以用户确认的 Stitch 设计稿为准，去向见第 6 节）。

| 模块 | 页面 / 路由 | 能力 | 说明 |
|------|-------------|------|------|
| 任务管理（任务中心） | `PackagePage.vue`（`/package`） | 远程下载、一键操作（下载后自动分析/安装/反编译/重编译/重签名）、任务队列并行、历史记录本地持久化 | README 中"工作流与任务管理"章节 |
| 设备管理 | `DevicePage.vue`（`/device`） | ADB 设备自动检测、TCP/IP 远程连接、重启/恢复模式/Bootloader、Shell 命令、APK/AAB/APKS 安装、卸载/导出、Logcat 实时输出 | 通过 `src/main/ipc/` 与后端 `adb_handler.py` 通信 |
| APK 工具 | `PackagePage.vue`（`/package`） | 应用分析（包名/版本/权限/SDK）、Apktool 反编译/重编译（资源/源码选择性）、签名配置管理、V2 签名 | 后端 `apk_handler.py` 的 `apk.analyze` / `apk.decompile` / `apk.recompile` / `apk.sign` 等 |
| 工作流编辑器 | `WorkflowEditorPage.vue`（`/workflow-editor`） | 基于 vue-flow 的画布式编排，模板保存/加载/执行 | 后端 `template_handler.py` 与 `workflow_handler.py` |
| 设置 | `SettingsPage.vue`（`/settings`） | 请求超时、签名配置、路径配置、主题、语言 | 配置走 `src/main/stores/appStore.ts`（electron-store） |
| 其他 | `DiagnosticsPage.vue`、`OtherToolsPage.vue`、`AboutPage.vue` | 自检诊断、插件页、关于 | 插件目录 `cli/plugins/` 目前为空 |

### 4.1 主题系统

三模式（浅色 / 深色 / 自动跟随系统），由 CSS 变量驱动，见 `src/renderer/assets/styles/themes/`。

## 5. 技术栈

| 层 | 技术 | 依据 |
|----|------|------|
| 前端 | Vue 3、Vite、Pinia、Vue Router、Naive UI、vue-i18n | `package.json` `dependencies`；`README.md`"技术栈"章节 |
| 工作流画布 | @vue-flow/core + background/controls/minimap | `package.json`；`WorkflowEditorPage.vue` |
| 桌面框架 | Electron 38（`electron`、`vite-plugin-electron`） | `package.json` `devDependencies` |
| 状态 | Pinia，自定义 localStorage 持久化插件 | `src/renderer/main.ts`；`AGENTS.md` |
| 后端 | Python 3（仅标准库），JSON-RPC over stdin/stdout | `cli/main.py`；`README.md` |
| 构建/发布 | electron-builder 26；`npm run release` 一键发版 | `package.json` `build` 字段与 `scripts` |

版本号由 `package.json` 的 `version` 字段驱动（当前 `2.2.0`），发版脚本统一维护（`scripts/release.mjs`）。

## 6. 现状 vs 规划

| 领域 | 现状（已实现） | 规划（标注"规划中"/"目标设计"） |
|------|----------------|----------------------------------|
| 工作流执行 | 线性模式：`node.next` 是唯一控制流，`edges` 必须为空；`on_failure` 支持 `fail` / `skip` / `retry:N` | DAG 模式（`edges`、`condition`、`on_success` 字段已预留并存储，当前不执行，见 [03-数据模型.md](./03-数据模型.md#2-工作流节点-workflownode)) |
| 工作流编排 | 画布编辑器 + 模板 CRUD（`template.save/load/list/delete/execute`） | 分支/条件执行；节点级调试 |
| 入参类型 | 基础类型：文件/文件夹/文本/数字/布尔/JSON（BaseType，见 [03-数据模型.md](./03-数据模型.md#4-类型系统-typeannotation)） | **规划中**：单选/多选列表（Port 增加 `options` 与 `multi` 字段），编辑器暴露八种入参类型；动态数据源绑定（如设备列表）已明确延后 |
| 工具模型 | 内置原子工具（`file.read`、`text.replace`、`net.download`、`shell.exec` 等 20 个）已按"声明 ports + 类型化 execute"实现；描述符工具（apktool/adb 等）由节点在 `params.args` 里裸写 CLI 参数 | **目标设计**：统一「操作」模型，工具 = JSON（元信息 + env_deps + validate/version + `operations[]`），节点绑定 tool+operation 与类型化输入，脚本统一为 `*_script` 类型（详见 [03-数据模型.md](./03-数据模型.md#102-目标设计统一操作模型)) |
| 脚本执行场景 | 工作流引擎可运行任意编排（含 `shell.exec` 等） | **规划中**：自检/数据分析脚本库 |
| 发布 | Windows NSIS 安装包；GitHub Releases 自动更新（`electron-updater`，`dev-app-update.yml`） | macOS / Linux 目标已配置（`package.json`），非重点验证平台 |
| 领域内容分发 | 现状：Android 工作流（`cli/workflows/`）与工具描述符（`cli/registry/tools/`，7 个）随包内置 | **规划（已决策）**：零内置，迁至 `examples/` 作为可导入示例包；工作流经管理页/编辑器导入、描述符经工具管理页导入，二进制用户自备；`extraResources` 仅保留 `cli/` |
| 界面与模块 | 现状：PackagePage（任务/APK 工具）、DevicePage（设备管理）、/plugins 占位页等设备专属页面 + 对应后端 handler | **规划（已决策）**：彻底退役，新四模块 IA（工作流/任务/工具/设置）；结构/交互重设计；视觉以用户确认的 Stitch 设计稿为准 |
| 冷启动与体验 | 现状：无引导的空列表；任务记录已持久化 | **规划中**：通用示例导入即跑、空状态引导、历史筛选、任务完成/失败应用内提示 + 可选系统通知 |
