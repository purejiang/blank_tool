# 05 分期开发计划

本计划基于与产品方的访谈确认，按"先稳定、再打底、后闭环"的顺序划分为 Phase 0~6。每个阶段给出目标、任务清单与验收要点。进度追踪与任务拆解以本文件为准。

## 阶段总览

| 阶段 | 目标 | 关键产出 | 依赖 |
|---|---|---|---|
| Phase 0 | 稳定性（阻塞项） | 修掉 protocol 同名冲突，后端可正常启动 | 无（阻塞一切） |
| Phase 1 | 基础模型 | 单选/多选入参类型；统一工具「操作」模型；领域内容外部化（examples/ 导入示例包） | Phase 0 |
| Phase 2 | 工作流编辑与管理（MVP） | 工作流级入参/出参面板、按 operation 渲染节点配置、管理列表页、导入导出、子工作流 | Phase 1 |
| Phase 3 | 任务执行闭环 | 任务页 workflow-first 表单、实时节点进度/日志/出参展示 | Phase 2 |
| Phase 4 | 工具与环境管理 | 可写覆盖目录、描述符 CRUD、管理页（tools + environments） | Phase 0 |
| Phase 5 | 脚本执行 + CLI 完善 | 脚本作为工具/节点、`cli.py tool <name>` 子命令 | Phase 4 |
| Phase 6 | 收尾 | i18n 补全、`ApiMethodMap` 类型化、稳定性回归、文档完善 | 全部 |

## Phase 0：稳定性（阻塞项）

**目标**：消除后端启动即崩溃的导入错误，让全链路可跑；`npm run check` 与 pytest 全绿。

**任务清单**

1. 合并消息类：把 `backend/app/protocol.py` 中的 `BackendResponse`、`BackendSuccessPayload`、`BackendErrorPayload`、`BackendStreamEvent`、`BackendApiRequest`、`ErrorCode` 并入 `backend/app/protocol/` 包（建议新建 `protocol/messages.py`）。
2. 统一导出：在 `backend/app/protocol/__init__.py` 一并导出消息类与既有类型系统（`BaseType`、`TypeAnnotation`、`TypeRegistry`、`Port`、`PortSet`）。
3. 删除 `protocol.py`，确保所有 import 可用：
   - `backend/main.py:26`（`from app.protocol import ErrorCode`）
   - `backend/app/api_handler.py:19-24`（`from app.protocol import (BackendResponse, BackendSuccessPayload, BackendErrorPayload, ErrorCode)`）
   - `backend/app/workflow/definition.py:29`、`backend/app/workflow/validation.py:41`
   - `backend/app/tools/descriptor_tool.py:28`、`backend/app/tools/builtin/*.py`
4. 加导入回归测试（例如 pytest 里 import `app.main` / `app.api_handler` / `app.protocol`，断言消息类可导入）。
5. 顺带解锁 `cli.py`：去掉内联 bootstrap，改为复用 `main.bootstrap`（`backend/cli.py` 42~49 行注释已说明原委）。

**验收要点**

- `python backend/main.py`（或启动应用）后端正常启动，日志无 `ImportError`。
- `npm run check` 通过；`pytest tests/contracts/ tests/backend/` 通过。
- `cli.py list-tools` / `run` 等子命令正常（不再依赖内联 bootstrap 的脆弱路径）。

## Phase 1：基础模型

**目标**：给工具/工作流提供更强的类型表达力，为编辑器与任务表单打底；同时落地**已决策的领域内容外部化**（应用零内置领域内容）。

**任务清单**

0. **领域内容外部化（已决策）**：
   - `git mv` 工作流（`backend/workflows/*.json`）与工具描述符（`backend/registry/tools/*.json`）至 `examples/{workflows,tools}/android/`；
   - 删除 `copy_defaults` 死代码（`backend/app/template/store.py`，从未被调用）；
   - `package.json` 的 `build.extraResources` 移除 `runtime` 条目（仅保留 `backend/`）；
   - 新增 `examples/README.md` 导入指引：工作流经管理页/编辑器导入、描述符经工具管理页导入、二进制自备（本地 `runtime/`、自定义路径或系统 PATH）；
   - **空注册表回归**：`backend/registry/tools/` 清空后应用仍可完整使用 18 个内置原子工具与通用工作流能力。
1. **单选/多选入参类型**：`Port` 增加 `options: List[str]` 与 `multi: bool` 字段，贯穿后端 schema（`backend/app/protocol/ports.py`）、序列化（`to_dict` / `from_dict`）、校验与编辑器渲染。
2. **统一工具「操作」模型**：描述符增加 `operations[]`，每个操作含类型化 `inputs` / `outputs` 与 `args` 映射；引擎（`backend/app/workflow/engine.py`）支持按 operation 校验输入、拼命令、返回类型化输出。
3. **迁移示范工具**：把核心 APK 链路工具（apktool / adb / bundletool）迁移到 operations 模型作为范例。

**验收要点**

- `Port` 序列化往返包含 `options` / `multi`，后端校验不接受非法选项值。
- 至少 3 个工具（apktool / adb / bundletool）能用 operations 声明并正确执行。
- 空注册表回归：`backend/registry/tools/` 为空时后端可启动，`cli.py list-tools` 仍列出 18 个内置原子工具。
- 现有线性工作流不回归（`pytest tests/contracts/test_workflow_contracts.py`、`test_template_contracts.py` 通过）。

## Phase 2：工作流编辑与管理（MVP）

**目标**：把编辑器从"能画能跑"提升到"可管理的工程化编辑"。

**任务清单**

1. 编辑器新增**工作流级入参/出参编辑面板**：支持 8 种类型（含单选/多选）。
2. **节点配置按所选 operation 渲染**：节点配置面板改为展示该 operation 的类型化输入（文件/文件夹、字符串、布尔、单选/多选等），而非通用 `args` 列表。
3. 新增**工作流管理列表页**：一级路由 `/workflow` 展示已存模板（名称、描述、时间、标签、节点数）；编辑器改为二级页 `/workflow/editor/:name?`。
4. **导入/导出 JSON**：工作流可导出为 `WorkflowDefinition` JSON、可导入校验后入画布（复用 `serializer.ts` 的 `validateOnDeserialize`）。这是 `examples/workflows/android/` 示例工作流的引入途径。
5. **子工作流组合节点**：节点可调用已存模板作为子工作流；带**递归防护**（深度上限 + 在途名称集合，防止 A 调 B、B 调 A 死循环）。

**验收要点**

- `/workflow` 列表页与 `/workflow/editor/:name` 路由可达，旧 `/workflow-editor` 路由可跳转或迁移。
- 工作流级入参/出参面板与节点按 operation 渲染均可用；导出文件可再导入。
- 子工作流嵌套出现循环时给出明确报错而非栈溢出。

## Phase 3：任务执行闭环

**目标**：让用户在任务页以"选模板 → 填表单 → 看实时进度"的方式跑工作流。

**任务清单**

1. **任务页（PackagePage）workflow-first**：选模板 → 按入参类型动态渲染表单（文件/文件夹选择、字符串、布尔、单选/多选等）→ 调用 `template.execute`。
2. **实时节点生命周期事件**：引擎发出 `node_started` / `node_completed` / `node_failed`（事件 schema 见 `backend/app/workflow/streaming.py`），经既有 `stream-event` 通道转发到渲染层；任务卡片展示节点进度、日志与类型化出参。
3. 现有 APK 一键流程保留但**降为次要**入口。

**验收要点**

- 选择模板后表单字段与入参类型一一对应，提交后任务中心出现任务，节点状态实时流转。
- 节点失败时 `on_failure` 语义正确生效，任务状态与错误信息可读。

## Phase 4：工具与环境管理

**目标**：用户可在应用内导入/删除工具与环境描述符。工具导入即 `examples/tools/android/` 示例包描述符的引入途径。

**任务清单**

1. **可写覆盖目录**：`<output_dir>/registry/{tools,environments}`，持久化用户自定义（含路径 `overrides.json`）。
2. **描述符 CRUD**：新增 `env.*` 与工具导入/删除 handlers；导入校验描述符合法性。
3. **工具与环境管理页**：新增页面（tools tab + environments tab），支持查看、导入、删除。

**验收要点**

- 导入合法描述符后立即出现在 `tool.get_tools` / `workflow.list_envs` 中；删除后消失。
- 非法描述符导入被拒绝并给出原因。

## Phase 5：脚本执行 + CLI 完善

**目标**：让用户脚本成为一等公民，CLI 补齐工具调用能力。

**任务清单**

1. **脚本作为"可导入的依赖环境的工具/节点"**：脚本节点类型 `*_script`，带 `env_deps` 与 `operations`（有参/出参），可被工作流引用。
2. **CLI 新增 `tool <name>` 子命令**：单独调用某个工具（带参/出参），不依赖 Electron。
3. CLI 支持运行脚本。
4. 迁移其余工具到 operations 模型。

**验收要点**

- `python cli.py tool <name> --input key=value` 能独立调用工具并打印类型化结果。
- 脚本节点在引擎与 CLI 双路径下行为一致。

## Phase 6：收尾

**目标**：补全工程化短板，交付可发版状态。

**任务清单**

1. i18n（zh-CN + en-US）补全：所有新增 UI 文案双语文档化。
2. `src/shared/ipc/protocol.ts` 的 `ApiMethodMap` 类型化补全（对齐后端 `API_MAP`，保持 `shared-contracts.test.mjs` 100% 覆盖断言）。
3. 稳定性回归：`npm run check`、`pytest tests/`、Playwright e2e 全绿。
4. 文档完善：同步更新 [01-产品概述](./01-产品概述.md) / [02-系统架构](./02-系统架构.md) / [03-数据模型](./03-数据模型.md) / [04-开发指南](./04-开发指南.md)。

**验收要点**

- 全量测试通过；双语文案无缺失；`ApiMethodMap` 覆盖所有后端方法。

## 依赖说明

- **Phase 0 阻塞一切**：protocol 冲突不修，后端起不来，后续所有阶段都无法联调。
- **Phase 1 是 Phase 2/3 的类型基础**：节点按 operation 渲染（Phase 2）与任务表单（Phase 3）都依赖 `operations[]` 与单选/多选入参类型。
- **Phase 5 脚本依赖 Phase 4 的环境导入**：脚本需要 `env_deps` 指向已导入的环境，所以环境管理（Phase 4）先行。
- Phase 2 与 Phase 4 均只依赖 Phase 0/1，可并行推进（若资源允许）。
