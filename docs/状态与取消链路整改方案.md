## 0.5 取消的必要性分层（2026-09-19 复核，回答「取消功能是否必需」）

把「取消」拆成四层，因为它们的需求强度完全不同：

| 层 | 触发者 | 现状 | 是否必需 |
|---|---|---|---|
| A 交互中断 | 用户 Ctrl+C | `cli.py` 无 `signal` / `KeyboardInterrupt`（import 清单已核实） | 部分，见下 |
| B 程序化取消 | Stop 按钮 / `request.cancel` | 渲染层唯一调用方 `DiagnosticsPage.vue:187`；**工作流编辑器无 Stop** | 必需（新前端几乎必然要加） |
| C 自动回收 | **主进程自己** | `commandHandlers.ts:47-75` 静默 300s 后**主动**发 `request.cancel` | **必需——当前就在线运行** |
| D 关停清理 | 后端退出信号 | `main.py:168-181` `_cancel_all_runs` → `_drain_pending` | 必需（进程卫生） |

**C 是决定性证据**：取消链路不是「待实现的功能」，而是应用**现在就在调用**的回收机制
（`commandHandlers.ts:52-72` 用 `cb.taskId` 构造 `request.cancel` 并发往后端 stdin）。
所以「要不要取消」其实没有选择权——骨架必须留。

### ⚠️ 对 B1.1 必要性的重要修正

原文档 §6.1 称「`descriptor_tool.py:613` 那个空 dict 是 adb/aapt/apktool 所有长任务取消失效的
主因，先修它收益最大」——**该表述不准确**。核实各工具的 spawn 形态后：

| 工具 | Windows spawn 形态 | 有孙进程 | `terminate()` 够吗 |
|---|---|---|---|
| `exec.shell`（core 内置） | `cmd.exe /c "<字符串>"`（`exec_tools.py:165-177`） | ✅ 真身在孙 | ❌ 不够 |
| `exec.code` | `[python, -c, code]` list（`exec_tools.py:292`） | ❌ | ✅ 够 |
| descriptor `java_jar`（apktool / bundletool） | `[java, -jar, x.jar]` list（`descriptor_tool.py:693`） | ❌ | ✅ 够 |
| descriptor `binary`（adb / aapt / apksigner） | `[exe, ...]` list | ❌ | ✅ 够 |
| descriptor `shell_script` | `[cmd.exe, tool.cmd, ...]`（`:689-690`） | 视脚本内容 | ⚠️ 可能 |
| `exec.shell`（Unix） | `shell=False` + `shlex.split`（`:171-172`） | ❌ | ✅ 够 |

补充事实：`base_executor.py:159-165` 只在**命令是字符串**且 `shell is None` 时才置 `shell=True`；
descriptor 工具走的是 **list + 显式 shell 选择**，本身**不是** `cmd /c` 字符串形态。

**结论**：树杀（B1.1）的真实服务对象是 **`exec.shell`(Windows) 与 `shell_script`**，
**不是** adb / aapt / apktool。descriptor 工具的病是**取消信号根本送不到**
（`cancel_check` 缺失 → 不轮询 → 跑满 timeout），不是「杀不干净」；
`holder` 传真之后 `terminate()` 对它们是**够的**。

→ **B1.1 的完整度可降级**：Windows 上先用 `taskkill /F /T /PID` 即可覆盖 `cmd.exe /c`；
Job Object 只在 `cmd /c "start /b ..."` 这类**父先亡**的场景不可替代，可放第二阶段。

### 关于 A 层的现状（比原文档乐观）

全仓库**无 `creationflags` / `CREATE_NEW_PROCESS_GROUP` / `start_new_session`**（已 grep 核实），
即子进程仍挂在同一控制台进程组下。因此在真实控制台里 Ctrl+C 时，Windows 会把
`CTRL_C_EVENT` **广播给组内所有进程**，子进程通常跟着退出——
原文档「Ctrl+C 无任何清理、子进程变孤儿」的表述**过强**。

真正会留孤儿的是：
1. **无控制台**场景（被别的脚本调用 / `| tee` 重定向 / CI 管道）——`CTRL_C_EVENT` 无处广播；
2. **子进程自建分离进程**（`start /b`、GUI 子系统进程）；
3. **B1.4 落地之后**——`CREATE_NEW_PROCESS_GROUP` 主动切断广播，把 1、2 变成必然。

→ 所以 **B7 是「从不精确到精确」，不是「从 0 到 1」**；而 **B1.4 与 B7 的强耦合反而更硬**。
（终审更新：B1.4 的 Windows 侧 flag 已整个删除，该耦合**收窄为 Unix only**，见 §0.6 / B1.4。）

### 0.7 实施期复审（第四轮，边落地边对码，7 项修正）

前三轮审的是**方案**，这一轮审的是**代码**。7 项全部是「照原方案直译会埋雷」的地方：

| # | 严重级 | 发现 | 处置 |
|---|---|---|---|
| 1 | 🔴 **会误杀无关进程** | `assign_to_job` 原稿带「取不到 `_handle` 就用 PID 走 `OpenProcess`」兜底。真实 `Popen` 在 Windows 上**必定**有 `_handle`，该分支只会在伪对象上触发；而 PID 一旦被系统复用，它会把**无关进程**拉进 job，随后 `TerminateJobObject` 直接杀掉它 | 删掉兜底，`assign_to_job` 改为**严格 handle-only** |
| 2 | 🟠 **句柄二次关闭** | `executor._terminate_job` / `_release_job` 在 holder 路径上取不到句柄后，会回落到关闭 `self._job` 这份**镜像**。取消路径已经先把句柄取走并关闭，这里就是**二次 `CloseHandle`**——而该句柄值可能已被系统回收给别的对象 | holder 存在即视为句柄归属方：镜像置 `None`、且不再触碰 |
| 3 | 🟡 **PID 复用窗口** | `_kill` 在 job 已成功树杀之后仍会走 `taskkill /T /PID` 回退。此时直接子进程已经冷掉，PID 理论可被复用 | 新增 `_job_managed` 标志：一旦 job 覆盖过该进程，job 就是唯一杀法，**跳过 PID 回退** |
| 4 | ℹ️ 小 bug | `_communicate_cancellable` 的 `' '.join(cmd)`：`shell=True` 时 `cmd` 是**字符串**，join 会把命令拆成逐字符，超时报错文案全是空格 | 仅对 `list` 做 join |
| 5 | ⚠️ **回归** | `DescriptorTool` 现在硬依赖 `context.cancel_check` / `context.cancelled()`（与 `exec_tools.py:203,230`、`flow_tools.py:287` 的既有写法一致），把 4 处用 `SimpleNamespace` 伪造 `ToolContext` 的测试**打挂**了 | 4 处改用**真 `ToolContext`**（dataclass，`work_dir` 必填、其余可选），杜绝将来再次漂移 |
| 6 | 🔴 **Windows 上会「探测即杀」** | `_pid_alive` 用 `os.kill(pid, 0)` 判活——但 Windows 的 `os.kill` 对非控制台信号一律走 `TerminateProcess`，**这个「探测」会把目标杀掉**。当时只被 POSIX-only 的 `_killpg_tree` 调用所以没爆，但一个以 Windows 为主场的模块里摆着这种函数就是雷 | 提为公开 `pid_alive()`：Windows 用 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`（**只读、不可能杀**），POSIX 保留 `os.kill(pid, 0)` |

> 第 1、2、3 条都源自同一个设计要点：**job 句柄有唯一归属方**。

## 2. 后端实施清单

### B1 取消真正能中断进程

#### B1.1 进程树终止（🔴 终审重写：Job Object 必须在 **spawn 时**创建）

> 🔴 **终审发现（前两轮子 agent 审查都漏了）**：原设计在**取消时**才
> `CreateJobObject → AssignProcessToJobObject(pid) → CloseHandle` —— 这只杀得了被 assign 的
> **那一个**进程。孙进程在 job 创建之前就已存在，**从不在 job 里**：job 成员靠父子继承
> （Vista+ 子进程自动进入父进程的 job），**不能事后追认**。原稿「为什么首选」里声称覆盖的
> 「父已亡孙 reparent」「取消竞态期间新生的子进程」两个场景，恰恰**只有 spawn 时建 job 才成立**。

正确设计：**job 在 spawn 时创建，handle 存进 `process_holder`；取消时只需 `CloseHandle`**。

```
proc_tree.py（零第三方依赖，TaskManager 与 ProcessExecutor 都能 import 而不成环）

Windows — spawn 时（ProcessExecutor.run 在 Popen 之后立即调用）：
    job = create_kill_on_close_job()      # CreateJobObjectW +
                                          # SetInformationJobObject(
                                          #   JobObjectExtendedLimitInformation,
                                          #   JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)
    AssignProcessToJobObject(job, proc._handle)
    holder["job"] = job                   # 创建/赋值失败（权限、嵌套 job 限制）时
                                          # holder["job"]=None 并记 warning（走回退）
Windows — 取消/超时时：
    close_job(holder)                     # CloseHandle(job) → 内核原子终止整棵树。
                                          # 宿主崩溃 / 被 kill -9 时 OS 关闭句柄同样清树
                                          # —— 这才是 Job Object 真正的「为什么首选」
Windows — 回退（spawn 时 job 建失败的那些进程）：
    subprocess.run(["taskkill", "/F", "/T", "/PID", str(pid)],
                   creationflags=CREATE_NO_WINDOW, timeout=grace)
Unix：spawn 时 start_new_session=True（见 B1.4）；
    取消时 os.killpg(os.getpgid(pid), SIGTERM) → 等 grace → SIGKILL；
    进程已无 pgid 时回退 proc.terminate()
降级：任何平台上述都失败时 proc.terminate()，记 warning（不要静默吞掉）
正常结束时：finally 里 close_job —— 否则每次执行泄漏一个 job 句柄
```

配套改动：
- `ProcessExecutor.run`：spawn 后建 job、存 `holder["job"]`；正常返回路径与 `_kill()` 都要关 job。
- `TaskManager._terminate`：先 `close_job(holder)`，holder 里没有 job 才 `terminate()` →
  再回退 `terminate_tree(pid)`。
- 与 §0.5 的降级结论合并：第一阶段可以先只做 `taskkill /F /T`（覆盖 `cmd.exe /c` 主场景），
  spawn-time Job Object 作为第二阶段补「父先亡 / 宿主崩溃」的内核级保证。

**关于 `CREATE_NEW_PROCESS_GROUP` 与 `/T` 的关系**（原方案的判断正确，保留）：
前者只影响 Ctrl+C 投递、不减父子关系，不能替代树杀。两者都要：
Windows 上进程组用于信号隔离，Job Object / `/T` 用于真正清理。

#### B1.2 `cli/app/tools/builtin/exec_tools.py` — ShellExec / CodeExec

现状 `:175` / `:291` 用裸 `subprocess.run(...)`，既不登记 holder 也不读 cancel_check。
改用 `ProcessExecutor`：

```python
executor = ProcessExecutor(
    timeout=timeout,
    process_holder=context.process_holder,   # 引擎已注入
    cancel_check=context.cancel_check,        # 引擎已注入
)
try:
    rc, out, err = executor.run(args, cwd=cwd, env=env, shell=shell)
except TimeoutException:
    return {"returncode": -1, "stdout": "", "stderr": f"timeout after {timeout}s", "success": False}
if context.cancelled():
    raise WorkflowCancelled()        # 引擎归类为 cancelled（见 B2）
return {"returncode": rc, "stdout": out, "stderr": err, "success": rc == 0}
```

**必须保留的既有语义**（否则是行为回归）：

- Windows → `shell=True` + 字符串命令；Unix → `shlex.split` + `shell=False`（`:165-172` 原样保留）。

- `ProcessExecutor` 硬编码 `encoding='utf-8', errors='ignore'`（当前用默认编码）。
  可接受（`errors='ignore'` 兜底），但要在改动说明里写明。
- `raise WorkflowCancelled()` 是**已确立契约**（`flow_tools.py:287-288` 即如此），
  引擎 `_execute_tool:687-688` 会 catch 并转 `_NodeRun(cancelled=True)`。
- `ProcessExecutor.run` 签名是 `cmd: list[str]`（`executor.py:44`），而 Windows `shell=True`

#### B1.5 `returncode or -1` 的 0 值陷阱（⚠️ 严重度下调）

`executor.py:75` 与 `:104` 写了 `return self.process.returncode or -1, "", ""`。
改为：

```python
rc = self.process.returncode
return (rc if rc is not None else -1), "", ""
```

> ⚠️ **审查修正**：原文档称它「把成功报成失败」，**夸大了**。两处 `_kill()` 内部都会
> `wait()`，`returncode` 会被回填，绝不会是 `None`；`0 or -1` 只在「取消竞态恰好撞上正常退出」
> 的窄窗口发生。仍应修（语义正确性），但它是 P2 而非 P0，不要用它抢占 B1.1~B1.3 的优先级。

#### B1.6 取消时不要丢弃已产出的输出（⚠️ 审查新增）

`executor.py:104` 在取消分支直接 `return self.process.returncode or -1, "", ""` ——
**主动丢弃了子进程在被杀之前已经产出的 stdout/stderr**。这与该模块 docstring 的精神矛盾
（它强调「重入 communicate 不丢缓冲输出」），对排查问题很不利：用户看到的是「取消，无输出」，
而实际进程已经打印了半屏日志。

**修法**：取消路径先 `self.process.communicate()`（进程已被 kill，立即返回）把缓冲读完，
再返回 `(rc, stdout, stderr)`。这样 `exec.shell` 的取消结果里能带上部分输出。

> 关于 `communicate(timeout=)` 的重入：审查确认 `_communicate_cancellable()`
> （`executor.py:93-118`）docstring 的主张**是正确的**，CPython 文档保证超时重入不丢缓冲。
> 该处无需改动。

### B2 取消不再被归类为「失败」

**根因**（`engine.py:481-482`）

```python
if not attempt.retryable or attempts > max_retries:
    return attempt        # ← retry=0（默认）时在此直接 return，不再复查取消
```

审查做了完整控制流推演，四种输入组合的结论：

| 输入 | 走到哪 | 结果 |
|---|---|---|
| 工具抛 `WorkflowCancelled` | `:477` 命中 | `cancelled` ✅ |
| 工具返回失败 dict（被杀）。`retry=0` | `:481` | **`failed`** ❌ |
| 工具返回失败 dict。`retry>0` 且退避后仍失败 | `:481` | `failed`（但退避前的 `:485` 会命中取消）⚠️ |
| 工具抛普通异常 | `:694` → `:481` | `failed`（正确，除非是取消导致） |

> ⚠️ **审查补充的时序约束**：**当前（B1 之前）这条错误路径还不成立**——
> 因为工具根本没接 `cancel_check`，不会「因被杀而返回非零」。
> **B1 接通取消的那一刻，这条路径才被激活。** 所以 **B2 必须与 B1 同批或紧随其后落地**，
> 否则会开出一个「取消全部显示为失败」的回归窗口。

**方案（双层，都做）**

1. **工具层（主）**：被取消后 `raise WorkflowCancelled()`（已在 B1.2 / B1.3 列出）。
2. **引擎层（兜底）**：`_run_node` 返回失败前补判定：

```python
if not attempt.retryable or attempts > max_retries:
    if context.cancelled():
        return _NodeRun(attempts=attempts, cancelled=True)
    return attempt
```

并在 `_execute_tool` 拿到结果、归类失败**之前**补一次 `context.cancelled()`，
覆盖「工具不响应取消但恰好报错」的情况。

### B4 长节点的存活可证（⚠️ 审查后重设）

**根因（修正后的表述）**：桥接层用一个**每帧重置的 inactivity timeout**（默认 300s）
来判断后端是否卡死。这是把 **transport watchdog 当成了 execution liveness**——
而一个正在跑 10 分钟反编译的后端**是健康的**，只是没有事件可发。
「300s 内无事件」被误判为「卡死」并触发自动取消，是**模型层面的错误**，不是阈值太小。

**修法（两层，都要）**

1. **桥接层按 method 解耦超时**（治本）：`workflow.execute` 不应沿用逐帧 inactivity 语义。
   改为给 workflow 执行一个独立的、长得多的存活预算，与「后端进程无响应」这个
   transport 层判断解耦。`commandHandlers.ts:47-75` 的 `armTimeout` 需按 method 分支。
   > 注意：**不要直接豁免/关闭该超时** —— 它是后端真卡死时的唯一回收手段。
   > 是「换个判活模型」，不是「取消保护」。
2. **引擎发执行层心跳**（补充探针，这也是 Temporal 的标准做法）：
   节点执行期间每 30s 发 `node_heartbeat`（`{node_id, elapsed_ms}`），节点结束即停。
   `try/finally` + `daemon=True` 严格配对，分片 sleep 保证可中断。
   心跳**不作为公开契约要求消费方实现**（见 §3）。

> 审查曾提出「心跳只是治标」，两方结论的调和是：**心跳是正确的机制**（Temporal 正是
> 由被监控方主动 heartbeat），但**原方案把它当成「喂饱那个错误的超时」是错的层次**。
> 正确做法是先修判活模型，心跳用于让「执行层存活」变成可观测事实。
> 来源：[Temporal 心跳](https://docs.temporal.io/develop/python/activities)、
> [K8s 探针](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

### B7 CLI 取消闭环

**现状**：无注册、无信号处理、退出码 2 不可达（§0.2）。

1. `run` 分支启动前注册：`TaskManager().register(run_id, task_id, stop_event)`。
   `run_id` 用真实唯一值 —— `f"cli-{uuid4().hex[:12]}"`。**不要再用固定 `"cli"`**，
   否则多次运行互相覆盖注册。
2. 安装 `SIGINT` / `SIGTERM`：**第一次** → `TaskManager().cancel(run_id)`，
   让引擎走 B2 的正确归类；**第二次** → 立即退出（沿用 `main.py:125-135` 的二次信号语义）。
   `signal.signal` 用 try/except 包裹（照抄 `main.py:140-142`）。
3. **必须做孤儿清理**：`finally` 中 `cancel` 后 `unregister`（对齐 `api_handler.py:216-218`），
   **不要直接 `sys.exit`**。
   > 🔴 与 B1.4 强耦合：加了 `CREATE_NEW_PROCESS_GROUP` 后，控制台 Ctrl+C
   > **不再**自动带走子进程树，这一步从「保险」变成「唯一手段」。
4. **`KeyboardInterrupt` 也要兜住**：Windows 下 `signal.signal(SIGTERM)` 支持有限，
   控制台 Ctrl+C 通常以 `KeyboardInterrupt` 形式出现，需与信号处理同等对待。
5. **取消退出码用 130**（⚠️ 审查修正）。
   > 原方案用 2：与 `argparse`「参数错误 = 2」冲突，且不合 Unix 惯例
   > （`128 + SIGINT(2) = 130`）。同步修正 `cli.py:629` 的 docstring 与 §6.4 验收。
   > 若你的既有脚本已依赖「2 = 取消」，需显式确认可破坏；否则用 130。
   来源：[Exit codes 惯例](https://tldp.org/LDP/abs/html/exitcodes.html)

## 3. 事件契约 v2（⚠️ 审查后重设，这是前端重构的输入）

### 3.1 核心决策：收敛为单一权威终态

原方案让 `workflow_result` 与 `workflow_completed` / `workflow_failed` / `workflow_cancelled`
**并存**，同时又声明 `workflow_result` 是「唯一的完整结果出口」——**自相矛盾**，
且违反本文档自己定的原则「不要让消费方从多个事件推断终态」。
后果是可预期的：新前端会写出「既看 `workflow_failed` 又看 `workflow_result.status`」的双套逻辑。

**决策：`workflow_result` 是唯一权威终态；删除另外三个终态事件。**

| type | 何时发 | 载荷 |
|---|---|---|
| `node_started` | 节点即将执行 | `node_id`, `tool`, `total?`（foreach/branch 提供） |
| `node_completed` | 节点到达终态，**恰好一次** | `node_id`, `status`, `duration_ms`, `attempts`, `error?` |
| `node_retrying` | 即将退避重试 | `node_id`, `attempt`, `next_delay_ms` |
| **`workflow_result`** | 运行结束，**三种结局都发、且仅此一条终态** | `success`, `status`, `cancelled`, `outputs`, `node_results`, `error`, `run_dir` |
| `node_heartbeat` | 节点执行中每 30s（**内部机制，非契约**） | `node_id`, `elapsed_ms` |

公共字段：`run_id`（顶层 run 身份）、`workflow_id`（定义名，嵌套为子模板名）。

**为什么现在是最佳时机删除那三个事件**：前端本来就要重建，此刻收敛契约的成本最低；
拖到前端重写完成后再改，就是二次破坏。需要同批更新的地方（容易漏）：
`streaming.py` 的三个 `emit_*`、`render_event_line`、`cli.py:_EVENT_COLORS`、
`engine.py` 三处 `emit_workflow_*` 调用点、以及 `test_streaming.py` / `test_engine_node_events.py`。

### 3.2 补齐缺失状态（审查发现）

| 缺失 | 主流做法 | 本项目建议 |
|---|---|---|
| **重试中** | Airflow `up_for_retry`；Prefect `Retrying` | 新增 `node_retrying`。**必要性最高**：当前退避期间节点对外**完全无信号**（只有先前的 `node_started`，无心跳直到 B4），消费方无法区分「运行中」与「退避中」。引擎已知道 `attempt` 与 `_retry_delay()` |
| **取消中** | Prefect 区分 `Cancelling` → `Cancelled`；Temporal 区分 `CANCELED` 与 `TERMINATED`，且取消需清理确认后才算终态 | **建议不做新事件类型**。取消请求的受理状态已由 `request.cancel` 的返回值（`{cancelled: bool}`）表达；若需在 UI 体现「取消中」，让 `node_heartbeat` 带 `cancelling: true` 即可。理由：本项目取消延迟上限是轮询分片（0.5s）+ 树杀（≤5s），够短，不值得为此引入一个状态机 |
| **排队中** | Airflow `queued`/`scheduled`；Prefect `Pending` | **不加**。单 run 线性引擎没有队列语义，加了也填不上值——**不要定义填不上的状态**，这是比缺状态更糟的反模式 |
| **上游失败** | Airflow `upstream_failed` | **不加**。线性链无上游概念，`skipped` 已覆盖 `on_failure: skip` 语义。属合理偏离 |

### 3.3 新前端必须遵守的两条

1. **关联 run 用 `task_id`（web 路径）或 `run_id`，绝不要用 `workflow_id`。**
   本轮 renderer 就因为拿 `workflow_id`（= 定义名）去比自造 run id，导致事件被 100% 丢弃。
2. **`node_completed` 必须读 `status` 字段分支，不要假定成功。**
   参考实现就在仓库里：`cli.py:511-515` 的 `_STATUS_COLORS` + `:565-568`。

### 6.4 CLI 手工验收（Windows 必做）

```powershell
cd D:\cyanrain\ai\vibecoding\wt-workflow\cli
& C:\Users\admin\.workbuddy\binaries\python\envs\default\Scripts\python.exe cli.py run <workflow.json> --json
```

1. **取消中断**：工作流放一个 `exec.shell`，命令 `ping -t 127.0.0.1`，运行后 Ctrl+C
   → 1s 内退出，**退出码 130**，任务管理器**无残留 `ping.exe`**。
2. **复合命令树杀**：命令改 `cmd /c "ping -t 127.0.0.1"`，重复上一步。
   这是 `shell=True` 的真实场景，`terminate()` 在此必然失效。
3. **父亡孙存活**：命令改 `cmd /c "start /b ping -t 127.0.0.1"`（父立即退出、孙被 reparent）
   → 验证 Job Object 是否仍能清干净。**这是 B1.1 换成 Job Object 的核心验收点**，
   也是 `taskkill /T` 单独使用时唯一会漏的场景。
4. **descriptor 路径**：用一个 adb / apktool 的 descriptor 工具跑长任务，同样 Ctrl+C。
5. **失败 vs 取消区分**：故意让节点失败（`flow.assert`）→ 退出码 1、终态 `workflow_result.status == "failed"`；
   Ctrl+C → 退出码 130、`status == "cancelled"`。
6. **skipped 语义**：`on_failure: skip` 节点失败 → 该节点 `status == "skipped"`，整体仍 `success`。
7. **输出保留边界**（**已定档：仅 timeout 路径**，见 §6.5 决策 A）：节点**超时**时，结果里应带上
   被杀前的部分 stdout（B1.6）——由
   `test_exec_shell_timeout_keeps_the_output_produced_before_the_kill` 把守。
   **取消**（Ctrl+C）时**不**保留：工具被杀后 `raise WorkflowCancelled`，返回值按契约丢弃，
   取消节点在 `node_results` 里没有 outputs。这是**有意的范围决定**，不再是缺口。
8. **`--json` 完整性**：`node_results` 含每节点 `duration_ms` / `attempts` / `status`。

**B1.6 结论（已定档：方案 A —— 仅 timeout 路径保留输出）**

| 选项 | 做法 | 结论 |
|---|---|---|
| **A. 认定不需要** | §6.4 步骤 7 改成「仅 **timeout** 路径保留输出」 | ✅ **采纳**：执行层本来就对（见下），0 成本；放弃「取消时前端能显示已滚出的日志」 |
| B. 引擎携带 | `WorkflowCancelled` 增加 `stdout/stderr` 负载；`engine._run_node` 捕获后把 `_NodeRun(cancelled=True)` 带上 outputs；`node_results` 落盘时保留 | ❌ 否决：代价中等，且要动引擎 + 事件契约 |
| C. 工具不抛、只返回 | 让工具返回 `success=False` 的 dict，靠引擎既有的 B2 复查取消来归类 | ❌ 否决：`WorkflowCancelled` 承担 **嵌套传播**（foreach/branch/workflow.run 靠它向上冒泡，`test_cancel_semantics.py` 有 3 个用例锁着），改成返回值会同时破坏那层 |

采纳 A 的依据：**执行层本来就正确**。`ProcessExecutor.drain_output()` 把被杀前已产出的

`raise WorkflowCancelled`，引擎侧 `_NodeRun(cancelled=True)` 也不携带 outputs。
所以 §6.4 步骤 7 已改写为「仅 timeout 路径保留输出」，不再是缺口。

**⚠️ 一次假回归：真凶是测试自身的启动竞态，不是代码**

落地这条验收时先写了一个「python 子进程先 `print` 再 `sleep 3`、`timeout=1`」的用例，它**失败**了
（`stdout == ''`），一度被判成 `ProcessExecutor` 的 B1.6 回归。实测后该结论被**推翻**：

| 观测 | 结果 |
|---|---|
| 真 `ProcessExecutor` 三条路径（`_communicate_once` / `_communicate_cancellable` / 带 holder）跑 timeout | `drain_output()` **都返回** `'before-timeout\n'` |
| 子解释器「首字节延迟」（经 cmd.exe + 管道实测） | pytest 的 venv python **1.59–1.99s**；managed 3.13.12 **0.95–1.06s** |
| CPython 源码 `subprocess.py:1659-1669` | 超时时读取线程**仍存活**，抛 `TimeoutExpired(args, timeout)`，**不带任何输出**；注释明说 fds 保持打开，以便用户**再调一次 `communicate()`** |

即：`timeout=1` **短于** venv 解释器从启动到第一行 `print` 的时间，子进程还没写就被杀，
`stdout == ''` 是**正确行为**。该用例已改为由 **shell 本身**写标记再阻塞
（Windows：`echo before-timeout & ping -n 30 127.0.0.1 >nul`；POSIX：`sh -c 'echo before-timeout; sleep 30'`），
1s 内必然已产出，把断言从「解释器启动有多快」里解耦（实测 1.15–1.16s，连跑 3 次一致）。

同时按源码结论**删掉了**中途加的 `_rescue_partial` / `_partial` 兜底：
`TimeoutExpired.stdout` 只是 `.output` 的 property 别名（`subprocess.py:186-194`），
Windows / 线程路径根本拿不到输出；而 `_communicate_cancellable` 的超时分支本来就是
「kill 完直接抛、由 `drain_output` 收尾」——两条路径现在在这一点上**对称**，
`drain_output` 的 docstring 已写明「再调一次 `communicate()` 就是恢复机制，别用 `TimeoutExpired` 简化掉」。

## 7. 边界：本轮不做的事

- **不改 renderer 任何代码**（§5 只留备忘）。
- **不动桥接层「首帧即 resolve」**（`commandHandlers.ts:118-121`）——全局时序，风险大于收益。
- **不重载 `workflow_id`** 去承载 run 身份。
- **不改 `TaskManager` 的取消语义**（墓碑 TTL、`_seen` 防串号、task_id 别名）——现状正确，
  只替换杀进程的实现。**不删 `stop_event`**（`cancel` 内部依赖它）；`api_handler.py:198` 的
  检查按 B6 的终审定性处理（是竞态守卫而非死代码，删它是为了用引擎归类替代）。
- **不引入 `psutil` 等第三方依赖**（后端是纯标准库，见 §1.5）。
- **不定义填不上的状态**（`queued` / `upstream_failed`），不做取消两阶段状态机（§3.2 已论证）。

- **流式 handler 线程无上限（`api_handler.py:233-239`）暂不处理** —— 单用户桌面场景风险低
  （终审裁定移入本节，见 §0.6 #7）；若将来并发流式请求明显增长，加 Semaphore 上限（如 8）即可。
