# 取消链路：本地 17 提交 vs 远端 94e09f2 —— 冲突逐文件取舍

> 用途：push 被 `non-fast-forward` 拒绝后，用于决定怎么合。
> 结论基于 `git diff 0a90694..02de6e9`（我们）与 `git diff 0a90694..94e09f2`（远端）逐块对读，
> 以及 `git merge-tree --write-tree` 的冲突试算。**未改动任何代码。**

| 侧 | 提交 | 规模 |
|---|---|---|
| 本地 | `121ee48 feat(cli): cancel the whole process tree…` | 14 files +2553 −75 |
| 本地 | `02de6e9 docs: record the landed cancellation commit…` | 1 file +4 |
| 远端 | `94e09f2 fix(cli): make cancellation, timeouts and interrupts actually take effect` | 18 files +1996 −216 |

> ⚠️ 早前一度把分叉说成「本地领先 17」。**那是错的**，基准取到了**冻住的 `origin/workflow`（`e4cc11f`）**。

## 2. ⚠️ 先看这条：两边的 holder 协议不一样

这是**决定"能不能单边替换"的关键**，也是 4 个冲突的根：

| | holder 键 | 谁去杀 |
|---|---|---|
| 我们 | `holder["job"]` = **Job Object 句柄** | `TaskManager._terminate` → `proc_tree.terminate_job_in(holder)` |
| 远端 | `holder["kill"]` = **可调用对象**（`ProcessExecutor._kill_tree`） | `TaskManager._terminate` → `holder["kill"]()` |

→ **`executor.py` 与 `task_manager.py` 必须成对取舍**，不能只拿一边。
（好消息：两者可以合成一条更干净的路径 —— 把 job 终止塞进远端的 `_kill_tree()`，
`task_manager` 就整取远端、连 `proc_tree` 都不用 import。）

## 3. `cli/app/common/executor.py`

规模：我们 +138 −21；远端 +200 −39。

| 维度 | 我们（`121ee48`） | 远端（`94e09f2`） |
|---|---|---|
| **树杀机制** | Windows **Job Object**：spawn 时 `attach_job` 入册（成员靠父子继承，事后追认抓不到孙进程），取消时 `TerminateJobObject`；POSIX `killpg`；Win 回退 `taskkill /F /T` | **没有 Job Object**。Windows 先 `taskkill /T /F`（**趁树还活着**），再 `terminate()`；POSIX `start_new_session` + `killpg` |
| **holder 契约** | `holder["job"]` = 句柄 | `holder["kill"]` = `_kill_tree` 可调用对象 |
| **取消归类** | 无（靠工具层 `context.cancelled()`） | **`self.cancelled` 公开标志**，`run()` 里置位，工具/`base_executor` 读它 |
| **超时/取消后的输出** | **`drain_output()` 保留已产出的 stdout/stderr** | 丢弃（`return rc or -1, "", ""`） |
| **取消检查时机** | 轮询循环内 | 轮询循环内 **+ `communicate()` 正常返回后再查一次**（外部杀掉会让 `communicate()` 正常返回而不是抛异常 → 否则看着像普通失败，白烧一次重试） |
| **异常兜底** | 无 | `except BaseException: self._kill_tree(); raise`（Ctrl+C / 任意解释器级展开都不漏子进程） |
| **管道收尾** | 无 | `_kill_tree()` 末尾**关闭 stdout/stderr/stdin**（防幸存的孙进程持有继承句柄、卡住后续 wait/communicate） |
| **Windows 子进程窗口** | 无 | `CREATE_NO_WINDOW` |
| **测试替身** | `attach_job` 严格 handle-only | `_kill_descendants` 用 `type(process) is not subprocess.Popen` 跳过伪对象，故 `_kill_tree` 对 mock 安全 |
| **cmd 渲染** | 内联 `isinstance(cmd, list)` 三元 | `Command = Union[str, list, tuple]` + `_describe(cmd)` |
| **`run()` 签名** | 保留 `on_output` | **删掉 `on_output`**（已核实：全仓库**无任何调用方**，只有定义处，删了安全） |

### ⚠️ 两处设计互斥，不能原样叠加

1. **`drain_output()` × 「关管道」**
   我们的 `drain_output()` 依赖管道**仍打开**且可重入 `communicate()`；远端的 `_kill_tree()` 在收尾时
   会把三条流关掉。若照搬远端的 `_kill_tree` 再调 `drain_output()`，`communicate()` 会抛异常，
   被我们那里的 `except Exception: pass` 吃掉 → **不崩，但输出永远拿不回来**（静默退化，最坏的那种）。
   *（注：Job Object 在场时孙进程已被一起杀掉，管道本就该自然关闭，所以"关管道"的动机在 job 方案下大幅减弱。）*

2. **`_kill_tree()` 的 Windows 段**
   远端注释明说 `taskkill /T` **只在树还活着时**才够用，所以才"先 taskkill 再 terminate"。
   但「父先亡、孙被 reparent」这种树已经不完整的情况，`/T` 走不到 —— 那正是 Job Object 覆盖的场景。

## 4. `cli/app/common/task_manager.py`

规模：我们 +22 −3；远端 +87 −15。

| 维度 | 我们 | 远端 |
|---|---|---|
| `_terminate` | `proc_tree.terminate_job_in(holder)` → 回退 `proc_tree.terminate_tree(pid)` → `process.terminate()` | 优先 `holder["kill"]()` → 回退 `process.terminate()` |
| `register()` | 未改 | 新增 `*, honor_stop_event: bool = False`（供 **信号处理器**这类"不能取本类锁"的场景） |
| `is_cancelled()` | 未改 | 新增 `_entry_cancelled()`：`honor_stop_event` 的 run 一旦其 `stop_event` 被外部 set 也算取消 |
| **重复 cancel** | 未改 —— `if entry.get("cancelled"): continue` 会**提前跳过**，于是"第一次 cancel 到达时进程还没起来"这种情形，第二次 cancel **不会**再去终止新挂载的进程 | **修好了**：重复 cancel 重新 set event + 重新 terminate |
| **`unregister()`** | 未改（只 `cleanup_task_log(run_id)`） | **修好了**：`run_id` 与 `task_id` **两个**缓冲都 flush；`task_id` 缓冲仅在不被其他 in-flight run 共享时才 drop（原实现漏 flush `task_id`，per-task 日志静默丢失） |
| `list_runs()` | 未改 | 用 `_entry_cancelled()`，不再直读 `info["cancelled"]` |

→ **远端在 `task_manager` 上是严格超集（job 那一处除外）**。我们这边只多了 job 分支。

## 9. 推荐合并方案（函数级）

以 **`94e09f2` 为基底**，把我们那 6 项净增叠上去；我们与远端重复的部分直接让位。

> 代价可控：本地**只有 2 个提交**（`121ee48` + `02de6e9`）需要重接，其余 15 个早已在远端。
> 也就是说「以远端为准」最坏情况只丢今天这一轮，**不会**波及之前那批 refactor。

1. **`proc_tree.py`** —— 整取我们的（远端没有对应物）。
2. **`executor.py`** —— 取远端的整体结构（`_kill_tree` / `_kill_descendants` / `_taskkill` /
   `cancelled` / `except BaseException` / `CREATE_NO_WINDOW` / `start_new_session` / `_describe` / 删 `on_output`），然后：
   - 保留我们的 job 入册与释放（`attach_job` / `_release_job` + holder 归属规则）；
   - 在 `_kill_tree()` **最前面**插入 job 分支：`if self._job_managed: TerminateJobObject → 返回`，
     否则走远端原序列；
   - **保留 `drain_output()`，并把它排在远端"关管道"之前**（或直接去掉关管道那一段 —— job 在场时
     孙进程已被一并杀死，管道本就会自然关闭）。**这条是合并里最容易踩的坑。**
   - `cancelled` 只在取消时置位（**timeout 不置位**），照远端语义。
3. **`task_manager.py`** —— **整取远端的**（含 `honor_stop_event`、重复 cancel、双缓冲 flush）；
   我们那段 job 分支**删掉**，因为 `holder["kill"]` 现在就是带 job 的 `_kill_tree`，单一代码路径更干净，
   而且 `task_manager` 再也不需要 import `proc_tree`。
4. **`exec_tools.py`** —— 取远端为基底，取回我们的 `_child_text_encoding()`，timeout 分支改回
   `executor.drain_output()[1]`；保留远端的 `_timeout_from()` 与 `executor.cancelled or …` 判断。
5. **`descriptor_tool.py`** —— 取远端的 **`getattr`** 版（更健壮）；`execute()` 里我们那处
   `raise WorkflowCancelled()` 可留可去（远端已在 `base_executor` 更底层做了）。
   我们改过的那 2 个测试文件（改用真 `ToolContext`）**可以留着**，属改进。
6. **`base_executor.py`** —— 自动合并；保住我们流式 `spawn_options()` 那 3 行。
7. **`engine.py`** —— **保住我们的 B2**（远端没动）。
8. **`docs/` + tests** —— 我们的方案文档与三类真进程测试保留，按新实现调接线；
   远的 `test_cli_run_scope.py`、`test_cancel_semantics.py` 增量自动进来。

## 12. 合并落地结果（2026-09-20 实施）

**基底 = 远端 `94e09f2`**，把本地 `121ee48` + `02de6e9` 接上去（`git merge 94e09f2`）。
4 个冲突的最终形态：

1. **`task_manager.py` —— 整取远端**。`_terminate` 走 `holder.get("kill")()`；`import proc_tree`
   与 `_TERMINATE_GRACE_SECONDS` 一并去掉（§9.3 的预期落地）。
2. **`descriptor_tool.py` —— 取远端的 `getattr` 版**（两处冲突块）。我们 `execute()` 里那处
   `raise WorkflowCancelled()` 与 `import` 是自动合并进来的，保留（§6 判定"可留"）。
3. **`executor.py` —— 远端为基底 + 4 项净增**：
   - `run()`：spawn 后 `proc_tree.attach_job(...)` 入册，整体包进 `try/finally`，
     `finally` 只 `_release_job()`（关句柄、不杀任何东西，`adb start-server` 这类后代照活）；
   - `_kill_tree()` **最前面**插 job 分支：`if self._job_managed: self._terminate_job(); self._reap(); return`，
     非 job 路径原样保留远端序列；
   - 新增 `drain_output()` / `_reap()` / `_terminate_job()` / `_release_job()`；
   - ⚠️ **删掉远端 `_kill_tree()` 末尾的"关管道"收尾**（§9.2 的坑）：管道必须保持打开，
     `drain_output()` 才拿得回被杀前的输出。job / `killpg` 已覆盖幸存的孙进程，管道自会关闭。
4. **`exec_tools.py` —— 远端为基底 + `_child_text_encoding()` + timeout 分支 `executor.drain_output()[1]`**。
   `executor.run(...)` 的调用**改回 `cmd=` 关键字**（与 `base_executor.py` 的调用风格一致，
   也让既有 `lambda self, **kwargs` 测试替身继续成立）。

**取消路径也 drain**：`_communicate_cancellable` 的取消分支 `return self.drain_output()`
（与 timeout 分支对称，`drain_output` 成为唯一恢复机制）。工具边界仍按 §6.5 **方案 A** 丢弃
（被杀即 `raise WorkflowCancelled`），所以对 `node_results` 无影响 —— 与方案 A 不冲突。

**我们的测试按新接线调整（§9.8）**：

- `test_cancel_process_tree.py`：三例 `executor._kill()` → `executor._kill_tree()`；
  守卫对象由 `proc_tree.terminate_tree` 换成 `ProcessExecutor._kill_descendants`
  （合并后非 job 路径不再经过 `terminate_tree`），并补一条"已退出进程不得再 kill"的实断言。
- 同一文件里 drain 那例：把 `terminate_tree` 空桩换成 `_kill_descendants` 空桩，
  避免假 `Popen` 真的走到 `taskkill`。
