## 1. 范围与用法

- **本文档做什么**：定义重构后需要哪些屏幕、每屏包含哪些功能元素、每个元素绑定哪个后端方法、有哪些状态与边界，以及**哪些东西现在做不了**（第 7 节）。
- **本文档不做什么**：不定视觉（07 定）、不排期（[05-分期开发计划](./05-分期开发计划.md) 定）、不含实现代码。
- **怎么用**：
  1. 做 UI 设计/AI 生成时，读第 2 节（外壳）+ 第 3 节（目标屏）+ [`ui-prompts/`](./ui-prompts/README.md)（逐屏提示词）；
  2. 做前端实现时，读第 3 节（功能 + API 绑定）+ 第 5 节（跨屏约定）+ 第 7 节（缺口，先改后端/preload 再实现 UI）；
  3. 验收时用第 9 节清单逐项勾。

## 2. 信息架构与外壳

### 2.1 一级模块（冻结）

| 模块 | 路由 | 页面 |
|---|---|---|
| 工作流 | `/workflows` | 工作流列表 |
| 工作流 | `/workflows/editor/:name?` | 工作流编辑器（二级页，从列表进入） |
| 任务 | `/tasks` | 任务中心（默认 tab 为「任务」，`?tab=runs` 为「运行记录」） |
| 任务 | `/tasks/editor/:name?` | 任务编辑（二级页：新建/改参；即「任务的编辑」唯一入口） |
| 工具 | `/tools` | 工具（三页之一：工具 / 环境 / 插件） |
| 工具 | `/tools/env` | 环境（同属「工具」一级模块，页面头区段切换跳转） |
| 工具 | `/tools/plugins` | 插件（同上） |
| 设置 | `/settings` | 设置（含「关于」块与诊断/关于入口） |

- `/` 重定向到 `/workflows`。
- **工具模块的三页（2026-09-28 决策）**：`/tools`、`/tools/env`、`/tools/plugins` 是**三个独立页面**——各有自己的页面标题、描述、工具栏与空态，靠页面头右侧的**区段切换**互相跳转；它们**共用侧边栏的「工具」这一个导航项**（一级导航仍是 4 项，不拆出「环境」「插件」）。此前"同一页三个 tab 面板"的写法（原 `docs/ui-prompts/07-tools-env-plugins.md`）已废弃。与 `/tasks?tab=runs` 的 `?tab=` 写法**有意不同**：那两个 tab 是同一任务对象的两种视图，这里是三类不同对象（工具描述符 / 运行环境 / 插件清单），各自有独立的列表、工具栏与空态。
- 二级路由（**不进侧边栏**，从一级页进入）：`/about`（关于，内容等同 S7 的「关于」块，二者只保留一个入口）、`/diagnostics`（诊断，即 S8）、`/tasks/editor/:name?`（任务编辑，见 S3）。
- 退役边界：界面中**不得出现任何 Android 专属入口或措辞**（设备管理、APK 一键操作、签名配置等，也**不在界面文案里点名 `examples/**/android` 子目录**）。Android 能力只存在于用户自行导入的 `examples/` 内容里，执行路径与其他工作流完全一致。

## 3. 屏幕清单

每屏给出：**目的 / 布局分区 / 功能元素 / 数据来源 / 状态 / 边界与现状差距**。

### S0 启动加载屏

- **元素**：应用名、进度条、当前步骤文案、已耗时秒数、失败态文案 + 「重试」/「重新加载」。
- **数据**：`registerServices` → `appConfig` / `system.info` / `build.info` → 工具探测（`tool.get_tools`）→ 主题/语言/更新/任务流订阅。
- **状态**：加载中 / 失败（可重试，超 3 次禁用重试）/ 完成。
- **现状**：已实现，微调文案与视觉即可。

### S1 工作流列表 `/workflows`

- **目的**：管理工作流模板（下称"工作流"）——**回答"我有哪些工作流"并做增删改与导入导出**：新建、导入、导出、试运行、改名、复制、删除、搜索。
- **本页不展示运行结果**：卡片上**没有**"上次运行成功/失败"徽章（**设计决策，2026-09-28**）。运行状态属于「运行记录」（S4），工作流列表只表达"有哪些工作流、各自的元信息"。因此本页**不与 `history.list` join**。
- **布局**：页面头（标题 + 描述）→ 工具栏 → 卡片网格 / 空态。
- **工具栏元素**：
  | 元素 | 行为 | 数据 |
  |---|---|---|
  | 「新建工作流」主按钮 | 跳 `/workflows/editor`（空定义） | — |
  | 「导入」 | 文件多选或目录选择 → 导入并出结果报告（M2） | `selectFile` / `selectDirectory` + `template.import_path {path}` |
  | 「导出」 | 需先选中卡片：加载定义 → 写 JSON 到用户选定路径 | `template.load` + `showSave` + `writeTextFile`（WP1 已补通道，缺口 #1 已修） |
  | 搜索框 | 按 `name` / `description` / `tags` 前端过滤 | — |
  | 刷新 | 重新拉列表 | `template.list` |
- **卡片元素**（**唯一数据源 `template.list`**：`name` / `description` / `created_at` / `updated_at` / `tags` / `node_count`）：
  - 名称、一句话描述（可为空则显示占位）
  - meta：`节点数 {node_count}`、`最近更新 {updated_at}`
  - 标签 chips（`tags`，为空则不显示）
  - `⋯` 菜单：编辑 / 复制 / 试运行 / 导出 / 重命名 / 删除
- **交互**：
  - 点击卡片 → 进入编辑器（`/workflows/editor/<name>`）
  - 复制 = `template.load` + `template.save`（新名称，重名先确认）
  - 试运行 = 打开 M1 输入表单 → `template.execute {name, inputs}`（**一次性试跑，不保存参数**；要保存参数就去任务模块建任务，见 S3）
  - 重命名 = `template.load` + `template.save`（新名）+ `template.delete`（旧名）
  - 删除 = 确认弹层（M4）→ `template.delete {name}`；⚠️ 有任务引用该工作流时会变成悬挂引用（S3 的 `workflow_exists = false`），**不级联删任务**
- **空态**：无工作流时居中引导，两个按钮：「导入示例工作流」（文件多选或目录选择，说明文案写"仓库 `examples/workflows/generic` 的示例零依赖、导入即跑；`examples/workflows/` 下另有需先导入工具描述符才能跑的示例"）/「新建工作流」。**界面文案不点名 `android` 目录**（退役边界，见 §2.1）；需要精确路径时放在文档/日志提示里。
- **状态**：加载中（骨架卡片）/ 空 / 有数据 / 加载失败（可重试）/ 后端不可用横幅。
- **边界与差距**：
  - `tags` 现在可读可写：`template.load` 已附带 `description` / `tags` / `created_at` / `updated_at`（WP5 已修缺口 #12），编辑器可直接做标签编辑并回写 `template.save`。

### S2 工作流编辑器 `/workflows/editor/:name?`

- **目的**：画布式编排线性工作流，配置节点与工作流级出入参，试运行并观察节点实时状态。
- **布局**：顶栏 → 左栏工具面板（240px）/ 中间画布 / **右栏常驻侧栏（320px，内部「工作流 ｜ 节点」双 tab）**。
  - **右栏常驻（2026-10 决策，取代早先"未选中节点时右栏整体不显示"）**：工作流信息与出入参需要一个稳定入口，否则只能靠顶栏按钮唤起模态框。切换规则：**跟随选中状态**（选中节点 → 切到「节点」；取消选中 → 切回「工作流」），用户手动点 tab 后不被覆盖。
  - **画布方向**：横向链（左→右）。自动布局为一整行（`x = 80 + index*320, y = 140`，见 `graphLayout.ts`），与节点左右端口一致——早先的纵向堆叠会让每条连线绕成 U 形。节点坐标为画布态、**不序列化**（后端 schema 无坐标字段），重新加载总是重排。
- **顶栏元素**：
  | 元素 | 行为 | 数据 |
  |---|---|---|
  | 返回 | 回 `/workflows`（有未保存改动先确认） | — **未做**：`/workflows` 列表页尚不存在（`/` 直接重定向到编辑器），没有可返回的目标 |
  | **工作流名** | 在右栏「工作流」tab 的**工作流信息**里编辑（名称 / 版本 / 描述）；顶栏标题只读显示，点击即切到该 tab | `meta.name` 现可编辑（**已落地**）；`tags` 只存在于模板包装元数据，由 `template.load` 一并返回（WP5 已修缺口 #12）；裸定义文件没有 tags（返回 `[]`），保存后即持久化。**编辑 tags 的 UI 仍未做**（需把模板包装元数据与 `WorkflowDefinition` 分开管理） |
  | 保存 | 顶栏「保存为模板」对话框，名称/描述预填当前工作流信息；**重名即覆盖** | `template.save {name, definition, description, tags}` |
  | 试运行（主按钮） | 打开输入表单 → 执行 | `workflow.execute {definition, inputs}` |
  | 运行中：取消 | 顶栏「运行」变「取消」，终止正在跑的节点与子进程 | `request.cancel {task_id}`（**已落地**：`task_id` 是后端注册的别名，见下文「执行反馈」） |
  | 问题面板开关 | 展示静态校验结果，warning 不阻断；点击条目定位节点 | `workflow.validate {definition}`（**已接入**） |
  | 状态徽标 | 已保存 / 未保存改动 / 运行中 | 画布序列化快照与最近一次加载/保存的比较 |
- **左栏 工具面板**（`workflow.list_tools`）：
  - 分组：内置（`kind = shipped-native`）/ 插件（`native`）/ 已导入描述符（`descriptor`）
  - 条目：名称、有效性点（`is_valid`）、一句话描述（`description`，缺失时回退为端口数量）、拖拽手柄
  - **搜索框与「点击追加到链尾」已落地**（追加位置 = 当前链尾节点右侧 320px）
  - `is_valid = false` 的条目：视觉变灰 + **禁用拖拽**（`draggable=false` + `dragstart` 兜底）+ tooltip 说明
- **画布**（@vue-flow）：
  - 点阵背景、缩放控件、小地图、`fitViewOnInit`；连线为 `smoothstep` + 箭头（`MarkerType.ArrowClosed`）
  - 节点卡片：图标、**节点名（= 工具名）+ 副标题（`工具 · 操作`）**、状态标记、输入端口（左侧 handle）/ 输出端口（右侧 handle）、必填标星
  - 节点状态：`idle` / `running`（脉冲环）/ `success`（✓）/ `error`（✗）/ `skipped` / `cancelled`
  - 连线：拖拽连接，类型不兼容时禁止并提示（按端口 `base` 比较，`subtype` 仅建议性）；**自连接被拒绝**
  - 节点操作：选中、`Delete` 删除、拖动（右键菜单与「复制节点 / 在其后插入」**仍未做**）
  - 空态提示已 i18n
- **右栏「节点」tab**（原「节点配置」，现分 5 区）：
  - **基本**：节点 ID（可编辑；校验非空、唯一、**不含 `.`**——引擎用 `.` 分隔引用路径；改名会同步重写全部 `$nodes.<旧 id>.` 引用与连线）
  - **功能**：工具名 + **操作下拉**（`operations[]`，来自 `workflow.list_tools`）+ 操作描述；切换操作时清空已填参数并提示
  - **参数**：按操作渲染类型化参数表单 —— `text` / `number` / `boolean` / 单选 / 多选 / `file` / `directory` / `json`；`file` / `directory` 带「浏览」按钮；`json` 用等宽 textarea + 解析校验；**控件实现收敛在 `PortInput.vue` 一处**（节点面板与试运行入参对话框共用）
  - **表达式绑定展示与插入（已落地）**：每个参数旁一个「插入引用」按钮与 `$` 触发候选（`ExpressionPicker.vue`），候选分组为 **工作流入参 / 上游节点输出 / 运行时上下文**；`$nodes.<id>.params.<key>` 也列在上游分组；管道变换 `basename` / `dirname` / `default:<值>`；已有绑定以 chips 展示、可单个删除。**插入规则**：空字段插整值引用 `$path`（引擎保留原类型），已有文本的字段插 `${path}`（文本插值）；在字段里手打 `$` / `${` 也会弹出候选并就地补全。
  - **内联校验**（`expressionBinding.ts`，镜像 `cli/app/workflow/expression.py`）：错误（未闭合插值、空表达式、未知根、`_` 开头私有段、未知管道、路径段数不符、引用未知/下游节点）**阻止保存**；警告（端口/参数键/入参不存在、base 类型不匹配、整值引用与插值混用会被当字面量）仅提示。**只能引用上游节点**：引擎按链序累积 `$nodes.<id>`，引用下游必然在运行时 "missing node"。
  - 校验提示：未选操作 / 缺失必填输入（列出端口名）/ 选择端口未定义 `options`
  - **行为**：节点级字段 `on_failure`（`fail` | `skip`）、`retry`（数字，旁边说明隐含退避 `min(2^(n-1), 30s)`）
  - **输出**：只读输出端口列表（类型 + 名称 + 说明），供下游 `$nodes.<id>.outputs.<port>` 引用
  - 底部：保存 / **删除节点**（删除确认对话框由页面提供）
- **右栏「工作流」tab**：
  - **工作流信息**（`WorkflowInfoPanel.vue`）：名称（必填，保存时作为模板名）/ 版本 / 描述；只读统计（节点数 / 连线数）
  - **工作流级出入参**（`IoAuthoringPanel`，**已从模态框改为内联**）：inputs / outputs 双 tab；行显示名称、类型、必填徽章、描述；编辑表单含名称（`snake_case` 校验）、8 种类型（文本 / 文件 / 目录 / 布尔 / 数字 / JSON / 单选 / 多选）、必填开关、描述、单选与多选的选项列表编辑器（增删 + 上下移）；同侧重名校验；跨侧允许同名。
- **执行反馈**：
  - 顶部 alert 横幅：成功 / 失败（显示 `error`）/ 已取消；发生新一次运行前保留
  - 节点状态实时更新：订阅 `stream-event` 的 5 类事件 —— `node_started{node_id, tool}`、`node_completed{node_id, status(ok|failed|skipped|cancelled), duration_ms, attempts, error?}`、`workflow_completed{success}`、`workflow_failed{error}`、`workflow_cancelled`。⚠️ **关联键是 `task_id`**：`api_handler` 会把调用方的 `task_id`（页面生成的 `wf-…` 运行身份）注入每条事件；事件的 `workflow_id` 是**定义名**、`run_id` 是 JSON-RPC 请求 id（页面事先不知道），用它们过滤会把事件全部丢掉——早先的实现正是因此完全收不到事件。取到首个匹配事件的 `run_id` 后再收紧过滤（**已修正**）。
  - ⚠️ 取消时引擎**不发 `node_completed`**（直接返回取消结果），实时流里只会有 `workflow_cancelled` → 界面把仍在 `running` 的节点统一改成 `cancelled`。
  - **运行日志抽屉**：`task.read_log {task_id}`（`content` / `truncated` / `size` / `log_path`）+ 打开日志文件（`openPath`）——**仍未做**。
- **线性模型守卫（画布多余出边）** —— 设计决策，2026-09-21；**已实现**（`graphLayout.ts` + 页面警告条 + `TemplateManager.blockedReason`）：
  - **问题**：`next` 是单指针，一个节点只有**第一条**出边能被保存。丢掉其余出边后，那些目标节点不再有任何入边，文档于是出现多个 entry node → 后端 `WorkflowDefinition.__post_init__` **抛错拒绝**（`linear workflow '<name>' must have exactly one entry node (no incoming next reference), got [...]`）。而 `template.save` 走的是 `WorkflowDefinition.from_dict`，所以**画布上画出的分支根本存不下去**，不是"多余出边被静默忽略"。任何真分支（分叉、菱形）都必然触发。
  - **画布实时警告**：检测到不可序列化的出边时，在画布上方（执行横幅同层）显示 warning 条 —— 一句结论 + 逐条列出 `<源节点 id> → <目标节点 id>` + 一句出路说明。警告随画布实时变化，不等保存才出现。
  - **保存前阻断**：打开保存对话框与提交保存**两处**都先检查；命中则拒绝保存并给出可读原因（含具体连线），**不要**把文档交给后端去抛结构错误。阻断后关闭对话框，让用户回到画布修改（对话框的遮罩挡住了画布）。
  - **出路**：分支与遍历用 `flow.foreach` 等组合工具表达（见 [06-后续路线图](./06-后续路线图.md)：「DAG 条件分支已由组合原语满足」），画布连线只表达线性链。
  - **单一真源**：检测与序列化必须共用同一份「第一条出边胜出」的规则（同一个 helper），否则界面提示会与实际落盘漂移 —— 现为 `graphLayout.resolveNextMap`，`serializeWorkflow` 与 `extraOutgoingEdges` 共用它。
  - **不算命中的情况**：源节点已不在画布上的边；「同源同目标」的重复边（`next` 相同，无损失）。
  - 另：画布**拒绝自连接**（自环会被后端判为 cycle 并拒绝整个文档），在 `onConnect` 处提示。
- **状态**：未保存改动标记、运行中（禁用重复运行、显示取消）、校验有 error、后端不可用、出边冲突（画布警告 + 保存被阻断，见上文「线性模型守卫」）。
- **边界与差距**：
  - **节点级超时不存在**（`WorkflowNode` 没有 timeout 字段，只有描述符操作级 `timeout`）→ 配置面板不提供该字段。
  - 无撤销/重做、无快捷键体系。
  - 节点坐标不持久化：重新加载总是**重排成横向一行**（`graphLayout.horizontalLayout`）→ 不要承诺"布局保持"。
  - 序列化只取每个节点的第一条出边为 `next`；多余出边**不可保存**（原因、实时警告与保存前阻断见上文「线性模型守卫」）。`type` 字段仅标签用途，界面不必暴露。
  - **节点显示名不持久化**：后端 `WorkflowNode` 没有 label/name 字段，节点卡片标题只能是工具名（+ 操作名）。要支持"给节点起名"需先给后端 schema 加 `label` 字段（本轮回合未做）。
  - ~~**前端线格式已漂移（T24 清理项）**~~ —— **已清理**：`serializer.ts` 的 `WorkflowNodeJSON` / `WorkflowDefinitionJSON` 不再声明也不再输出 `edges` / `condition` / `on_success`（`WorkflowNodeData` 同步去掉 `type` / `on_success` / `condition`）。载入一份仍带这些字段的老文档时只 `console.warn` 一次（说明它们会在下次保存时消失），不报错、不阻断——与后端 `from_dict` 忽略未知键的行为一致。

### S3 任务 · 任务列表（`/tasks` 默认 tab）+ 任务编辑（`/tasks/editor/:name?`）

> **模型（2026-09-28 定稿）**：**任务 = 可持久化的执行配置** = 一个已保存工作流 + 一套保存的入参（+ 可选工作目录）。它与"工作流"（只存图，不存参数）和"运行"（一次执行，进运行记录且会被保留策略裁剪）是三件不同的事。因此：
>
> - **任务列表展示任务定义**，不是运行日志；任务在**第一次运行之前就存在**，也不会被 `history` 的裁剪策略删掉。
> - **"任务的编辑"= 选工作流 + 填初始参数并保存**（`task.save`），再按需要执行（`task.execute`）。这是唯一的任务编辑入口，没有第二处。
> - 同一工作流**可以挂多个任务**（不同参数各存一份）；执行产生的是"运行记录"，属于 S4。
>
> 数据源：`task.list` / `task.get` / `task.save` / `task.delete` / `task.execute` + `template.list` / `template.load`（选工作流、渲染表单）+ `run.list`（在跑）。

#### S3.1 任务列表（`/tasks` 默认 tab）

- **目的**：管理"要做的事"——新建、编辑改参、复制、删除、运行、看某个任务的运行记录。
- **布局**：页面头 → 工具栏 → 任务行列表 / 空态。
- **工具栏**：「新建任务」主按钮（跳 `/tasks/editor`）、搜索框（按 `name` / `description` / 绑定的工作流名过滤）、刷新（`task.list`）。
- **列表行**（数据源 `task.list`：`name` / `workflow` / `workflow_exists` / `inputs` / `input_count` / `has_work_dir` / `description` / `created_at` / `updated_at`）：
  - 任务名 `name`、一句话描述 `description`（可空）
  - **绑定的工作流** `workflow` + `workflow_exists = false` 时的警示徽章（"工作流已不存在"，点进编辑页重选）
  - meta：`入参 {input_count} 项`、`最近更新 {updated_at}`、`has_work_dir` 时标出"已指定工作目录"
  - **不显示运行状态徽章**：状态属于 S4 运行记录（与 S1 同一口径，避免列表与 `history` 的隐式 join）
  - 行操作：**运行**（`task.execute {name}`，直接用保存的入参，执行后跳 S4 并展开本次运行）/ 编辑（→ `/tasks/editor/<name>`）/ 复制（`task.get` + `task.save` 新名）/ 删除（M4 确认；`task.delete` 只删任务定义，**不动运行记录与产物**）/ 查看运行记录（→ `/tasks?tab=runs&task=<name>`）
- **空态**：无任务 → 「新建任务」；若同时没有任何工作流 → 引导去 `/workflows` 创建或导入（空态文案需分这两种情况）。
- **状态**：加载中 / 空 / 有数据 / 加载失败（可重试）/ 后端不可用横幅。

#### S3.2 任务编辑 `/tasks/editor/:name?`（新建 = 无 `name`）

- **目的**：**任务的编辑**——把"这套入参"存下来并绑定到一个工作流（可反复运行，不必每次重填）。
- **层级（设计决策，2026-09-28）**：**主体是入参的持久化表单**；工作流只是"这套入参的 schema 来源 + 运行目标"，是低频的一次性元信息 → **它只占顶部一行紧凑选择器，不占侧栏**。给工作流选择常驻 320px 侧栏会把真正吃宽度的东西（目录路径、JSON 多行、多选组、帮助文本）挤窄，是反的。
- **布局**：顶部返回 + 标题（+「删除」）→ 基本信息一行（任务名 / 描述）→ 工作流一行 → **入参表单占满宽度（两列网格；路径与 JSON 等宽字段整行）** → 底部固定操作条。
- **元素**：
  - 顶部：任务名（可编辑，路径安全：无分隔符、无 `..`）、描述；编辑既有任务时右侧有「删除」
  - **工作流一行**（紧凑，单行高度）：小字标签「工作流」+ 可搜索的选择框（数据源 `template.list`，选项显示名称 + 节点数）+ 当前工作流的描述 + 「打开工作流」次要按钮（跳 `/workflows/editor/<name>`）
  - **入参表单**：按选中工作流的 `definition.inputs` 生成 —— 需先 `template.load {name}` 拿端口定义
    | 端口类型 | 控件 |
    |---|---|
    | `text` | 单行输入（`type=textarea` 的说明用多行） |
    | `file` | 路径输入 + 「浏览」按钮（`selectFile`） |
    | `directory` | 路径输入 + 「浏览」按钮（`selectDirectory`） |
    | `number` | 数字输入 |
    | `boolean` | 开关 |
    | `json` | 等宽多行输入 + 解析校验 |
    | 单选（`options` 非空、`multi=false`） | 单选组 / 下拉 |
    | 多选（`options` 非空、`multi=true`） | 复选框组 |
  - 每个字段：必填标星、端口 `description` 作帮助文本；可选字段留空则**不提交该键**（不要把空串当值）
  - **工作目录 `work_dir`**（可选输入，留空则用工作流自己的目录 = 模板库目录），放在底部操作条左侧
  - 底部：「保存」（`task.save {name, workflow, inputs, work_dir, description}`）与「保存并运行」（`task.save` + `task.execute {name}`）
  - 必填缺失时**阻止保存/运行并逐字段标红提示**；`task.save` 会校验绑定工作流存在（不存在则报 `workflow not found: X`）
- **改绑工作流时的入参处理**（本屏唯一的"破坏性"交互）：
  - 按**端口名**对齐：新旧工作流都存在同名的入参 → 值保留；只存在于旧工作流的键 → **丢弃前先二次确认**（文案写明"将移除 N 个不匹配的入参已填值"）；没有任何值会丢失时不打扰。
  - 工作流被改名/删除（`workflow_exists = false`）时：选择器为空态样式 + 一行橙色提示，**「保存」禁用**直到重新选择；此时不自动清空已保存的 `inputs`。
  - 未选择工作流时（新建流程的初始态）：表单区居中提示"先选择一个工作流，再填写它的入参"。
- **入参校验口径**：后端**不做**端口级校验（只校验 `inputs` 是对象、任务名路径安全、工作流存在）——必填校验在表单层；运行期以引擎的端口检查为准，缺必填会在 S4/S5 显示为可读错误。
- **差距**：`Port` **没有 `default` 字段**，所以没有"默认值预填"能力（缺口 #10，登记在 [06](./06-后续路线图.md) §七）；参数快照与当前工作流声明不一致时（工作流后来加了必填入参），**不自动改写已保存的 `inputs`**，由运行期报错 + 编辑页按当前模板重渲染。

### S4 任务 · 运行记录（`/tasks?tab=runs`）

- **目的**：查看全部运行记录（任务跑出来的、以及试运行/CLI/无头产生的），筛选、回看、取消、重跑、清理。
- **布局**：筛选栏 → 列表 → （行展开 → S5 运行详情）。
- **筛选栏**：名称搜索（匹配 `workflow_name` / `source` / `task_name` / `task_id`）、**任务筛选**（`task_name`，从任务列表行进入时预置）、状态下拉（全部 / 运行中 / 成功 / 失败 / 已取消）、刷新。
- **列表行**：状态徽章 + 工作流名 `workflow_name` + **任务名 `task_name`**（为 `null` 显示"（试运行 / 一次性）"）+ 来源 `source` + 开始时间 `started_at` + 耗时 `duration_ms`。
  - 状态口径：摘要现投影 **13** 个字段（含 `status` / `cancelled` / `run_dir`，WP2 已修缺口 #11；`task_name` 随任务定义实体新增，WP7）→ 列表层可直接按 成功（`status = "succeeded"`）/ 失败（`failed`）/ 已取消（`cancelled`）筛选与配色；`success` 仍可作粗粒度兜底。
  - **运行中**不在历史里（历史只记终态），来自 `run.list` 的 `{run_id, task_id, cancelled, started_at, has_process}`，需合并展示
- **分页**：`history.list {limit, offset}`（默认 50，`0` = 不限）→ 「加载更多」
- **行操作**：取消（仅运行中，`request.cancel {task_id}`）/ 重新运行（**有 `task_name` → 用该任务当前保存的入参复跑 `task.execute`**；无 → 用记录里的 `inputs` 快照复跑，`source = "inline"` 的记录提示不可复跑）/ 打开运行目录 / 删除（`history.delete {run_id}`）/ 「清空全部」（`history.clear` + 二次确认）
- **空态**：无记录 → 引导「新建任务」。
- **边界与差距**：
  - **保留策略**：后端按 `server.config.json` 的 `history.{enabled, max_runs=200, max_bytes=200MB}` **自动裁剪**（每次写入后 `_prune`，`max_runs: 0` 等于立即裁剪但仍写盘）→ 本清单口径为"**按上限自动裁剪**"，界面需有说明文案；这三项现可读写（`history.get_config` / `history.set_config`，WP4 已修缺口 #5），写盘后立即生效（`store._config()` 每次重读，无需重启）。
  - ⚠️ **裁剪只影响运行记录，不影响任务定义**：任务存在 `<output>/task_defs/`，与 `history/` 是两套生命周期——这正是"任务列表不能建立在运行记录之上"的原因。


### S5 运行详情（S4 行展开后的抽屉；可升级为 `/tasks/:runId` 二级页）

- **目的**：回答"这次为什么失败 / 每一步花了多久 / 输出了什么"。
- **数据**：`history.get {run_id}` → 完整记录 `{run_id, exec_run_id, task_id, task_name, workflow_name, source, started_at, ended_at, duration_ms, inputs, node_results, success, status, cancelled, error, run_dir}`
- **元素**：
  - 头部：状态徽章、`workflow_name`、**`task_name`**（`null` 时显示"（试运行 / 一次性）"，并提供"存为任务"入口：把 `workflow_name` + 本次 `inputs` 预填到 `/tasks/editor`；`source = "inline"` 的记录没有工作流名，只能手动选）、`run_id`、`task_id`、起止时间、`duration_ms`
  - **重新运行语义**：有 `task_name` → `task.execute {name}`（用该任务**当前保存**的入参，不是这条旧记录的快照）；无 `task_name` → 用本记录的 `inputs` 快照复跑
  - 输入快照：`inputs` 键值表；值为路径时提供「打开」（`openPath`）
  - 逐节点步骤：遍历 `node_results`（**以节点 id 为键的字典**），每项显示 `status`（`ok|failed|skipped|cancelled`）、`duration_ms`、`attempts`、`error`、`outputs`
    - `node_id` 是**相对运行根的路径**，形如 `loop/0/step`（`flow.foreach` / 分支 / 子工作流产生的嵌套）→ 建议按 `/` 分层缩进或树形展示
  - 节点输出：按端口名展示；**截断标记必须专门渲染** —— 被 `shrink_outputs` 裁过的值形如 `{"_truncated": true, "_chars": <原长度>, "_preview": <前若干字符>, "_reason"?: ...}`（阈值按**字符数**：单字符串 > 8×1024 字符、单次输出总量 > 256×1024 字符），不要当普通文本显示
  - 运行级 `outputs` / `error`
  - 日志区：`task.read_log {task_id, tail_bytes?}`（`content` / `truncated` / `size` / `log_path`）+ 「打开日志文件」+ 刷新
  - 操作：取消（运行中）/ 重新运行 / 打开运行目录 / 删除记录 / 删除产物（`task.delete_output {paths}`）
- **边界与差距**：
  - **运行目录路径**：`workflow.execute` / `template.execute` 的返回 payload 与 `history.get` 记录**现均带 `run_dir`**（`<output_dir>/runs/<slug>`；`""` 表示该轮未能创建产物目录，此时禁用「打开运行目录」）—— WP2 已修缺口 #4。直接拿它调 `openPath`，**不要自行拼接**：slug 来自渲染层本地生成的 JSON-RPC 请求 id，而历史的 `run_id` 是后端另生成的 uuid4，两者本来就对不上；记录里的 `exec_run_id` 才是请求 id。
  - 历史里的 `run_id` 是后端新生成的 32 位 uuid4 hex，**不等于** IPC 请求 id；`task_id` 才是任务维度标识。
  - 历史里**没有进度字段**；进度只能来自运行中的实时事件，历史回看只能看终态。

### S6 工具 `/tools` · 环境 `/tools/env` · 插件 `/tools/plugins`

**三个页面，不是一个页面的三个 tab 面板**（2026-09-28 决策）：每个页面有自己的页面标题、一句话描述、工具栏与空态，靠页面头右侧的**区段切换**跳转；三者共用侧边栏的「工具」导航项。原设计把它们塞进同一屏的三个 tab 里，导致一个页面头（"工具 / 工具描述符、运行环境与插件加载状态"）同时描述三件事、三份工具栏与空态只能留一份，且与环境依赖这条最关键的跨页信息脱节。逐屏提示词也相应拆成 `07-tools.md` / `08-envs.md` / `09-plugins.md`（一屏一文件）。

#### S6.1 工具 `/tools`

> **实现状态（已完成）**：`src/renderer/views/ToolsPage.vue` + `src/renderer/components/tools/`（`ToolsSectionNav.vue` 区段切换、`toolEnvDeps.ts` 依赖聚合纯函数，单测 `tests/unit/tools/toolEnvDeps.test.ts`）。

  | **环境依赖的就绪状态** | `workflow.list_tools[].env_deps`（环境 `name` 数组）**join** `env.list[]`（按 `name` 取 `display_name` / `is_valid`）——渲染层本地聚合，不需要新后端方法 |
- **卡片元素**：名称、描述、来源徽章（内置 / 已导入 / 插件）、版本、操作数、状态徽章（可用 / 不可用）、实际路径、**环境依赖徽章行**。
- **环境依赖徽章（本页新增要求）**：声明了 `env_deps` 的工具必须在卡片上点名它需要的环境与是否就绪——已就绪写「需要 Python · 已检测」（绿），缺失写「需要 Java · 未配置」（橙）。**理由**：工具"不可用"最常见的原因就是环境没配好（`DescriptorTool._compute_valid()` 里 `env_deps` 解析失败即 `is_valid = false`），只给一个「不可用」徽章等于不说原因，用户还得自己猜。**没有声明依赖的卡片不显示该行**（不要用"无依赖"之类占位文案）；空数组与"后端不返回"在界面上都表现为不显示（见缺口 #18）。
- **详情展开**：`ports.inputs` / `ports.outputs`（类型、必填、`options`、`direction: "output"` 的产物端口）、每个 `operations[]`（名称、描述、inputs、outputs），以及 `env_deps` 的逐个解析结果（`tool.get_tools` 的**单工具**分支对描述符工具返回该字段；**列表分支不返回**，卡片一律用 `workflow.list_tools`）。
- **操作**：配置自定义路径（`tool.set_custom_path {tool_name, path}` + 文件选择）、重置路径（`tool.reset_custom_path {tool_name}`）、删除（`tool.delete {name}`，内置禁删）、搜索系统 PATH 开关（`tool.set_search_mode {system_search}`）。
- **导入**：目录批量（`tool.import_pack {path}`，返回 `{ok, imported, updated, failed, results[]}`）；单文件（`readTextFile` 读出 JSON → `tool.add {descriptor}`，WP1 已修缺口 #2）。
- **空态**：无描述符工具 → 引导「从 `examples/tools/` 导入工具描述符」（界面文案不点名 `android` 子目录，理由同 S1）。
- **边界**：`tool.add` / `tool.delete` / `env.add` / `env.delete` 失败时后端**抛错**（error envelope，渲染层 `unwrapBackendResponse` 会抛出 `BackendError`）而不再返回 `{"error": ...}` 成功 payload —— WP0 已修缺口 #7，「导入描述符（单文件）」与「导入工具包」的坏目录/空目录同样走异常路径。

#### S6.2 环境 `/tools/env`

- **行元素**（`env.list` 或 `workflow.list_envs`，二者返回形状相同，**只选一个调用**）：环境名（`display_name`，Java / Python / Node）、检测到的二进制路径 `binary_path`、版本 `version`、状态徽章（`is_valid` → 已检测 / 未配置）、`root_path`。
- **告警带（本页新增要求）**：只要存在未配置的环境**且**有工具依赖它，页面头下方出一条橙色告警带：「Java 未配置：依赖它的 1 个工具当前不可用。」+ 次按钮「查看受影响的工具」（跳 `/tools`）。这是 S6.1 依赖徽章的**反向视图**：工具页回答"我缺什么"，环境页回答"缺了会怎样"。
- **反向依赖列（本页新增要求）**：每行右侧显示「被 N 个工具依赖」（`workflow.list_tools[].env_deps` 按环境 `name` 在渲染层计数）；未配置且被依赖时写「N 个工具依赖 · 不可用」。**不新增后端方法**，也不显示后端没有的字段（例如"哪些工作流用到它"）。
- **操作**：刷新、**更改路径**（`env.set_path {name, path}` + 文件/目录选择，重置用 `env.reset_path {name}`；WP3 已修缺口 #13，路径持久化在 `<output>/registry/overrides.json` 的 `env_paths` 段，解析优先级仅次于 `env_var_override`）、导入自定义环境（`env.add {descriptor}`，收整份描述符 → 需要表单或 JSON 编辑器）、删除（`env.delete {name}`，内置环境受保护会抛错）。
- **改路径后必须重拉**：`env.set_path` / `env.reset_path` 会改变工具的 `is_valid` 与 `binary_path`，因此保存后要**同时刷新 `env.list` 与工具列表**，否则环境页与工具页会互相矛盾。
- **边界**：`env.list`（与 `workflow.list_envs` 同形状）现返回 `{name, display_name, type, is_valid, binary_path, version, root_path, env_var_override, path_override, source}`（WP3 已修缺口 #3）→ 显示名可由 `display_name` 给出，内置（`source: "bundled"`）与用户导入（`"overlay"`）可区分，删除按钮可按 `source === "bundled"` 预先禁用；删除失败仍以异常返回后端原因。
- **内置行标记**：受保护的环境（`cli/registry/environments/*.json`：java / python / node）删除会被拒；界面需据此前置禁用删除或在失败后给出可读原因。

#### S6.3 插件 `/tools/plugins`

- **工具栏**：「添加插件」（`module` / `path` / `config` JSON）、「重载」（`plugin.reload`）、刷新（`plugin.list`）。
- **行元素**：`module`、kind 徽章（`shipped-native` 内置 / `native` 原生）、`version`、加载状态（`loaded` / `error`）。⚠️ `plugin.list` **不会**返回 `descriptor` 这一 kind（清单加载器只允许 `shipped-native` / `native`；描述符工具走 `tool.*`，见 S6.1），所以界面上只会有两种徽章。
- **操作**：删除（`plugin.delete {module}`，`shipped-native` 禁用）；「重载」后要**重新拉工具列表**（插件注册的工具会随之增减）。
- **边界**：加载器现记录单个插件的 import/apply 失败（`loader.errors()`），`plugin.list` 对失败项返回 `loaded = false` + 具体 `error`，清单里存在但既未加载也无错误的条目返回 `error = "not loaded"`（WP3 已修缺口 #8）→ 界面可展示"加载失败 / 未加载"；条目另带 `source`（`shipped` / `user`）。
- **不要在这页显示环境依赖徽章**：`plugin.list` 不返回环境依赖，插件注册出来的内置工具（`BuiltinTool`）也没有 `env_deps` 字段（缺口 #18）——即便事实上依赖（`exec.code` 就走 `get_python_bin()` → 环境注册表的 `python`），当前也没有数据来源，画上去就是编数据。同理**不显示"该插件注册了哪些工具"**（后端无插件↔工具归属字段）。

### S7 设置 `/settings`

- **通用**：请求超时（存储键是 **`commands.timeout`，单位毫秒**，默认 **300000 ms = 300 秒**，不是 30 秒；界面按秒显示、下限 30 s，与 `src/main/ipc/index.ts` 的 `>= 30000` 门槛一致；**主进程启动时读一次 → 改动需重启应用生效**，界面必须写明）、系统通知开关（**产品要求默认关**；主进程 `appStore.ts` 的 `enableNotifications` 默认值已改为 `false`，并通过 `APP_CONFIG_VERSION` 6→7 迁移把老库里的 `true` 翻转，缺口 #15 已修）、删除任务时清理输出文件。⚠️ 旧实现把该控件绑到顶层 `timeout`（不在 schema → 非法键 → 静默丢失），WP10 已改为 `commands.timeout`，别再绑回去（见 §7-#19）。
- **外观**：浅色 / 深色 / 自动（靠 `data-theme` 属性，**不是** `prefers-color-scheme`）。
- **语言**：简体中文 / English（文案必须同时进 `zh-CN.ts` 与 `en-US.ts`）。
- **行为 / 日志**：日志级别（debug / info / warn / error）。
- **路径（2026-09-28 修正：只有两行可改）**：
  | 行 | 键 | 可改？ | 真实作用 | 生效时机 |
  |---|---|---|---|---|
  | 工具链与运行时目录 | `appConfig.runtime` | ✅ 「浏览」目录 | 主进程把它解析成绝对路径注入 **`BT_RUNTIME_DIR`**；后端据此解析**描述符里相对 `path`**（示例 `adb/adb.exe`、`apktool/apktool.jar`）与**内置环境的 `search_paths`**（`java.json` 的 `jre`、`python.json` 的 `python`）；同时它还是**后端解释器候选** `runtime/python/python.exe` 的根 | **后端启动时读取一次 → 改完必须重启后端**（`startPythonService`） |
  | 后端目录 / 入口 | `appConfig.server`（+ `serverEntry`） | ✅ 目录（入口不暴露） | 用哪个 `main.py` 启动后端；默认 `.\cli` 就是打包后 `extraResources` 的位置 | 同上（重启后生效） |
  - **数据来源**：`settings.getViewModel`（`{settings, displayPaths: {runtime, server}}`）/ `settings.resolvePaths {runtime, server}`（把候选值解析成绝对路径再显示）/ `appConfig.set`（保存）—— **只支持这两个键**，多画的行没有接口可用。
- **不要再画 `serverEntry` / `runtimeExecutable` / `output` / `logs` 四行**：
  - `serverEntry` / `runtimeExecutable` 在 schema 里可写，但**界面不暴露**（细粒度应急旋钮：只有 `runtime` 目录内的可执行文件名需要改时才用）。
  - **`output` / `logs` 根本不是 appConfig 的路径**：数据目录由主进程 `getAppLocalDataPath()` 下的固定子目录决定（`cache/`、`output/`、`tasks/`、`logs/`），通过 `BT_OUTPUT_DIR` / `BT_LOG_DIR` / `BT_CACHE_DIR` / `BT_TASKS_DIR` 注入后端（`src/main/python/service.ts:24-44`）。原来 appConfig 里的 `output.output` 与 `javaPath` **没有任何读取方**，已随 WP10 从 schema、`WRITABLE_CONFIG_KEYS` 删除（`APP_CONFIG_VERSION` 7→8 迁移清理老库残留，缺口 #19 已修）——所以**不能**给这两行画「浏览」按钮。真实路径是**只读**信息，显示在「存储」分组（`cache.info` 给出各块的 `path` / `size` / `files`，见下）。
- **粗粒度 vs 细粒度（不要以为三者重复）**：本组是**一个根目录管所有相对路径**；`/tools` 的「自定义路径」（`tool.set_custom_path`）是**按单个工具**覆盖；`/tools/env` 的「更改路径」（`env.set_path`）是**按单个环境**覆盖。⚠️ 特别说明：`/tools/env` 改的是**工具运行时**用的 Python/Java（后端进程内解析，**立即生效**），**不会**改变**后端自己**用哪个解释器（那是上面 `runtime` 行 + 重启）；界面上不要暗示它能修好后端启动失败。
- **工具路径**：**收敛到 `/tools`（工具页）**，设置页只留一个跳转链接，避免双入口（Phase 4 要求）。⚠️ 现状 `SettingsPage.vue` 仍整块保留「工具路径」卡片（含重置与校验），属 T24 未做的遗留。
- **存储**：`cache.info` 四块（tasks / output / logs 各自的 `path` / `size` / `files`，加 `total`）；每块可单独清除（`tasks.clear` / `output.clear` / `logs.clear`），另有「一键清除全部」（`storage.clear {target: "all"}`）。
  - ⚠️ **仍要写清后果**：`output.clear` 与 `storage.clear {target:"all"}` 现**默认跳过** `templates/`（已保存工作流）、`task_defs/`（**已保存的任务定义**）、`history/`（运行历史）、`runs/`（运行产物）、`registry/`（工具/环境覆盖与描述符）与 `output/plugins.json`（插件清单）—— WP4 已修缺口 #6，`task_defs` 随任务定义实体加入（WP7）；`cache.info.managed` 给出这**五块**的用量，可分别用 `target: "templates" | "task_defs" | "history" | "runs" | "registry"` 单独清理（`registry` 会清掉自定义工具路径、环境路径覆盖与导入的描述符；**`task_defs` 会清掉全部任务定义**——两者都属高风险操作，需二次确认）。只有显式传 `include_managed: true`（或 `target` 指向单个 managed 目录）才会删到这些数据，界面**不要**把它做成默认路径；「一键清除全部」的文案改为"清除产物与日志（保留工作流、任务与历史）"。
- **高级**：历史保留策略（`enabled` / `max_runs` / `max_bytes`）—— 现可读写：`history.get_config` 返回 `{enabled, max_runs, max_bytes, config_path}`，`history.set_config` 写入 `server.config.json`（保留其它键，原子落盘，写后立即生效）（WP4 已修缺口 #5）。
- **关于块**：应用版本 / Electron / Node / Python（`app.info` / `build.info` / `system.info`）+ 后端健康徽章（`get-backend-health`，仅探测进程存活）。
- **底部入口**：「诊断信息」→ `/diagnostics`；「关于」→ 弹窗（与 `/about` 二级路由同源同内容，二者只保留一个入口；03/02 中现有的 `/about` 页面内容即为该块）。

### S8 诊断 `/diagnostics`（只读）

- **后端健康**：健康 / 异常 / 未知、最后检查时间、**进程存活时长（前端计时）**。主进程 `get-backend-health` 只探测进程存活、`uptime_s` 恒为 `null`（有意设计）；能给出真实 uptime 的 `health` 方法已接入 `ApiMethodMap`（WP2），渲染层切换过去即可（T24）。
- **运行中运行表**：`run.list` → `run_id` / `task_id` / `cancelled` / `started_at` / `has_process`，每行「取消」（`request.cancel`）。⚠️ 该接口原名 `task.list`，随任务定义实体改名（WP7）：它列的是**在跑的运行**，与「任务定义」无关。
- **日志尾部**：三个 tab —— 后端日志（`logs.tail {lines}`）、Electron 日志（`readElectronLogTail`）、渲染层日志（内存 ring buffer）；显示行数、`truncated` 标记、刷新。
- **解析后路径**：runtime / server。
- **边界**：健康检查只判断进程存活，进程活着但卡死时仍报"健康"；诊断页不做任何配置写入。

## 5. 跨屏约定

1. **主题**：三模式（浅色 / 深色 / 自动，靠 `data-theme`）都要支持；设计稿至少出**浅色 + 深色两态**（"自动"跟随系统，等价于浅或深）；颜色只用 `--app-*` 变量（新增色相 light/dark 两侧都加）；字体只用 `--app-font` / `--app-font-mono`。
2. **i18n**：所有文案进 `zh-CN.ts` + `en-US.ts`；顺带清理遗留 Android 文案（`task.*` 里的 APK/设备/签名区块）与未被引用的键。
3. **状态徽章语义**（全站统一）：

   | 语义 | 值 | 视觉 |
   |---|---|---|
   | 运行中 | `running` | 蓝色 + spinner |
   | 成功 | `ok` / `succeeded` / `success=true` | 绿色 ✓ |
   | 失败 | `failed` | 红色 ✗ |
   | 跳过 | `skipped` | 灰色（`on_failure: "skip"` 触发，**不影响整轮成功**） |
   | 取消 | `cancelled` | 灰色/橙色（取消优先于失败：被取消的节点报 `cancelled` 而不是 `failed`） |
   | 未运行 | 无记录 | 中性灰 |

4. **三态齐备**：每个列表页必须有 加载中 / 空 / 错误（可重试）；每个空态必须给可点击的下一步。
5. **破坏性操作**：二次确认 + 明确后果文案；取消类操作不弹二次确认（运行中任务取消除外，需确认）。
6. **错误呈现**：后端错误经统一解包后展示 `message`；弱失败（返回 `{error}` 的 `tool.*` / `env.*`）必须显式检查。
7. **不做假定**：不要显示后端没有的字段（例如历史里的"进度百分比"；**内置/插件工具的环境依赖与"插件注册了哪些工具"也属于此类，见 §7-#18**；插件加载状态、运行目录、模板标签、描述符工具的 `env_deps` 等字段现已真实返回，见 §7 状态）。
