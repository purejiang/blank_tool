# 03 数据模型

> 本文档是维护 Blank Tool 工作流/模板/工具/环境系统的核心参考。所有类、字段、行为均已对照源码核实（标注 **延后** 的除外）。产品与架构背景见 [01-产品概述.md](./01-产品概述.md) 与 [02-系统架构.md](./02-系统架构.md)。

## 1. 工作流定义 WorkflowDefinition

**文件**：`cli/app/workflow/definition.py`

`WorkflowDefinition` 是工作流的**模式（schema）**，与执行解耦：它只描述"哪些工具按什么顺序、带什么参数运行"，保存/加载/校验都是纯 JSON。

```python
@dataclass
class WorkflowDefinition:
    name: str                                  # 唯一名称，如 "download-install"
    version: str = "1.0"                       # 工作流 schema 语义版本
    description: str = ""                      # 人类可读说明
    inputs: List[Port] = field(default_factory=list)    # 工作流级输入端口
    outputs: List[Port] = field(default_factory=list)   # 工作流级输出端口
    nodes: List[WorkflowNode] = field(default_factory=list)  # 节点，靠 next 串联
    edges: List[Dict[str, Any]] = field(default_factory=list)  # 预留，线性模式必须为空
```

序列化：`to_dict()` / `from_dict()` / `to_json_file()` / `from_json_file()`（UTF-8 JSON，缩进 2）。

### 1.1 线性模式规则（唯一控制流）

**`node.next` 是控制流的唯一来源，`edges` 是未来 DAG 模式的预留位，线性模式下必须为空列表**；非空 `edges`（或与 `next` 混用）会抛 `ValueError`。

### 1.2 校验规则（`__post_init__`，构造即校验）

1. `name` 必须是非空字符串；
2. `edges` 必须是列表且**为空**（预留 DAG 模式）；
3. 节点 `id` 必须唯一；
4. 每个 `node.next` 必须指向已存在的节点 id；
5. 线性链必须**恰好一个入口节点**（没有其他节点的 `next` 指向它）；
6. 从入口沿 `next` 走**不得成环**。

> 预留字段说明：`condition`、`on_success`、`type` 会被存储但**当前线性执行器不评估**（为了向后兼容，故意不在校验阶段拒绝 `condition` 字段）。静态校验 `validate_workflow`（`cli/app/workflow/validation.py`）还额外检查：工具是否存在、必填入参是否存在、`$nodes.<id>.outputs.<port>` 引用的端口基类型兼容、无孤儿节点。

## 2. 工作流节点 WorkflowNode

**文件**：`cli/app/workflow/definition.py`

```python
@dataclass
class WorkflowNode:
    id: str                        # 唯一节点标识，被其他节点的 next 引用
    type: str = "step"             # 预留 DAG 模式节点类型；当前只有 "step" 有意义
    tool: str = ""                 # 要调用的工具名，如 "bundletool" 或 "file.read"
    params: Dict[str, Any] = field(default_factory=dict)  # 传给工具的参数
    next: Optional[str] = None     # 线性链上下一节点 id；None = 末尾
    on_success: Optional[str] = None   # 预留 DAG；线性执行器不评估
    on_failure: str = "fail"       # fail（默认，终止）/ skip（跳过继续）/ retry:N
    condition: Optional[str] = None    # 预留 DAG 分支；线性模式下存储但不执行
    retry: int = 0                 # 失败重试次数（on_failure 为 retry:N 时使用）
```

节点校验（`__post_init__`）：`id` 与 `tool` 非空字符串；`on_failure` 必须是 `fail`、`skip` 或 `retry:N` 前缀。

**执行语义**（`cli/app/workflow/engine.py` 的 `WorkflowEngine`）：

- 入口 → 沿 `next` 逐节点执行；
- 节点参数先经 `ExpressionEngine` 解析（见第 8 节），再对工具端口做**必填存在性校验**（MVP 只查缺失，类型检查不做）；
- 失败处理：`fail`（终止整个工作流）、`skip`（记录失败但继续下一个节点）、`retry:N`（最多重试 N 次，重试预算也可来自 `node.retry`）；
- 带 `condition` 的节点在线性模式下直接抛 `NotImplementedError`；
- 工具分派双契约：`BuiltinTool` 走 `(params, ToolContext)`；描述符/代码命令工具走 `(command_list, CommandExecutionContext)`，命令列表取自 `params["args"]`。

## 3. 端口 Port

**文件**：`cli/app/protocol/ports.py`

端口是工作流节点与工具之间的契约：工具用端口声明输入输出，引擎据此校验每个必填输入在执行前是否提供。

```python
@dataclass
class Port:
    name: str                       # snake_case，正则 ^[a-z][a-z0-9_]*$
    type: TypeAnnotation            # 值类型（基础类型 + 建议性子类型）
    required: bool = True           # 输入是否必填（输出可忽略）
    description: str = ""           # 人类可读说明
    options: List[str] = field(default_factory=list)  # 单选下拉的候选值（仅 TEXT 基类型）
    multi: bool = False             # 是否多选（仅 TEXT 基类型，T2）
    direction: str = "input"        # "input"（默认）| "output"——见 3.1
```

`PortSet`（一个工具的输入+输出集合）：

- 输入与输出**内部**各自不允许重名（`_reject_duplicates`），输入输出两侧允许同名（如 `path` 同时是入参和出参）；
- `validate_inputs(data) -> List[str]`：**MVP 仅检查必填入参是否缺失**，返回错误字符串列表，空列表 = 合法。实际的值/类型运行时校验在工作流引擎里做。

### 3.1 产物端口（`direction: "output"`）

许多工具的"输出"其实是用户**作为输入传入的路径**（典型是命令行 `--out <path>` 参数）：工具并不在 stdout 里吐出这个值，而是按用户指定的位置写文件。要让下游节点能引用这个产物，又不想让描述符作者在 inputs 与 outputs 两侧**重复声明同一个端口**，Port 增加了 `direction` 字段：

- **默认 `"input"`**：纯输入端口，工具读取该值（如 `apk_path`、`src`）。
- **`"output"`**：**值仍按入参绑定与校验**（用户必须提供，例如 `--out` 参数），但语义上**它代表工具的产物**。引擎执行后会把这个绑定值原样复制到节点的 `outputs` 字典里（用 `setdefault` 语义，**不覆盖**工具自己回填的同名字段）。

效果：

| 角度 | 行为 |
|---|---|
| 节点 outputs | `direction=output` 的入参的绑定值自动出现在 `$nodes.<id>.outputs.<name>`，下游节点可直接引用 |
| 工具列表 (`workflow.list_tools`) | 同一端口**镜像出现在 inputs 与 outputs 两侧**（按名去重），编辑器把它当产物端口渲染，避免描述符作者在 outputs 里再写一遍 |
| 与"工具自己产出的 outputs"冲突 | 不覆盖——真实工具输出优先（`setdefault`） |
| 可选 output 端口未绑定 | 不出现在 outputs（不写 `None`，不抛错） |

> 仅对 `PortSet.inputs` 内的端口有意义；`PortSet.outputs` 内的端口本身就总是"输出方向"，`direction` 字段对它们没有额外效果。

示例（`examples/tools/android/apktool.json` 的 `decode` 操作）：

```json
{
  "name": "decode",
  "inputs": [
    {"name": "apk_path", "type": {"base": "file", "subtype": "apk"}, "required": true},
    {"name": "output_dir", "type": {"base": "directory"}, "required": true,
     "direction": "output", "description": "Directory to write the decoded tree to."}
  ],
  "outputs": [],
  "args_map": ["d", { "param": "apk_path" }, "-o", { "param": "output_dir" }]
}
```

下游节点引用：`$nodes.decompile.outputs.output_dir` → 直接拿到 `output_dir` 的绑定值，无需把 `output_dir` 再写到 outputs 数组里。

## 4. 类型系统 TypeAnnotation

**文件**：`cli/app/protocol/types.py`

两层类型模型：

```python
class BaseType(Enum):
    FILE = "file"
    DIRECTORY = "directory"
    TEXT = "text"
    NUMBER = "number"
    BOOLEAN = "boolean"
    JSON = "json"

@dataclass(frozen=True)
class TypeAnnotation:
    base: BaseType                  # 基础类型
    subtype: Optional[str] = None   # 领域标注，仅建议性（advisory），如 "apk"、"aab"
```

关键约定：

- `subtype` 必须匹配 `^[a-z][a-z0-9_]*$`，**引擎完全忽略它做兼容性判断**；
- 兼容性 `TypeAnnotation.is_compatible(source, target)` **只看 base**：`source.base == target.base` 即兼容。

### 4.1 端口在 JSON 中的序列化

`Port.to_dict()` 把 `TypeAnnotation` 内联为 `{"base": <enum值>, "subtype": <str|None>}`，并始终输出 `options`/`multi`/`direction` 三个字段（默认值 `[]` / `False` / `"input"`），保持 wire shape 稳定。`from_dict` 对缺失的这三个字段回退默认值，所以**老工作流 JSON（没有这三个字段）能无损反序列化**。

## 5. 工作流 JSON 示例

### 5.1 download-install：内置工具 + 描述符工具混排

**文件**：`examples/workflows/android/download-install.json`（已迁至 `examples/`，改经导入使用）

```json
{
  "name": "download-install",
  "version": "1.0",
  "description": "Download an APK from a URL and install it on a device",
  "inputs": [
    {"name": "url", "type": {"base": "text"}, "required": true, "description": "URL to download the APK from"},
    {"name": "device_id", "type": {"base": "text"}, "required": true, "description": "ADB device ID to install to"}
  ],
  "outputs": [
    {"name": "path", "type": {"base": "file"}, "required": true, "description": "Path to the downloaded APK"}
  ],
  "nodes": [
    {
      "id": "download",
      "tool": "net.download",
      "params": {"url": "$inputs.url", "dest": "downloaded.apk"},
      "next": "install"
    },
    {
      "id": "install",
      "tool": "adb",
      "params": {"args": ["install", "-r", "$nodes.download.outputs.path"]},
      "next": null,
      "on_failure": "fail"
    }
  ],
  "edges": []
}
```

注意两个节点的**不同参数形态**：

- `net.download` 是内置原子工具，参数按**命名端口**提供（`url`、`dest`）；
- `adb` 是描述符命令工具，参数是 `params.args`（命令行参数列表），且直接引用了上一节点输出 `$nodes.download.outputs.path`。

## 6. 模板 Template

### 6.1 存储：FileTemplateStore

**文件**：`cli/app/template/store.py`

- 抽象接口 `TemplateStore`（`save` / `load` / `list` / `delete` / `exists`），为将来替换 SQLite 存储留口；
- `FileTemplateStore`：每个模板一个文件 `<name>.json`，存放在**可写目录**；
- 目录解析：`BT_TEMPLATES_DIR` 环境变量 → 回退 `<output_dir>/templates`（`get_output_dir()` 返回可写路径）；构造时 `os.makedirs(exist_ok=True)`；
- `TemplateInfo`（`list` 返回）：`name`、`description`、`created_at`、`updated_at`、`tags`、`node_count`；
- `copy_defaults(source_dir)`：**已删除**（从未被调用，T21 随领域内容外部化移除）。设计意图是从只读目录（如 `cli/workflows/`）把不存在的 `*.json` 播种到可写目录，已存在的名字**绝不覆盖**；但仓库中没有调用方，且领域内容外部化后不再有随包模板，播种概念随之取消。

**文件格式（wrapped）**：

```json
{
  "definition": { "...WorkflowDefinition.to_dict()..." },
  "created_at": "2026-08-03T12:00:00.000000",
  "updated_at": "2026-08-03T12:00:00.000000",
  "description": "...",
  "tags": ["android", "install"]
}
```

> **为什么必须可写目录（Oracle finding #2）**：打包后 `cli/` 树被 `electron-builder` 拷到 `process.resourcesPath`（`extraResources`，见 `package.json`），是**只读**的，用户模板必须存于其外的可写目录。外部化后不再有任何随包模板，该结论依旧成立（不依赖预置内容）。`load` 同时接受 wrapped 格式与裸定义（无 `definition` 键时整文件即定义）；**裸定义加载就是导入格式**（`examples/` 中的工作流 JSON 即以此方式导入），`copy_defaults` 播种路径已删除；`list` 对损坏/非法文件跳过不崩溃。

**文件**：`cli/app/handlers/template_handler.py`，经 `API_MAP` 自动注册，走 `call-backend-api` 通道：

| 方法 | 行为 |

## 7. 工具描述符与执行

### 7.1 ToolDescriptor

**文件**：`cli/app/tools/descriptor_tool.py`

数据驱动的第三方工具声明，字段：

```python
@dataclass
class ToolDescriptor:
    name: str                                  # 唯一名，如 "apktool"
    display_name: str                          # 人类可读名，如 "Apktool"
    type: Union[str, Dict[str, str]]           # binary | java_jar | python_script | node_script | shell_script（支持按平台 dict）

    validate: Dict[str, Any]                   # {"cmd", "expect_contains", "expect_in", "expect_returncode"}
    version: Dict[str, Any]                    # {"cmd", "regex", "from_stream"}
    inputs: List[Port]                         # 声明式输入端口
    outputs: List[Port]                        # 声明式输出端口
    sensitive_arg_patterns: List[str] = field(default_factory=list)   # 日志脱敏扩展点
```

`load_descriptor(path)` 从 JSON 文件读取并校验（缺 `name`/`display_name`/`type`/`path` 抛错）。

### 7.3 执行：DescriptorTool 与引擎

- `DescriptorTool` 提供统一的工具接口表面（`name`、`is_valid`、`version`、`tool_path`、`execute`），使注册表能统一管理描述符工具与内置/插件工具（`BuiltinTool` 亦镜像该表面）；
- `is_valid` = 所有 env_dep 可解析 + 二进制存在 + validate 命令通过；`version` 用 `version_regex` 从输出抓取；
- 命令构造：`binary` 直接用工具路径作前缀；`java_jar` 用 `[java, "-jar", tool_path]`；`python_script`/`node_script` 用解释器前缀（`_INTERPRETER_DEP_BY_TYPE`），`shell_script` 同 binary；已带前缀的命令不重复加前缀；
- 工作流引擎（`cli/app/workflow/engine.py`）对描述符/内置工具按命令列表契约执行：`params["args"]` 解析后作为命令列表传给 `tool.execute(command, context)`，返回的 `{success, returncode, stdout, stderr}` 归一化为节点输出，非零退出码/显式失败会触发 `on_failure` 语义。
- **产物端口 surface**：操作里 `direction=output` 的入参（典型如 `--out <path>`），其绑定值会被 `_execute_operation` 复制到节点 outputs 字典（`setdefault`，不覆盖工具自填的同名字段），让下游 `$nodes.<id>.outputs.<name>` 引用无需再在 outputs 侧重复声明。详见 [3.1](#31-产物端口direction-output)。
- `Operation` 支持 `timeout`（秒，None=默认 600）与 `cwd`（静态路径 / `$workdir` / `$inputs.<key>`，None=work_dir；`$inputs.<key>` 缺失时 warn 并回退 work_dir），见 `descriptor_tool.py` 的 `_resolve_operation_cwd`。

## 8. 表达式引擎（供节点参数使用）

**文件**：`cli/app/workflow/expression.py`

节点参数里的 `$` 前缀点号引用在运行时解析（MVP：仅点号替换，无条件/循环/算术，不用 eval/exec/getattr）：

| 根 | 示例 | 含义 |
|----|------|------|
| `$inputs.<key>` | `$inputs.url` | 工作流级输入 |
| `$nodes.<id>.outputs.<port>` | `$nodes.download.outputs.path` | 上游节点输出 |
| `$nodes.<id>.params.<key>` | 无示例 | 上游节点已解析参数 |
| `$env.<name>` | `$env.PATH` | 环境变量 |
| `$workdir` | `$workdir/output.apks` | 工作目录 |

附加管道变换（固定集合）：`basename`、`dirname`、`default:<value>`。安全模型：固定根分发表 + 拒绝 `^_`（dunder/私有）路径组件 + 未知根/未知管道名直接抛 `ExpressionError`。

## 9. 环境描述符与解析

### 9.1 EnvironmentDescriptor

**文件**：`cli/app/env/descriptor.py`

```python
@dataclass
class EnvironmentDescriptor:
    name: str                   # snake_case 标识，如 "java"
    display_name: str           # 如 "Java Runtime"
    type: str                   # jre | python | node | custom
    binary: str                 # 相对环境根目录，如 "bin/java.exe"
    version_cmd: List[str]      # 版本探测参数，如 ["-version"]
    version_regex: str          # 提取版本的正则（恰好一个捕获组）
    search_paths: List[str]     # 相对 runtime/ 的搜索目录；空 = 未捆绑，需用户提供
    importable: bool = True     # 是否允许用户导入自定义实例
    env_var_override: Optional[str] = None   # 直接指向二进制的环境变量名，如 "BT_JAVA_BIN"
```

必填字段（缺则 `from_dict` 抛错）：`name`、`display_name`、`type`、`binary`、`version_cmd`、`version_regex`、`search_paths`。

**真实示例**：`cli/registry/environments/java.json`

```json
{
  "name": "java",
  "display_name": "Java Runtime",
  "type": "jre",
  "binary": "bin/java.exe",
  "version_cmd": ["-version"],
  "version_regex": "version \"([^\"]+)\"",
  "search_paths": ["jre"],
  "importable": true,
  "env_var_override": "BT_JAVA_BIN"
}
```

### 9.2 EnvironmentRegistry 四级解析

**文件**：`cli/app/env/registry.py`，默认描述符目录 `cli/registry/environments/`（java、python、node 三个）。

`resolve(name)` 按顺序找二进制，**先命中先得**，结果缓存至 `refresh()`：

1. **env_var_override**：描述符声明的环境变量（如 `BT_JAVA_BIN`）存在且指向的文件存在；
2. **内置运行时**：`runtime/<search_path>/<binary>`（如 `runtime/jre/bin/java.exe`）；
3. **系统环境变量**：按类型探测（jre → `JAVA_HOME`/`JRE_HOME`；python → `PYTHONHOME`；node → `NODE_HOME`/`NODEJS_HOME`；custom 无映射），尝试 `<root>/<binary>` 与 `<root>/bin/<binary>` 两种布局；
4. **PATH**：用二进制文件名 `shutil.which(...)`。

版本探测：跑 `[binary] + version_cmd`，15 秒超时，stdout+stderr 合并后按 `version_regex` 提取；探测退出码非 0 则 `is_valid=False`。`resolve` 对未知环境名**不抛异常**，返回空的无效 `ResolvedEnvironment`。

## 10. 已实现 / 延后

### 10.1 【已完成】单选 / 多选入参

`Port` 已增加两个字段，编辑器暴露**八种入参类型**：

- `options: List[str]`：可选项列表（单选下拉）；
- `multi: bool`：是否多选。

编辑器已暴露的类型全集：字符串（text）、文件（file）、文件夹（directory）、布尔（boolean）、数字（number）、JSON（json）、单选列表、多选列表。**动态数据源绑定（如设备列表）已明确延后**（见路线图），所以选项现阶段是静态列表。

### 10.2 【已完成】统一「操作」模型

迁移结果：

| 维度 | 现状（已实现） |
|------|----------|
| 内置原子工具（`file.read`、`net.download`、`exec.shell`、`exec.code` 等，`cli/app/tools/builtin/`，`BuiltinTool` 见 `cli/app/tools/builtin/base.py`） | 已按"声明 `ports` + 类型化 `execute(inputs, context)`"实现，保持不变，作为天然范本 |
| 描述符命令工具（apktool、adb 等，现位于 `examples/tools/android/`） | 已升级为 **operations**：工具 = JSON（元信息 + env_deps + validate/version + `operations[]`），每个 operation 含类型化 inputs/outputs 与 args 映射（T3）；APK 链路工具（apktool / adb / bundletool）已迁移为范例（T5） |
| 节点 | 节点可引用 `tool + operation`，并**绑定类型化输入**，不再裸写命令参数（T4）；引擎按 operation 校验输入、拼命令、返回类型化输出（`engine.py` 的 `_execute_operation_tool`） |
| 脚本 | 已统一为 `*_script` 类型 + env_deps，与普通工具同构（T17，如 `examples/tools/android/apk-audit.json`） |

一句话概括：**"裸写 CLI 参数"已升级为"声明操作 + 绑定类型化输入"**，编辑器可对每个节点做类型化校验与表单化配置，脚本（`*_script`）也归入同一工具模型。
