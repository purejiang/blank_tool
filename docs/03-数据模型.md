# 03 数据模型

> 本文档是维护 Blanks 工作流/工具/环境系统的核心参考。所有类、字段、行为均已对照源码核实（标注 **延后** 的除外）。产品与架构背景见 [01-产品概述.md](./01-产品概述.md) 与 [02-系统架构.md](./02-系统架构.md)。

## 1. 工作流定义 WorkflowDefinition

**文件**：`cli/app/workflow/definition.py`

`WorkflowDefinition` 是工作流的**模式（schema）**，与执行解耦：它只描述"哪些工具按什么顺序、带什么参数运行"，保存/加载/校验都是纯 JSON。

```python
@dataclass
class WorkflowDefinition:
    name: str                                  # 唯一名称，如 "download-install"
    version: str = "1.0"                       # 工作流 schema 语义版本
    description: str = ""                      # 人类可读说明
    inputs: List[Port] = field(default_factory=list)    # 工作流级输入端口
    outputs: List[Port] = field(default_factory=list)   # 工作流级输出端口
    nodes: List[WorkflowNode] = field(default_factory=list)  # 节点，靠 next 串联
```

序列化：`to_dict()` / `from_dict()` / `to_json_file()` / `from_json_file()`（UTF-8 JSON，缩进 2）。`from_dict()` **忽略未知键**（老版本 JSON 里的 `edges` / `condition` / `on_success` 会被直接丢弃，不会报错）。

### 1.1 线性模式规则（唯一控制流）

**`node.next` 是控制流的唯一来源**。分支用 `flow.branch` + `flow.compare` 组合实现（见第 9 节），不靠节点级条件字段 —— 因此 schema 里没有"存而不用"的字段。

### 1.2 校验规则（`__post_init__`，构造即校验）

1. `name` 必须是非空字符串；
2. 节点 `id` 必须唯一；
3. 每个 `node.next` 必须指向已存在的节点 id；
4. 线性链必须**恰好一个入口节点**（没有其他节点的 `next` 指向它）；
5. 从入口沿 `next` 走**不得成环**。

> 静态校验 `validate_workflow`（`cli/app/workflow/validation.py`）额外检查：工具是否存在、必填入参是否存在、`$nodes.<id>.outputs.<port>` 引用的端口基类型兼容、无孤儿节点。

## 2. 工作流节点 WorkflowNode

**文件**：`cli/app/workflow/definition.py`

```python
@dataclass
class WorkflowNode:
    id: str                        # 唯一节点标识，被其他节点的 next 引用
    type: str = "step"             # 节点类型标签，编辑器使用；当前只有 "step"
    tool: str = ""                 # 要调用的工具名，如 "bundletool" 或 "file.read"
    params: Dict[str, Any] = field(default_factory=dict)  # 传给工具的参数
    next: Optional[str] = None     # 线性链上下一节点 id；None = 末尾
    on_failure: str = "fail"       # fail（默认，终止）/ skip（跳过继续）
    retry: int = 0                 # 失败后的额外尝试次数（0 = 不重试）
```

节点校验（`__post_init__`）：`id` 与 `tool` 非空字符串；`on_failure` 必须是 `fail` 或 `skip`。

**执行语义**（`cli/app/workflow/engine.py` 的 `WorkflowEngine`）：

- 入口 → 沿 `next` 逐节点执行；
- 节点参数先经 `ExpressionEngine` 解析（见第 8 节），再对工具端口做**必填存在性校验**（运行时只查缺失，类型检查仅记 DEBUG 日志、不阻断）；
- 失败处理：`fail`（终止整个工作流）、`skip`（记录失败但继续下一个节点）；`retry` 是失败后的额外尝试次数，退避为 `min(2^(n-1), 30)` 秒；
- **不可重试**的失败不消耗重试预算：取消、未知工具、必填入参缺失、以及工具抛出的 `NonRetryableToolError`（如 `flow.assert` 断言失败）；
- 每个节点恰好发一个终态事件 `node_completed`（带 `status`：`ok` / `failed` / `skipped` / `cancelled`）；
- 工具统一走 `tool.execute(params, ToolContext)` 一个契约。

### 2.1 运行时工作目录（work_dir）与运行产物目录（rundir）

一次运行的 `work_dir` 决定**相对路径**解析：`file.*` / `text.grep` 的相对路径、`$workdir` 表达式都以它为准。解析优先级：

1. **显式传入**：`workflow.execute` / `task.execute` 的 `params.work_dir`（渲染层/任务页通常传任务目录）；
2. **文件自己的目录**：`workflow.execute` 传 `path`（以及 CLI `run <文件.json>`）时，取该 JSON 文件所在目录；
3. **兜底：本次运行的产物目录**（`$rundir`，即 `<output_dir>/runs/<run slug>`）——**按 id / 名称引用一份已保存的工作流就走这一档**；
4. 连产物目录都建不出来时，退回进程当前目录。

> ⚠️ **2026-09-30 行为变更**：第 3 档以前是"模板库目录"（`BT_TEMPLATES_DIR` → `<output_dir>/templates`）。按名引用一份已保存的工作流时，相对路径现在解析在**它自己那一次运行的产物目录**里，而不是工作流库里——工作流库是只读的定义仓库，相对输入本来就不该从那里读。传 `path` 的文件目标行为不变（仍取文件所在目录），显式 `params.work_dir` 也永远优先。

因此从任意 CWD 运行工作流，读相对输入都不再依赖 CWD。

**引擎自产文件不走 work_dir**，而是写进本次运行的产物目录：

- 路径：`<output_dir>/runs/<run_id>/`（`run_id` = `task_id`，CLI 无 `--task-id` 时为 `cli`），由引擎在 `execute()` 开头创建一次，所有嵌套层共用；
- 表达式根 `$rundir` / `${rundir}` 暴露该目录，供工作流作者写自己的产物，例如
  `"path": "${rundir}/evidence-${inputs.path | basename}.txt"`；
- 目前引擎自产文件只有 `flow.foreach` 的 `results_file`（`foreach_<run_id>_<node path>.json`）；
- 目录不可写时 `$rundir` 解析为空串，`flow.foreach` 退回 `work_dir`，运行本身不受影响；
- 注意目录按 `run_id` 复用：同一个 `task_id` 重跑会覆盖同名产物，需要隔离时用不同 `task_id`。

`work_dir` 可以是源码树，所以**不要**把引擎产物写进去（曾导致 `workflow.list()` 把产物当坏定义跳过）。

## 3. 端口 Port

**文件**：`cli/app/protocol/ports.py`

端口是工作流节点与工具之间的契约：工具用端口声明输入输出，引擎据此校验每个必填输入在执行前是否提供。

```python
@dataclass
class Port:
    name: str                       # snake_case，正则 ^[a-z][a-z0-9_]*$
    type: TypeAnnotation            # 值类型（基础类型 + 建议性子类型）
    required: bool = True           # 输入是否必填（输出可忽略）
    description: str = ""           # 人类可读说明
    options: List[str] = field(default_factory=list)  # 单选下拉的候选值（仅 TEXT 基类型）
    multi: bool = False             # 是否多选（仅 TEXT 基类型，T2）
    direction: str = "input"        # "input"（默认）| "output"——见 3.1
```

`PortSet`（一个工具的输入+输出集合）：

- 输入与输出**内部**各自不允许重名（`_reject_duplicates`），输入输出两侧允许同名（如 `path` 同时是入参和出参）；
- `validate_inputs(data) -> List[str]`：**MVP 仅检查必填入参是否缺失**，返回错误字符串列表，空列表 = 合法。实际的值/类型运行时校验在工作流引擎里做。

### 3.1 产物端口（`direction: "output"`）

许多工具的"输出"其实是用户**作为输入传入的路径**（典型是命令行 `--out <path>` 参数）：工具并不在 stdout 里吐出这个值，而是按用户指定的位置写文件。要让下游节点能引用这个产物，又不想让描述符作者在 inputs 与 outputs 两侧**重复声明同一个端口**，Port 增加了 `direction` 字段：

- **默认 `"input"`**：纯输入端口，工具读取该值（如 `apk_path`、`src`）。
- **`"output"`**：**值仍按入参绑定与校验**（用户必须提供，例如 `--out` 参数），但语义上**它代表工具的产物**。引擎执行后会把这个绑定值原样复制到节点的 `outputs` 字典里（用 `setdefault` 语义，**不覆盖**工具自己回填的同名字段）。

效果：

| 角度 | 行为 |
|---|---|
| 节点 outputs | `direction=output` 的入参的绑定值自动出现在 `$nodes.<id>.outputs.<name>`，下游节点可直接引用 |
| 工具列表 (`tool.list`) | 同一端口**镜像出现在 inputs 与 outputs 两侧**（按名去重），编辑器把它当产物端口渲染，避免描述符作者在 outputs 里再写一遍 |
| 与"工具自己产出的 outputs"冲突 | 不覆盖——真实工具输出优先（`setdefault`） |
| 可选 output 端口未绑定 | 不出现在 outputs（不写 `None`，不抛错） |

> 仅对 `PortSet.inputs` 内的端口有意义；`PortSet.outputs` 内的端口本身就总是"输出方向"，`direction` 字段对它们没有额外效果。

示例（`examples/tools/android/apktool.json` 的 `decode` 操作）：

```json
{
  "name": "decode",
  "inputs": [
    {"name": "apk_path", "type": {"base": "file", "subtype": "apk"}, "required": true},
    {"name": "output_dir", "type": {"base": "directory"}, "required": true,
     "direction": "output", "description": "Directory to write the decoded tree to."}
  ],
  "outputs": [],
  "args_map": ["d", { "param": "apk_path" }, "-o", { "param": "output_dir" }]
}
```

下游节点引用：`$nodes.decompile.outputs.output_dir` → 直接拿到 `output_dir` 的绑定值，无需把 `output_dir` 再写到 outputs 数组里。

## 4. 类型系统 TypeAnnotation

**文件**：`cli/app/protocol/types.py`

两层类型模型：

```python
class BaseType(Enum):
    FILE = "file"
    DIRECTORY = "directory"
    TEXT = "text"
    NUMBER = "number"
    BOOLEAN = "boolean"
    JSON = "json"

@dataclass(frozen=True)
class TypeAnnotation:
    base: BaseType                  # 基础类型
    subtype: Optional[str] = None   # 领域标注，仅建议性（advisory），如 "apk"、"aab"
```

关键约定：

- `subtype` 必须匹配 `^[a-z][a-z0-9_]*$`，**引擎完全忽略它做兼容性判断**；
- 兼容性 `TypeAnnotation.is_compatible(source, target)` **只看 base**：`source.base == target.base` 即兼容。

### 4.1 端口在 JSON 中的序列化

`Port.to_dict()` 把 `TypeAnnotation` 内联为 `{"base": <enum值>, "subtype": <str|None>}`，并始终输出 `options`/`multi`/`direction` 三个字段（默认值 `[]` / `False` / `"input"`），保持 wire shape 稳定。`from_dict` 对缺失的这三个字段回退默认值，所以**老工作流 JSON（没有这三个字段）能无损反序列化**。

## 5. 工作流 JSON 示例

### 5.1 download-install：内置工具 + 描述符工具混排

**文件**：`examples/workflows/android/download-install.json`（已迁至 `examples/`，改经导入使用）

```json
{
  "name": "download-install",
  "version": "1.0",
  "description": "Download an APK from a URL and install it on a device",
  "inputs": [
    {"name": "url", "type": {"base": "text"}, "required": true, "description": "URL to download the APK from"},
    {"name": "device_id", "type": {"base": "text"}, "required": true, "description": "ADB device ID to install to"}
  ],
  "outputs": [
    {"name": "path", "type": {"base": "file"}, "required": true, "description": "Path to the downloaded APK"}
  ],
  "nodes": [
    {
      "id": "download",
      "tool": "net.download",
      "params": {"url": "$inputs.url", "dest": "downloaded.apk"},
      "next": "install"
    },
    {
      "id": "install",
      "tool": "adb",
      "params": {"args": ["install", "-r", "$nodes.download.outputs.path"]},
      "next": null,
      "on_failure": "fail"
    }
  ]
}
```

注意两个节点的**不同参数形态**：

- `net.download` 是内置原子工具，参数按**命名端口**提供（`url`、`dest`）；
- `adb` 是描述符命令工具，参数是 `params.args`（命令行参数列表），且直接引用了上一节点输出 `$nodes.download.outputs.path`。

## 6. 工作流 Workflow 与任务定义 TaskDefinition

### 6.1 存储：FileWorkflowStore

**文件**：`cli/app/workflow/store.py`（生成 id 的规则在 `cli/app/ids.py`）

- 抽象接口 `WorkflowStore`（`@abstractmethod`：`save` / `load_with_meta` / `load` / `list` / `delete` / `exists`；`resolve` / `find_id_by_name` / `path_for_id` 等按 id 或名字解析的便利方法由 `FileWorkflowStore` 提供），为将来替换 SQLite 存储留口；
- `FileWorkflowStore`：**每份工作流一个文件 `<id>.json`**，存放在**可写目录**；
- 目录解析：`BT_WORKFLOWS_DIR` 环境变量（旧的 `BT_TEMPLATES_DIR` 仍会读，仅作兼容）→ 回退 `<output_dir>/workflows`（`get_output_dir()` 返回可写路径）；构造时 `os.makedirs(exist_ok=True)`；
  **旧目录收养**：只有走**默认**目录时才发生——把 `<output_dir>/templates/` 里的 `*.json` **移动**（`os.replace`）进 `workflows/`，目标已存在则不动，编完后旧目录空则删掉。显式传目录（构造参数或 `BT_WORKFLOWS_DIR`）时**绝不**伸手去碰旧路径。
- `WorkflowInfo`（`list` 返回）：`id`、`name`、`description`、`created_at`、`updated_at`、`tags`、`node_count`。

**id 身份（2026-09-30）**：文件名 stem **就是** id——`wf-` + 12 位小写十六进制（48 bit），`cli/app/ids.py::new_workflow_id()` 生成。文件里**不再冗余存一个 `id` 字段**，所以两者不可能漂移。要点：

| 主题 | 规则 |
|---|---|
| 生成的 id | `wf-<12 hex>`；路径 `<output_dir>/workflows/wf-3f9a2b1c4d5e.json` |
| 显示名 | **自由文本**：任意语言/标点、`/`、`:`、emoji 都可以，**可以重复**；存在文件内部，不再是文件名、也不再是身份 |
| 分配 | `save` 不传 `id` = **新建**（后端分配）；传 `id` = **覆盖那一份** |
| 改名 | 传**同一个 id** + 新 name：文件名不变，所以任务绑定与 `flow.foreach` / `flow.branch` 的子工作流引用**不会断** |
| 复制 | 不传 id 保存同一份定义 = 新工作流，原件不动 |
| 引用解析顺序 | `id` → 精确 `name` → 忽略大小写的 `name` → 受保护的"stem 即名字"兜底（`is_plain_stem` 拒绝分隔符与 `..`）；同时传 `id` 与 `name` 时 **id 优先** |
| 重名 | 按名字查命中多份时抛 `AmbiguousWorkflowNameError`（**响亮报错，不猜**）；按 id 引用永远唯一 |
| 导出 | 导出的是**纯 `WorkflowDefinition`**，不含 id → 导入到别的机器仍可移植 |
| 导入（`workflow.import_path`） | 按**显示名**匹配：唯一命中 → 覆盖并**保留原 id**（可重复导入、幂等）；无命中 → 新 id；**重名歧义 → 导入成一份新工作流**（新 id；这是唯一不会覆盖错文件的答案，报告里仍记 `imported`）；文件名 stem 与定义名不同时报告里给 `renamed_from` |
| 路径安全 | `save` 只接受 id 形状的值建路径（`id_file_path` 先过正则）；名字**不进路径**，所以不再需要"名称不得含 `/`"这类校验 |

**迁移（一次性、幂等、永不致命）**：构造时扫描目录，把旧 `<中文名>.json` 改名为 `<id>.json`。工作流的显示名本来就在文件里的 `definition.name`，所以**只改文件名、不重写内容**；无法解析的文件**原地不动**（仍可靠 stem 兜底引用），分配不到 id、改名失败都只记日志，不影响任何读写。

**文件格式（wrapped）**：

```json
{
  "definition": { "...WorkflowDefinition.to_dict()..." },
  "created_at": "2026-08-03T12:00:00.000000",
  "updated_at": "2026-08-03T12:00:00.000000",
  "description": "...",
  "tags": ["android", "install"]
}
```

> **为什么必须可写目录（Oracle finding #2）**：打包后 `cli/` 树被 `electron-builder` 拷到 `process.resourcesPath`（`extraResources`，见 `package.json`），是**只读**的，用户工作流必须存于其外的可写目录。外部化后不再有任何随包工作流，该结论依旧成立（不依赖预置内容）。`load` 同时接受 wrapped 格式与裸定义（无 `definition` 键时整文件即定义）；**裸定义加载就是导入格式**（`examples/` 中的工作流 JSON 即以此方式导入）；`list` 对损坏/非法文件跳过不崩溃。

> **已知取舍**：文件名不再能被人一眼认出（`apk-audit.json` → `wf-3f9a2b1c4d5e.json`）。换来的是一份中文名工作流不再产生中文文件名、改名不再断引用、同名不再互相覆盖。

### 6.2 对外 API：workflow_handler

**文件**：`cli/app/handlers/workflow_handler.py`，经 `API_MAP` 自动注册，走 `call-backend-api` 通道。整个工作流领域收口在这一个 handler（原先分开的 `template_handler.py` 已删除）：

| 方法 | 行为 |
|------|------|
| `workflow.save` | 持久化一个 `WorkflowDefinition`（带 `description`、`tags`）：`{name, definition, ...}` + 可选 `id`；不传 `id` 新建、传 `id` 覆盖；返回 `{id, name, ...}` |
| `workflow.load` | 按 `id` 或 `name` 加载为 JSON dict，返回 `{id, definition, description, tags, created_at, updated_at}`；不存在抛 `ToolException("workflow not found: ...")` |
| `workflow.list` | 列出所有工作流元信息（id/name/description/时间戳/tags/node_count），按名排序 |
| `workflow.delete` | 按 `id` 或 `name` 删除；不存在抛 `ToolException` |
| `workflow.validate` | 校验一份定义（`definition`，或按 `id` / `name` 取已保存的），不执行 |
| `workflow.import_path` | 从文件或目录导入（`{path}`），返回逐条报告；按显示名幂等（见上表） |
| `workflow.execute` | `@streaming`：**四种互斥入参，优先级 `id` > `name` > `definition` > `path`**（外加 `inputs` / `task_id` / `work_dir`）；经 `stream-event` 推送节点/终止事件，返回 `{success, outputs, node_results, error}` |

存储为进程级懒加载单例 `FileWorkflowStore`（首次使用才构造，避免 import 时的文件系统副作用）。

### 6.3 任务定义 TaskDefinition

**文件**：`cli/app/task/store.py`（`FileTaskStore`）+ `cli/app/handlers/task_def_handler.py`（`task.*`）；文件名 stem 是 `tk-<12 hex>`（`app.ids.new_task_id()`），规则与工作流**完全一致**（名字自由且可重复、id 才是身份、旧 `<name>.json` 一次性迁移并把旧 stem 写回 `name`）。

**任务定义 = 绑定的工作流 + 一套保存的入参 + 可选工作目录**。它与相邻两者的区别是数据模型的核心，别混：

| 概念 | 存什么 | 生命周期 |
|---|---|---|
| **工作流**（`app.workflow.store`） | 工作流图**与入参声明**（`Port`），**从不存运行用到的值** | 用户显式增删 |
| **任务定义**（`app.task.store`） | 工作流的 **id**（`workflow_id`，另留显示名 `workflow` 供展示）+ 入参快照 + 可选 `work_dir` | 用户显式增删，**永不自动裁剪**；可挂多个任务指向同一工作流 |
| **运行记录**（`app.history.store`） | 一次执行的输入快照、逐节点结果、耗时、错误、`run_dir`、`task_def_id`、`workflow_id` | 每次运行写一条，**按 `history.max_runs` / `max_bytes` 自动裁剪** |

**文件格式**（一任务一文件，`<id>.json`）：

```json
{
  "name": "nightly-audit",
  "workflow": "apk-audit",
  "workflow_id": "wf-3f9a2b1c4d5e",
  "inputs": {"apk_path": "D:/x.apk", "deep": true},
  "work_dir": "",
  "description": "每晚审计",
  "created_at": "2026-09-28T12:00:00.000000",
  "updated_at": "2026-09-28T12:00:00.000000"
}
```

`workflow_id` 是**绑定身份**（改名不断链、重名不指错），`workflow` 只是保存时的显示名快照（列表与历史里展示用）。老任务只有 `workflow` 时，构造 `FileTaskStore` 会用 `backfill_workflow_ids` 按名字解析一次、把 id 补进文件（一次性、幂等；名字歧义时**宁可保留按名绑定**也不猜，失败不致命）。

**迁移（与工作流同一套，但多一步）**：旧任务的**显示名是从文件名推出来的、文件里根本没存**，所以先看文件里有没有 `name`：有 → 纯 `os.replace` 改名（不重写内容）；没有 → 先把旧 stem 写进 `name` 再改名，否则改名会毁掉名字的唯一副本。文件里连 `name` 都读不出来时（老格式兜底）`name` 回退成文件 stem。

- **目录解析**：`BT_TASK_DEFS_DIR` → 回退 `<output_dir>/task_defs`（`get_output_dir()` 返回可写路径）；构造时 `os.makedirs(exist_ok=True)`。
  ⚠️ **刻意不放 `<output>/tasks/`**：那是 `get_tasks_root()` 的**每次运行工作目录**（`tasks.clear` 会整棵清掉，`task.delete_task_dir {task_id}` 按 `task_id` 删子目录也会误伤），而任务定义是用户数据。
- **路径安全**：`FileTaskStore` 只接受 `tk-<12 hex>` 形状的值建路径（`app.ids.id_file_path`）；任务名**不进路径**，因此不再有"名字不得含分隔符/`..`"的限制。
- **`inputs` 是不透明快照**：原样存取，store **从不解释**值；后端只校验"是对象"，端口级校验留给运行期的 `PortSet.validate_inputs`（与引擎口径一致），必填校验由表单层负责。
- **损坏容忍**：`list()` 跳过无法解析/非法文档的文件并记 warning；`load()` 抛 `ValueError`；**缺 `workflow` 或缺非空 `workflow` 视为损坏**（这种任务永远跑不起来）。可选字段（`inputs` / `work_dir` / `description` / 时间戳）缺失即回退空值。
- **覆盖语义**：`created_at` 首次保存时写入、覆盖时保留；`updated_at` 每次保存刷新；`inputs` **整体替换**（不与旧值合并）。**覆盖必须带 `id`**——只给 `name` 是"新建一份同名任务"（名字可以重复，两份都留着）。
- **悬挂引用**：绑定按 `workflow_id` 引用工作流，因此**工作流改名不会断链**；工作流被**删除**后任务仍在（**不级联删用户数据**）。`task.list` / `task.get` 通过工作流库的 id 是否还存在计算 `workflow_exists`；`task.execute` 在此时抛 `workflow not found: ...`。工作流声明后来变化时，以**当前**工作流为准，不自动改写已保存的 `inputs`。

**对外 API**（`task_def_handler.py`，`API_MAP` 自动注册）。除 `task.list` 外全部接受 `id` 或 `name`（**id 优先**）：

| 方法 | 行为 |
|------|------|
| `task.list` | 列出所有任务定义（按名排序）：`id` / `name` / `workflow` / `workflow_id` / `workflow_exists` / `inputs` / `input_count` / `has_work_dir` / `description` / `created_at` / `updated_at` |
| `task.get` | 单条：`{task, workflow_exists}`；不存在抛错 |
| `task.save` | 创建/覆盖：`{name, workflow_id?, workflow?, inputs?, work_dir?, description?}` + 可选 `id`；校验工作流**已存在**、`inputs` 是对象；返回 `{id, saved, name}` |
| `task.delete` | 删除任务定义，并**一并删除该任务各次运行的整个产物目录**（按记录的 `task_def_id` 匹配，老记录无 id 时回退 `task_name`；`run_dir` 取历史摘要里的值、缺失则按 `run_id` 重推；best-effort、失败只记日志）；**运行记录保留**（历史有自己的保留策略与"清空记录"入口）；不存在抛错 |
| `task.execute` | `@streaming`：按 `workflow_id`（缺则回退 `workflow` 名）加载工作流并运行；入参 `{**saved_inputs, **request.inputs}`（浅合并，请求覆盖）；`work_dir` = 请求 > 保存值 > 本次运行产物目录；历史记录带 `task_name` / `task_def_id` / `workflow_id`，而 `source` 仍是**工作流名**；运行**不回写**保存的入参 |

> ⚠️ **命名**：`task.*` 现在指**任务定义**；`task.read_log` / `task.append_log` / `task.delete_task_dir` / `task.delete_output` 里的 `task_id` 是**一次运行的身份**（沿用旧名，见 08 §6 的命名遗留说明），与任务定义的 `id`（`tk-…`）不是一回事。原先由 `task.list` 返回的"在跑运行列表"已改名 **`run.list`**（`{runs: [...]}`）。
>
> 运行身份（`task_id` / `run_id`）**不从任务名派生**：同一任务可并发运行，各有独立 run 目录与历史记录。

### 7.3 执行：DescriptorTool 与引擎

- `DescriptorTool` 提供统一的工具接口表面（`name`、`is_valid`、`version`、`tool_path`、`execute`），使注册表能统一管理描述符工具与内置/插件工具（`BuiltinTool` 亦镜像该表面）；
- `is_valid` = 所有 env_dep 可解析 + 二进制存在 + validate 命令通过；`version` 用 `version_regex` 从输出抓取；
- 命令构造：`binary` 直接用工具路径作前缀；`java_jar` 用 `[java, "-jar", tool_path]`；`python_script`/`node_script` 用解释器前缀（`_INTERPRETER_DEP_BY_TYPE`），`shell_script` 同 binary；已带前缀的命令不重复加前缀；
- 工作流引擎（`cli/app/workflow/engine.py`）对描述符/内置工具按命令列表契约执行：`params["args"]` 解析后作为命令列表传给 `tool.execute(command, context)`，返回的 `{success, returncode, stdout, stderr}` 归一化为节点输出，非零退出码/显式失败会触发 `on_failure` 语义。
- **产物端口 surface**：操作里 `direction=output` 的入参（典型如 `--out <path>`），其绑定值会被 `_execute_operation` 复制到节点 outputs 字典（`setdefault`，不覆盖工具自填的同名字段），让下游 `$nodes.<id>.outputs.<name>` 引用无需再在 outputs 侧重复声明。详见 [3.1](#31-产物端口direction-output)。
- `Operation` 支持 `timeout`（秒，None=默认 600）与 `cwd`（静态路径 / `$workdir` / `$inputs.<key>`，None=work_dir；`$inputs.<key>` 缺失时 warn 并回退 work_dir），见 `descriptor_tool.py` 的 `_resolve_operation_cwd`。

## 8. 表达式引擎（供节点参数使用）

**文件**：`cli/app/workflow/expression.py`

节点参数里的 `$` 引用在运行时解析（无条件/循环/算术，不用 eval/exec/getattr）。有**两种写法**：

**① 整值表达式**：整个字符串就是一个表达式，解析结果**保留原类型**（数字仍是数字、dict 仍是 dict），用于绑定到类型化端口。

| 根 | 示例 | 含义 |
|----|------|------|
| `$inputs.<key>` | `$inputs.url` | 工作流级输入 |
| `$nodes.<id>.outputs.<port>` | `$nodes.download.outputs.path` | 上游节点输出 |
| `$nodes.<id>.params.<key>` | `$nodes.write.params.content` | 上游节点已解析参数 |
| `$env.<name>` | `$env.PATH` | 环境变量。**来源是后端进程的环境变量**（`ExecutionContext.env`，由 `app/workflow/runner.py` 与 `cli/cli.py` 注入 `os.environ`）；`env` 为空字典时任何 `$env.*` 都会以 "missing key" 失败 |
| `$workdir` | `$workdir` | 工作目录（解析规则见 2.1 节） |
| `$rundir` | `${rundir}/report.txt` | 本次运行的产物目录（`<output_dir>/runs/<run_id>`，见 2.1 节） |

**② 插值**：字符串里出现 `${...}` 时逐个替换。整串**恰好是一个** `${...}`（前后无文字）时同样保留原类型；混在文字中时按文本渲染（字符串原样、布尔为 `true`/`false`、`null` 为空串、对象/数组为紧凑 JSON）：

```json
"message": "auditing ${inputs.target}, need >= ${inputs.min_matches} (found ${nodes.scan.outputs.count})"
```

两种写法都支持管道变换（固定集合）：`basename`、`dirname`、`default:<value>`。

> 转义：`$${HOME}` 输出字面量 `${HOME}`（`exec.shell` 之类的命令参数里写 shell 变量时要用它）；`$$foo` 输出字面量 `$foo`。
> 陷阱：以 `$` 开头但后面还跟着文字的整值写法（如 `"$inputs.x done"`）会报错并提示改用 `${...}`——不带 `${}` 的字符串是**纯字面量**，不会做任何替换。

安全模型：固定根分发表 + 拒绝 `^_`（dunder/私有）路径组件 + 未知根/未知管道名/未闭合的 `${` 直接抛 `ExpressionError`。

> **前端同一套规则**：编辑器在参数旁内联校验表达式（`src/renderer/components/workflow/expressionBinding.ts`：未知根 / 私有段 / 未知管道 / 路径段数不符 / 未闭合插值 = 阻止保存；端口与参数键不存在、base 类型不匹配、整值与插值混用 = 警告）。并且**候选只列上游节点**——`$nodes.<id>` 是链序累积的，引用下游必然在运行时 "missing node"。

## 9. 环境描述符与解析

### 9.1 EnvironmentDescriptor

**文件**：`cli/app/env/descriptor.py`

```python
@dataclass
class EnvironmentDescriptor:
    name: str                   # snake_case 标识，如 "java"
    display_name: str           # 如 "Java Runtime"
    type: str                   # jre | python | node | custom
    binary: str                 # 相对环境根目录，如 "bin/java.exe"
    version_cmd: List[str]      # 版本探测参数，如 ["-version"]
    version_regex: str          # 提取版本的正则（恰好一个捕获组）
    search_paths: List[str]     # 相对 runtime/ 的搜索目录；空 = 未捆绑，需用户提供
    importable: bool = True     # 是否允许用户导入自定义实例
    env_var_override: Optional[str] = None   # 直接指向二进制的环境变量名，如 "BT_JAVA_BIN"
```

必填字段（缺则 `from_dict` 抛错）：`name`、`display_name`、`type`、`binary`、`version_cmd`、`version_regex`、`search_paths`。

**真实示例**：`cli/registry/environments/java.json`

```json
{
  "name": "java",
  "display_name": "Java Runtime",
  "type": "jre",
  "binary": "bin/java.exe",
  "version_cmd": ["-version"],
  "version_regex": "version \"([^\"]+)\"",
  "search_paths": ["jre"],
  "importable": true,
  "env_var_override": "BT_JAVA_BIN"
}
```

### 9.2 EnvironmentRegistry 五级解析

**文件**：`cli/app/env/registry.py`，默认描述符目录 `cli/registry/environments/`（java、python、node 三个）。

`resolve(name)` 按顺序找二进制，**先命中先得**，结果缓存至 `refresh()`：

1. **env_var_override**：描述符声明的环境变量（如 `BT_JAVA_BIN`）存在且指向的文件存在；
2. **路径覆盖 `env_paths`**（WP3 #13）：`<output>/registry/overrides.json` 的 `env_paths` 段按环境名记录用户指定路径，由 `env.set_path` / `env.reset_path` 读写（与 tool `custom_paths` 同文件、同风格）。路径是文件 → 直接使用；是目录 → 依次尝试 `<dir>/<binary>`、`<dir>/bin/<basename(binary)>`；
3. **内置运行时**：`runtime/<search_path>/<binary>`（如 `runtime/jre/bin/java.exe`）；
4. **系统环境变量**：按类型探测（jre → `JAVA_HOME`/`JRE_HOME`；python → `PYTHONHOME`；node → `NODE_HOME`/`NODEJS_HOME`；custom 无映射），尝试 `<root>/<binary>` 与 `<root>/bin/<binary>` 两种布局；
5. **PATH**：用二进制文件名 `shutil.which(...)`。

⚠️ `_find_binary` 在热路径上且结果被缓存 —— 任何覆盖变更（`set_path` / `reset_path` / 重新导入描述符）必须调用 `registry.refresh()` 才会生效。

版本探测：跑 `[binary] + version_cmd`，15 秒超时，stdout+stderr 合并后按 `version_regex` 提取；探测退出码非 0 则 `is_valid=False`。`resolve` 对未知环境名**不抛异常**，返回空的无效 `ResolvedEnvironment`。

## 10. 已实现 / 延后

### 10.1 【已完成】单选 / 多选入参

`Port` 已增加两个字段，编辑器暴露**八种入参类型**：

- `options: List[str]`：可选项列表（单选下拉）；
- `multi: bool`：是否多选。

编辑器已暴露的类型全集：字符串（text）、文件（file）、文件夹（directory）、布尔（boolean）、数字（number）、JSON（json）、单选列表、多选列表。**动态数据源绑定（如设备列表）已明确延后**（见路线图），所以选项现阶段是静态列表。

### 10.2 【已完成】统一「操作」模型

迁移结果：

| 维度 | 现状（已实现） |
|------|----------|
| 内置原子工具（`file.read`、`net.download`、`exec.shell`、`exec.code` 等，`cli/app/tools/builtin/`，`BuiltinTool` 见 `cli/app/tools/builtin/base.py`） | 已按"声明 `ports` + 类型化 `execute(inputs, context)`"实现，保持不变，作为天然范本 |
| 描述符命令工具（apktool、adb 等，现位于 `examples/tools/android/`） | 已升级为 **operations**：工具 = JSON（元信息 + env_deps + validate/version + `operations[]`），每个 operation 含类型化 inputs/outputs 与 args 映射（T3）；APK 链路工具（apktool / adb / bundletool）已迁移为范例（T5） |
| 节点 | 节点可引用 `tool + operation`，并**绑定类型化输入**，不再裸写命令参数（T4）；引擎按 operation 校验输入、拼命令、返回类型化输出（`engine.py` 的 `_execute_operation_tool`） |
| 脚本 | 已统一为 `*_script` 类型 + env_deps，与普通工具同构（T17，如 `examples/tools/android/apk-audit.json`） |

一句话概括：**"裸写 CLI 参数"已升级为"声明操作 + 绑定类型化输入"**，编辑器可对每个节点做类型化校验与表单化配置，脚本（`*_script`）也归入同一工具模型。

### 10.3 【延后】`flow.foreach` / `flow.branch` 的端口名仍叫 `template`

词汇上"模板"已全部改称"工作流"（模块、方法名、CLI、文档），但**组合类节点的端口名**仍是 `template` 系列——它们是**已保存工作流图里的字段名**，改名会让所有旧图失效（`WorkflowDefinition.from_dict` 找不到必填入参直接抛错）。确切归属（`cli/app/tools/builtin/flow_tools.py`）：

| 工具 | 端口 | 方向 |
|---|---|---|
| `flow.foreach` | `template` | 入参（每个 item 要跑的工作流，按 id 或名称解析） |
| `flow.branch` | `true_template` / `false_template` | 入参（条件真/假时要跑的工作流） |
| `flow.branch` | `template` | **出参**（实际跑了哪一个，原样回显；no-op 时空串） |

注意 `flow.branch` 的入参与出参里各有一个不同的 `template` 语义（一个"要跑哪个"、一个"跑了哪个"），改名时别一起盲改。改名推迟到有迁移/别名层时再做，见 [09-后端缺口修复与优化方案 §4e WP11](./09-后端缺口修复与优化方案.md)。**在此之前新代码不要按端口名推断语义**：端口叫 `template`，值是一份工作流的 id 或名称。
