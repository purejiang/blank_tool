# 02 系统架构

> 本文档描述 Blank Tool 的三进程架构、IPC 通信、后端自动发现机制、无头 CLI、路径解析与环境配置。产品定位见 [01-产品概述.md](./01-产品概述.md)，数据模型见 [03-数据模型.md](./03-数据模型.md)。

## 1. 三进程架构总览

Blank Tool 是标准的 Electron 三进程桌面应用：

```
┌───────────────────────────────┐
│ Renderer（渲染进程）          │
│  Vue 3 + Pinia + Vue Router   │
│  + Naive UI（src/renderer/）  │
│  window.electronAPI.*         │
└──────────────┬────────────────┘
               │ contextBridge（src/preload/index.ts）
               │ 通过 ipcRenderer.invoke / ipcRenderer.on
┌──────────────▼────────────────┐
│ Main（主进程）                 │
│  src/main/                    │
│  ├─ ipc/            IPC handlers│
│  ├─ python/         Python 子进程│
│  │                管理 + 路径解析│
│  ├─ stores/         electron-store│
│  └─ window/updater/ 窗口/更新     │
└──────────────┬────────────────┘
               │ spawn Python 子进程
               │ stdin/stdout JSON-RPC（一行一个 JSON）
┌──────────────▼────────────────┐
│ Python Backend（cli/）    │
│  main.py → ApiHandler         │
│  app/handlers/*.py (API_MAP)  │
│  app/workflow/ 工作流引擎      │
│  app/tools/    工具注册表      │
│  app/env/      环境注册表      │
└───────────────────────────────┘
```

三者的职责边界：

| 进程 | 目录 | 职责 |
|------|------|------|
| Renderer | `src/renderer/` | UI、页面状态（Pinia）、通过 `window.electronAPI` 调用能力、订阅事件 |
| Main | `src/main/` | 生命周期、窗口、IPC 路由、Python 进程拉起与保活、应用配置（electron-store）、自动更新 |
| Python Backend | `cli/` | 真正的业务能力：工作流引擎、模板存储、环境解析、工具/环境描述符注册（Android 专属工具类与 handler 已删除，T23） |

### 1.1 数据流（一次普通请求）

1. Renderer 调用 `window.electronAPI.callBackendAPI({ id, method, params })`；
2. preload（`src/preload/index.ts`）经 `contextBridge` 暴露 `electronAPI`，内部走 `ipcRenderer.invoke('call-backend-api', request)`；
3. Main 进程的 `setupCommandHandlers`（`src/main/ipc/commandHandlers.ts`）收到请求，把 `{id, method, params}` 以一行 JSON 写入 Python 子进程的 stdin，并在 `requestCallbacks` Map 里登记回调；
4. Python `cli/main.py` 读取 stdin 行，交 `ApiHandler.handle_request` 分派到对应 handler；
5. handler 返回后，`send_json` 以一行 JSON 写回 stdout；
6. Main 进程的 stdout 监听按 `id` 匹配 `requestCallbacks`，resolve 给 Renderer 的 invoke Promise。

**超时**：`setupCommandHandlers` 的 `requestTimeout` 默认 **300000ms（5 分钟）**，不是 30 秒。长任务（反编译、签名）依赖这个默认值；渲染层可在设置页调整请求超时。

## 2. IPC 通道与协议

### 2.1 单一后端调用通道

所有"调用后端能力"的请求都走**一个** IPC 通道，方法名就是 JSON-RPC 的 method 字段：

| 通道 | 方向 | 用途 |
|------|------|------|
| `call-backend-api` | renderer → main | 通用后端调用，请求形如 `{id, method, params}`，method 如 `template.execute`、`workflow.execute` |
| `stream-event` | main → renderer | 流式响应转发（logcat、下载进度、工作流节点事件等） |
| `get-app-config` / `set-app-config` / ... | renderer → main | 应用配置读写（详见第 6 节） |
| `device-change`、`logcat-output` 等 | main → renderer | 后端事件广播 |

通道名全部集中在 `src/shared/ipc/channels.ts`。**改通道名必须同步 `tests/shared-contracts.test.mjs`**，否则契约测试会失败（见 `AGENTS.md`）。

### 2.2 流式响应（streaming）

后端用 `@streaming` 装饰器（`cli/app/common/decorators.py`）标记的 handler，会在**独立线程**运行、多次回包：

- 每次回包形如 `{"id", "result", "stream_id", "finished": false}`；
- 线程结束时发送 `{"id", "stream_id", "finished": true}`；
- `ApiHandler.stream_handler`（`cli/app/api_handler.py`）负责建线程、注册到 `TaskManager`（支持取消）并转发事件；
- Main 进程 `commandHandlers.ts` 按 `response.finished` 区分流式与普通响应：`finished === false` 的包通过 `stream-event`（或 logcat 专用通道）转发给发起请求的 `sender`，并 resolve 首个包给 Renderer。

装饰器组合约定：`@streaming` 必须在最外层（`@streaming` + `@logs_errors(...)`），`logs_errors` 只记录非受控异常并继续抛出。

## 3. Python 后端

### 3.1 入口与请求循环

`cli/main.py`：

- `bootstrap()`：加载 `.env`（`load_dotenv`）与 `server.config.json`（`load_server_config`），初始化日志（`BT_LOG_DIR`，默认 `cli/logs/`）；
- 主循环逐行读 stdin，用 `ThreadPoolExecutor(max_workers=4)` 并发处理；
- 支持 stdin EOF 后重连（最多 10 次）、SIGTERM/SIGINT 优雅退出（先排空在途请求，10 秒宽限）；
- 注入 `health` handler（返回 `status: ok` 与 uptime）。

### 3.2 请求分派：ApiHandler 与自动发现

`cli/app/api_handler.py` 的 `ApiHandler._load_handlers()` 用 `pkgutil.walk_packages` 扫描 `app.handlers` 包下所有模块，把每个模块导出的 `API_MAP` 字典并入 `api_map`。**新增 handler 不需要改注册表**，只要：

1. 在 `cli/app/handlers/` 下新建模块；
2. 导出 `API_MAP = {"方法名": 函数}`；
3. 函数签名 `(params, stream_handler) -> dict`。

现有 handler 一览（`cli/app/handlers/`）：

| 模块 | 主要方法 |
|------|----------|
| `app_handler.py` | 应用/构建/系统信息（`app.info`、`build.info`、`system.info`） |
| `cache_handler.py` | 缓存/存储信息与清理（`cache.get_info`、`output.clear`、`tasks.clear`、`logs.clear`、`storage.clear`） |
| `env_handler.py` | 环境描述符 CRUD（`env.list`、`env.add`、`env.delete`） |
| `log_handler.py` | 日志读取（`logs.tail`） |
| `task_handler.py` | **运行身份域**（`task_id` = 一次运行的身份）：`run.list`（在跑的运行）、`task.read_log`、`task.delete_output`、`task.delete_task_dir`、`request.cancel` |
| `task_def_handler.py` | **任务定义域**（工作流 + 保存的入参，`<output>/task_defs/`）：`task.list`、`task.get`、`task.save`、`task.delete`、`task.execute`（WP7 新增，2026-09-28） |
| `template_handler.py` | `template.save/load/list/delete/execute` |
| `tool_handler.py` | 工具描述符管理（`tool.get_tools`、`tool.add`、`tool.delete`、`tool.set_custom_path`、`tool.reset_custom_path`、`tool.get_custom_paths`、`tool.set_search_mode`） |
| `workflow_handler.py` | `workflow.execute`、`workflow.validate`、`workflow.list_tools`、`workflow.list_envs` |

> 原 `apk_handler.py`、`adb_handler.py`、`aab_handler.py`、`download_handler.py`、`install_handler.py` 等 Android 专属 handler 及其契约测试已**删除**（T23），表中为全部现存 handler。

### 3.3 工具发现（描述符 + 内置/插件）

- **描述符工具**：`ToolManager`（`cli/app/tools/tool_manager.py`）扫描描述符目录 `cli/registry/tools/*.json`（内置）+ `<output>/registry/tools/*.json`（用户覆盖层，同名优先），实例化为 `DescriptorTool`。代码类（`BaseTool` 子类）目录扫描已移除；
- **内置/插件工具**：`BuiltinTool`（`cli/app/tools/builtin/base.py`）由 shipped-native 插件经 `register_plugin_tool` 显式注册（`cli/app/plugins/builtin/*` 包装 `cli/app/tools/builtin/*`）。核心清单 `SHIPPED_MANIFEST`（`file`/`text`/`exec`/`flow`/`workflow`）总是加载，扩展清单 `EXTENDED_MANIFEST`（`file_ext`/`dir`/`archive`/`text_ext`/`net`/`exec_ext`）按 `server.config.json` 的 `tools.atomic_extensions` 启用；
- 旧 `_BUILTIN_TOOLS` 字典（`engine.py`）与 `BaseTool`/`CommandTool` 类层级（`base_tool.py`）已删除，内置工具统一走 `ToolManager` 注册表。

工具发现相关：环境注册表 `EnvironmentRegistry` 扫描 `cli/registry/environments/*.json`（java、python、node）。

### 3.4 插件系统（manifest 驱动）

插件经清单（manifest）驱动的加载器 `cli/app/plugins/loader.py` 加载，入口 `apply(ctx, config)`（可选 `unmount(ctx)`）。清单条目为 `{module, kind, path?, config?}`，`kind` 取 `"shipped-native"` / `"native"`。来源依次：`SHIPPED_MANIFEST`（5 个核心内置）→ 按 `tools.atomic_extensions` 启用的 `EXTENDED_MANIFEST`（6 个扩展内置）→ 用户插件（`server.config.json` `plugins` 段，其次 `<output>/plugins.json`）。

## 4. 无头 CLI（cli/cli.py）

后端除 stdin JSON-RPC 模式外，还有一个**独立于 Electron 应用**的无头命令行入口，**不走 stdin JSON-RPC、没有流式 IPC**。内置工具与工作流都能以命令方式单独调用，适合自检、调试与 CI：

```bash
python cli/cli.py run <workflow.json|template-name> --input key=value   # 执行工作流（可加 --json / --task-id）
python cli/cli.py run --task <task-name> --input key=value   # 用「任务定义」的绑定工作流 + 保存入参执行（--input 覆盖保存值）
python cli/cli.py list-tools        # 列出全部工具（描述符 + 内置/插件工具）
python cli/cli.py list-envs         # 列出已解析环境（java/python/node）
python cli/cli.py validate <workflow.json>   # 静态校验工作流
python cli/cli.py tool <name> --input key=value   # 单独调用某个工具/操作（T18，带参/出参，不依赖 Electron）
python cli/cli.py list-templates    # 列出已保存模板
python cli/cli.py list-tasks        # 列出已保存任务定义（每行 `名称<TAB>绑定的工作流`）
python cli/cli.py import-pack <dir>       # 批量导入目录中的工具描述符（领域包，两阶段校验）
python cli/cli.py import-templates <path> # 批量导入工作流 JSON（文件或目录）到模板库
python cli/cli.py history [run_id] [--limit N]  # 查看运行历史（列表或单条完整记录）
```

> `run` 的位置参数 `target` 与 `--task` **互斥**；两者都省略是一次用法错误（退出码 2，与其它 argparse 用法错误一致），未知任务/未知工作流退出 1。任务定义（`app.task.store`）与模板、运行记录是三份不同数据，详见 [03-数据模型](./03-数据模型.md#63-任务定义-taskdefinition)。

### 4.1 排障记录：cli.py 从 main 复用 bootstrap

`cli/cli.py` 第 37-39 行注释说明：直接从 `main` 导入并复用 bootstrap 逻辑（`from main import bootstrap`，仅做 dotenv + server config + 日志初始化）。历史上曾因 `app/protocol/` 包与旧版单文件模块 `app/protocol.py` 同名冲突导致 `from main import bootstrap` 失败、被迫在 cli.py 里各维护一份，该问题已修复。现在 bootstrap 逻辑只有 `main.py` 一处，修改无需两处同步。

> **现状（已修复）**：`app/protocol/` 包统一导出——消息类 `BackendSuccessPayload`/`BackendErrorPayload`/`ErrorCode`（`messages.py`），类型系统 `BaseType`/`TypeAnnotation`/`Port`/`PortSet`（`types.py`）。`BackendResponse`/`BackendStreamEvent`/`BackendApiRequest`/`TypeRegistry` 等旧模型已随死代码清理移除（`api_handler` 以字典内联构造响应，不再需要这些消息类）。`import main`（`cli/main.py` → `app/api_handler.py`）导入正常，后端可正常启动，无阻塞项。

## 5. 路径解析

### 5.1 开发 vs 打包

判别逻辑集中在 `src/main/python/paths.ts` 的 `getBaseDir()`，**请勿在别处重新实现**：

```ts
export function getBaseDir(): string {
  return !app.isPackaged
    ? path.join(__dirname, '..', '..')   // dev：相对项目根
    : process.resourcesPath;              // prod：electron-builder extraResources 放置目录
}
```

- **Dev**（`!app.isPackaged`）：`cli/`、`runtime/` 相对项目根；
- **Production**（`app.isPackaged`）：相对 `process.resourcesPath`。`package.json` 的 `build.extraResources` 只把 `cli/`（排除 cache/output/logs）拷入资源目录，`runtime/` 不随包分发——已外部化：由用户本地自备（本地 `runtime/` 目录、自定义工具路径或系统 PATH）。

### 5.2 运行时 runtime/

**现状**：`runtime/` 在仓库中本就被 `.gitignore` 排除（二进制从不入仓库），也不再经 `build.extraResources` 随应用分发（`extraResources` 只有 `cli/` 条目）——**用户本地自备**：本地 `runtime/` 目录、设置页的「工具链与运行时」目录、按工具的自定义路径（`/tools`）或系统 PATH 均可。Python 运行时的默认路径是 `runtime/python/python.exe`（见 `src/shared/config/pathConfig.ts` 的 `runtimeExecutable`），外部化后 `runtime/python` 通常不存在，系统 Python 成为**实际默认**（该回退逻辑在 `src/main/python/paths.ts`）。不要假设系统 PATH 里有 `adb`/`java`，一律通过环境注册表解析（见 [03-数据模型.md](./03-数据模型.md#9-环境描述符与解析))。

> **`runtime/` 不只是"Python 在哪"**：它同时是后端解析**相对路径的工具描述符**（示例 `examples/tools/android/adb.json` 的 `"path": "adb/adb.exe"`、`apktool.json` 的 `"apktool/apktool.jar"`）与**内置环境 `search_paths`**（`cli/registry/environments/java.json` 的 `jre`、`python.json` 的 `python`）的根——本机 `runtime/` 下确实有 `aapt/ adb/ apktool/ bundletool/ jre/` 等。所以设置页那一行的作用远大于它的旧标签「运行时」；开发模式下后端还能自行回退到项目根 `runtime/`，**打包后 `runtime/` 不在包内**，相对路径的描述符工具会全部不可用，必须靠这一行指到用户自备的工具链。

> 注：`runtime/`、`cache/`、`output/` 在 `.gitignore` 中，本地缺目录时属正常；外部化后 `runtime/` 由用户自行创建或完全不用。

## 6. 环境与配置

### 6.1 主进程配置：electron-store

`src/main/stores/appStore.ts` 用 `electron-store`（文件名 `app-config`）管理应用配置：

- JSON schema 校验（`schema` 字段），带版本化迁移（`APP_CONFIG_VERSION = 8`，`MIGRATIONS` 逐版本迁移，`runConfigMigrations` 启动时执行）；
- 关键键：`app`（theme/language/autoStart/minimizeToTray）、`runtime`/`server`/`serverEntry`/`runtimeExecutable`/`rendererEntry`/`preloadCandidates`（路径配置）、`commands`（timeout/maxHistory/outputFormat）、`logs`、`language`、`theme`、`enableNotifications`、`autoDeleteOutputOnTaskRemove`；
- **`output` 与 `javaPath` 两个死键已删除**（WP10 / 缺口 #19）：它们的值从来没有任何读取方，`MIGRATIONS[7]` 会把老库里的残留 `delete` 掉（版本 7→8）。设置页也**只**支持 `runtime` / `server` 两个键（`settings.getViewModel` / `settings.resolvePaths`）。数据目录 `cache/`、`output/`、`tasks/`、`logs/` 固定为 `%LOCALAPPDATA%\blank_tool\` 下的子目录，由主进程注入 `BT_*_DIR`，不经 appConfig（**不可配置**）；
- 渲染层通过 `window.electronAPI.appConfig.*` 读写；写操作有 `isWritableConfigKey` 白名单。

### 6.2 后端配置：.env + server.config.json

后端配置由 `cli/app/env/__init__.py`（`app.env` 包）加载；纯路径助手（`resolve_path` / `get_runtime_dir` / `ROOT`）在 `cli/app/utils/paths.py`：

- `cli/.env`（实际只有 `APP_VERSION`、`PROJECT_NAME`）；
- `cli/server.config.json`（从 `server.config.example.json` 拷贝）：`env` 段里的键会写入进程环境变量，`.env` 中已存在的键优先。示例默认值：

```json
{
  "env": {
    "APP_VERSION": "1.0.1",
    "PROJECT_NAME": "blank_tool_server",
    "BT_LOG_LEVEL": "DEBUG",
    "BT_CACHE_DIR": "../cache",
    "BT_OUTPUT_DIR": "../output"
  }
}
```

**`server.config.json` 里的相对路径以 `cli/` 目录为基准**（如 `../cache`）。

### 6.3 关键环境变量（后端）

| 变量 | 用途 | 默认/回退 |
|------|------|-----------|
| `BT_RUNTIME_DIR` | 运行时（runtime/）根目录：主进程用 appStore 的 `runtime` 键解析后注入（**设置页「工具链与运行时」那一行 = 这个变量**，改后需重启后端）；后端用它解析**描述符里的相对 `path`**（如 `adb/adb.exe`、`apktool/apktool.jar`）与**内置环境的 `search_paths`**（`jre` / `python`） | `cli/runtime` → 项目根 `runtime/`（env 分支不检查是否存在） |
| `BT_CACHE_DIR` | 缓存目录（下载等） | 桌面应用：主进程注入 `%LOCALAPPDATA%\blank_tool\cache`（macOS `~/Library/Caches/blank_tool/`、Linux `~/.cache/blank_tool/`）；纯 CLI 下 `./cache`（相对 cli/） |
| `BT_OUTPUT_DIR` | 统一输出目录（`templates/`、`task_defs/`、`history/`、`runs/`、`registry/` 都在其下） | 桌面应用：主进程注入 `%LOCALAPPDATA%\blank_tool\output`；纯 CLI 下 `./output`（相对 cli/）。**不可通过设置页更改**（缺口 #19） |
| `BT_LOG_DIR` | 日志目录 | 桌面应用：主进程注入 `%LOCALAPPDATA%\blank_tool\logs`；纯 CLI 下无 → `cli/logs/` |
| `BT_LOG_LEVEL` | 日志级别 | `DEBUG` |
| `BT_TEMPLATES_DIR` | 模板可写目录 | 无 → `<output_dir>/templates` |
| `BT_TASK_DEFS_DIR` | 任务定义可写目录（工作流 + 保存的入参） | 无 → `<output_dir>/task_defs` |
| `BT_TASKS_DIR` | 任务工作目录根（**每次运行**的 scratch，不是任务定义） | 无 → `<cache_dir>/tasks` |
| `BT_JAVA_BIN` / `BT_PYTHON_BIN` / `BT_NODE_BIN` | 环境二进制直接覆盖（env_var_override） | 由环境描述符声明 |
| `APP_VERSION` / `PROJECT_NAME` | 版本与项目名 | `cli/.env` |
| `BT_SERVER_CONFIG` | server.config.json 路径 | `cli/server.config.json` |
| `BT_SEARCH_SYSTEM_TOOLS` | 是否搜索系统工具 | 关 |

## 7. 测试体系

架构上注意五套测试分别由不同运行器驱动（详见 `AGENTS.md`，最容易踩坑）：

| 命令 | 运行器 | 范围 |
|------|--------|------|
| `npm run test` | vitest | `tests/unit/**`、`tests/integration/**` |
| `pytest tests/contracts/` | pytest | 后端 handler 契约测试 |
| `pytest tests/cli/` | pytest | Python 单测（协议/端口/工具/引擎/环境/CLI） |
| `node --test tests/shared-contracts.test.mjs` | node:test | IPC 通道名与 pathConfig 字符串契约 |
| `npx playwright test` | Playwright | `tests/e2e/`（当前无 spec，`passWithNoTests` 保门禁） |

改了后端 handler 或 IPC 通道名后，必须手动跑对应的契约测试（`npm run test` 不会覆盖后两者）。
