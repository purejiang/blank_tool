# 02 系统架构

> 本文档描述 Blank Tool 的三进程架构、IPC 通信、后端自动发现机制、无头 CLI、路径解析与环境配置。产品定位见 [01-产品概述.md](./01-产品概述.md)，数据模型见 [03-数据模型.md](./03-数据模型.md)。

## 1. 三进程架构总览

Blank Tool 是标准的 Electron 三进程桌面应用：

```
┌───────────────────────────────┐
│ Renderer（渲染进程）          │
│  Vue 3 + Pinia + Vue Router   │
│  + Naive UI（src/renderer/）  │
│  window.electronAPI.*         │
└──────────────┬────────────────┘
               │ contextBridge（src/preload/index.ts）
               │ 通过 ipcRenderer.invoke / ipcRenderer.on
┌──────────────▼────────────────┐
│ Main（主进程）                 │
│  src/main/                    │
│  ├─ ipc/            IPC handlers│
│  ├─ python/         Python 子进程│
│  │                管理 + 路径解析│
│  ├─ stores/         electron-store│
│  └─ window/updater/ 窗口/更新     │
└──────────────┬────────────────┘
               │ spawn Python 子进程
               │ stdin/stdout JSON-RPC（一行一个 JSON）
┌──────────────▼────────────────┐
│ Python Backend（backend/）    │
│  main.py → ApiHandler         │
│  app/handlers/*.py (API_MAP)  │
│  app/workflow/ 工作流引擎      │
│  app/tools/    工具注册表      │
│  app/env/      环境注册表      │
└───────────────────────────────┘
```

三者的职责边界：

| 进程 | 目录 | 职责 |
|------|------|------|
| Renderer | `src/renderer/` | UI、页面状态（Pinia）、通过 `window.electronAPI` 调用能力、订阅事件 |
| Main | `src/main/` | 生命周期、窗口、IPC 路由、Python 进程拉起与保活、应用配置（electron-store）、自动更新 |
| Python Backend | `backend/` | 真正的业务能力：ADB/Apk/Bundletool 工具封装、工作流引擎、模板存储、环境解析 |

### 1.1 数据流（一次普通请求）

1. Renderer 调用 `window.electronAPI.callBackendAPI({ id, method, params })`；
2. preload（`src/preload/index.ts`）经 `contextBridge` 暴露 `electronAPI`，内部走 `ipcRenderer.invoke('call-backend-api', request)`；
3. Main 进程的 `setupCommandHandlers`（`src/main/ipc/commandHandlers.ts`）收到请求，把 `{id, method, params}` 以一行 JSON 写入 Python 子进程的 stdin，并在 `requestCallbacks` Map 里登记回调；
4. Python `backend/main.py` 读取 stdin 行，交 `ApiHandler.handle_request` 分派到对应 handler；
5. handler 返回后，`send_json` 以一行 JSON 写回 stdout；
6. Main 进程的 stdout 监听按 `id` 匹配 `requestCallbacks`，resolve 给 Renderer 的 invoke Promise。

**超时**：`setupCommandHandlers` 的 `requestTimeout` 默认 **300000ms（5 分钟）**，不是 30 秒。长任务（反编译、签名）依赖这个默认值；渲染层可在设置页调整请求超时。

## 2. IPC 通道与协议

### 2.1 单一后端调用通道

所有"调用后端能力"的请求都走**一个** IPC 通道，方法名就是 JSON-RPC 的 method 字段：

| 通道 | 方向 | 用途 |
|------|------|------|
| `call-backend-api` | renderer → main | 通用后端调用，请求形如 `{id, method, params}`，method 如 `apk.analyze`、`template.execute`、`workflow.execute` |
| `stream-event` | main → renderer | 流式响应转发（logcat、下载进度、工作流节点事件等） |
| `get-app-config` / `set-app-config` / ... | renderer → main | 应用配置读写（详见第 6 节） |
| `device-change`、`logcat-output` 等 | main → renderer | 后端事件广播 |

通道名全部集中在 `src/shared/ipc/channels.ts`。**改通道名必须同步 `tests/shared-contracts.test.mjs`**，否则契约测试会失败（见 `AGENTS.md`）。

### 2.2 流式响应（streaming）

后端用 `@streaming` 装饰器（`backend/app/common/decorators.py`）标记的 handler，会在**独立线程**运行、多次回包：

- 每次回包形如 `{"id", "result", "stream_id", "finished": false}`；
- 线程结束时发送 `{"id", "stream_id", "finished": true}`；
- `ApiHandler.stream_handler`（`backend/app/api_handler.py`）负责建线程、注册到 `TaskManager`（支持取消）并转发事件；
- Main 进程 `commandHandlers.ts` 按 `response.finished` 区分流式与普通响应：`finished === false` 的包通过 `stream-event`（或 logcat 专用通道）转发给发起请求的 `sender`，并 resolve 首个包给 Renderer。

装饰器组合约定：`@streaming` 必须在最外层（`@streaming` + `@logs_errors(...)`），`logs_errors` 只记录非受控异常并继续抛出。

## 3. Python 后端

### 3.1 入口与请求循环

`backend/main.py`：

- `bootstrap()`：加载 `.env`（`load_dotenv`）与 `server.config.json`（`load_server_config`），初始化日志（`BT_LOG_DIR`，默认 `backend/logs/`）；
- 主循环逐行读 stdin，用 `ThreadPoolExecutor(max_workers=4)` 并发处理；
- 支持 stdin EOF 后重连（最多 10 次）、SIGTERM/SIGINT 优雅退出（先排空在途请求，10 秒宽限）；
- 注入 `health` handler（返回 `status: ok` 与 uptime）。

### 3.2 请求分派：ApiHandler 与自动发现

`backend/app/api_handler.py` 的 `ApiHandler._load_handlers()` 用 `pkgutil.walk_packages` 扫描 `app.handlers` 包下所有模块，把每个模块导出的 `API_MAP` 字典并入 `api_map`。**新增 handler 不需要改注册表**，只要：

1. 在 `backend/app/handlers/` 下新建模块；
2. 导出 `API_MAP = {"方法名": 函数}`；
3. 函数签名 `(params, stream_handler) -> dict`。

现有 handler 一览（`backend/app/handlers/`）：

| 模块 | 主要方法 |
|------|----------|
| `apk_handler.py` | `apk.analyze`、`apk.decompile`、`apk.recompile`、`apk.sign`、`apk.get_progress`、`apk.cancel_task` |
| `adb_handler.py` | ADB 设备/命令（`adb.devices` 等） |
| `aab_handler.py` | AAB → APKS（bundletool） |
| `download_handler.py` | `download.file` |
| `install_handler.py` | 安装 |
| `template_handler.py` | `template.save/load/list/delete/execute` |
| `workflow_handler.py` | `workflow.execute`、`workflow.validate`、`workflow.list_tools`、`workflow.list_envs` |
| `task_handler.py` / `cache_handler.py` / `log_handler.py` / `tool_handler.py` / `app_handler.py` / `plugin_handler.py` | 任务、缓存、日志、工具、应用信息、插件 |

### 3.3 工具自动发现（两层）

- **代码工具**：`ToolManager`（`backend/app/tools/tool_manager.py`）扫描 `app.tools` 包下 `BaseTool` 子类（排除 `BaseTool` 本身与 `CommandTool`）；
- **描述符工具**：扫描 `backend/registry/tools/*.json`（aapt、adb、apksigner、apktool、bundletool、jarsigner、zipalign），用 `load_descriptor` 解析为 `ToolDescriptor`，实例化 `DescriptorTool`。描述符覆盖同名代码类，但 `_CODE_PRIORITY_NAMES = {"adb"}` 例外（adb 的代码类带流式方法，描述符让位）。**规划（已决策）**：这 7 个 Android 描述符迁至 `examples/tools/android/`，经工具管理页导入后进入注册表；零内置描述符工具，18 个内置原子工具不受影响；
- **内置原子工具**：工作流引擎的 `_BUILTIN_TOOLS` 字典（`backend/app/workflow/engine.py`）注册 18 个 `BuiltinTool`（`file.read`、`net.download`、`shell.exec`、`code.exec` 等），不走 `ToolManager`。

工具发现相关：环境注册表 `EnvironmentRegistry` 扫描 `backend/registry/environments/*.json`（java、python、node）。

### 3.4 插件系统（目前为空）

`backend/plugins/` 下任何带 `run(context, **params)` 的 `.py` 会被自动加载（机制已就绪）。**当前该目录为空**，无实际插件。

## 4. 无头 CLI（backend/cli.py）

后端除 stdin JSON-RPC 模式外，还有一个**独立于 Electron 应用**的无头命令行入口，**不走 stdin JSON-RPC、没有流式 IPC**。内置工具与工作流都能以命令方式单独调用，适合自检、调试与 CI：

```bash
python backend/cli.py run <workflow.json|template-name> --input key=value   # 执行工作流（可加 --json / --task-id）
python backend/cli.py list-tools        # 列出全部工具（描述符/代码 + 内置原子工具）
python backend/cli.py list-envs         # 列出已解析环境（java/python/node）
python backend/cli.py validate <workflow.json>   # 静态校验工作流
python backend/cli.py list-templates    # 列出已保存模板
```

### 4.1 排障记录：cli.py 为什么内联 bootstrap

`backend/cli.py` 第 42-49 行注释说明：最初尝试 `from main import bootstrap` 会失败。原因：`main` 导入 `app.api_handler`，后者 `from app.protocol import ...`，而 `app/protocol/` 现在是一个**包**，会遮蔽旧版单文件模块 `app/protocol.py`，导致导入错误。因此 cli.py 把 `bootstrap` 逻辑**内联**了一份（不读 stdin，仅做 dotenv + server config + 日志初始化），并刻意省略了 `main.bootstrap` 里针对 Electron 场景的旧版下载产物遗留警告。修改任一处 bootstrap 逻辑时需两处同步。

> **现状（已知阻塞项）**：上述 `app/protocol/` 包与 `app/protocol.py` 模块的同名冲突**目前仍存在**，`backend/app/protocol/__init__.py` 只导出 `BaseType/TypeAnnotation/TypeRegistry/Port/PortSet`，不含旧 `protocol.py` 中的 `BackendResponse`/`BackendErrorPayload`/`ErrorCode` 等。因此 `import main`（`backend/main.py:23` → `app/api_handler.py:19` 的 `from app.protocol import ...`）会抛 `ImportError`，后端无法启动（Electron 端表现即为"后端服务已退出"）。这是 README 中标注的 Phase 0 稳定性阻塞项，修复方向是收敛 `protocol.py` 旧模块与 `protocol/` 包的导出，属于排障/现状记录，本文档不展开修法。

## 5. 路径解析

### 5.1 开发 vs 打包

判别逻辑集中在 `src/main/python/paths.ts` 的 `getBaseDir()`，**请勿在别处重新实现**：

```ts
export function getBaseDir(): string {
  return !app.isPackaged
    ? path.join(__dirname, '..', '..')   // dev：相对项目根
    : process.resourcesPath;              // prod：electron-builder extraResources 放置目录
}
```

- **Dev**（`!app.isPackaged`）：`backend/`、`runtime/` 相对项目根；
- **Production**（`app.isPackaged`）：相对 `process.resourcesPath`。`package.json` 的 `build.extraResources` 当前把 `backend/`（排除 cache/output/logs）与 `runtime/` 拷入资源目录；**规划（已决策）**：仅保留 `backend/`，`runtime` 条目移除。`runtime/` 本就 gitignored、二进制从不入仓库，外部化后由用户本地自备。

### 5.2 运行时 runtime/

**现状**：`runtime/` 在仓库中本就被 `.gitignore` 排除（二进制从不入仓库），当前打包时经 `build.extraResources` 随应用分发，包含：`adb/`、`aapt/`（aapt2）、`apktool/`（.jar）、`bundletool/`（.jar）、`android/`（zipalign、apksigner.jar）、`jre/`（java、jarsigner）。Python 运行时的默认路径是 `runtime/python/python.exe`（见 `src/shared/config/pathConfig.ts` 的 `runtimeExecutable`），开发环境缺省时 `resolvePythonExecutable` 回退到系统 `python`。

**规划（已决策）**：`runtime/` 移出 `extraResources`（仅 `backend/` 随包分发），改为**用户本地自备**：本地 `runtime/` 目录、设置中的自定义工具路径或系统 PATH 均可。外部化后 `runtime/python` 通常不存在，系统 Python 成为**实际默认**（该回退逻辑已存在于 `src/main/python/paths.ts`）。不要假设系统 PATH 里有 `adb`/`java`，一律通过环境注册表解析（见 [03-数据模型.md](./03-数据模型.md#9-环境描述符与解析))。

> 注：`runtime/`、`cache/`、`output/` 在 `.gitignore` 中，本地缺目录时属正常；外部化后 `runtime/` 由用户自行创建或完全不用。

## 6. 环境与配置

### 6.1 主进程配置：electron-store

`src/main/stores/appStore.ts` 用 `electron-store`（文件名 `app-config`）管理应用配置：

- JSON schema 校验（`schema` 字段），带版本化迁移（`APP_CONFIG_VERSION = 5`，`MIGRATIONS` 逐版本迁移，`runConfigMigrations` 启动时执行）；
- 关键键：`app`（theme/language/autoStart/minimizeToTray）、`runtime`/`server`/`serverEntry`/`runtimeExecutable`/`rendererEntry`/`preloadCandidates`（路径配置）、`commands`（timeout/maxHistory/outputFormat）、`logs`、`output`、`theme`、`signatureConfigs` 等；
- 渲染层通过 `window.electronAPI.appConfig.*` 读写；写操作有 `isWritableConfigKey` 白名单。

### 6.2 后端配置：.env + server.config.json

后端配置由 `backend/app/utils/env.py` 加载：

- `backend/.env`（实际只有 `APP_VERSION`、`PROJECT_NAME`）；
- `backend/server.config.json`（从 `server.config.example.json` 拷贝）：`env` 段里的键会写入进程环境变量，`.env` 中已存在的键优先。示例默认值：

```json
{
  "env": {
    "APP_VERSION": "1.0.1",
    "PROJECT_NAME": "blank_tool_server",
    "BT_LOG_LEVEL": "DEBUG",
    "BT_CACHE_DIR": "../cache",
    "BT_OUTPUT_DIR": "../output"
  }
}
```

**`server.config.json` 里的相对路径以 `backend/` 目录为基准**（如 `../cache`）。

### 6.3 关键环境变量（后端）

| 变量 | 用途 | 默认/回退 |
|------|------|-----------|
| `BT_RUNTIME_DIR` | 运行时（runtime/）根目录 | `backend/runtime` → 项目根 `runtime/` |
| `BT_CACHE_DIR` | 缓存目录（下载等） | `./cache`（相对 backend/） |
| `BT_OUTPUT_DIR` | 统一输出目录 | `./output`（相对 backend/） |
| `BT_LOG_DIR` | 日志目录 | 无 → `backend/logs/` |
| `BT_LOG_LEVEL` | 日志级别 | `DEBUG` |
| `BT_TEMPLATES_DIR` | 模板可写目录 | 无 → `<output_dir>/templates` |
| `BT_TASKS_DIR` | 任务工作目录根 | 无 → `<cache_dir>/tasks` |
| `BT_JAVA_BIN` / `BT_PYTHON_BIN` / `BT_NODE_BIN` | 环境二进制直接覆盖（env_var_override） | 由环境描述符声明 |
| `APP_VERSION` / `PROJECT_NAME` | 版本与项目名 | `backend/.env` |
| `BT_SERVER_CONFIG` | server.config.json 路径 | `backend/server.config.json` |
| `BT_SEARCH_SYSTEM_TOOLS` | 是否搜索系统工具 | 关 |

## 7. 测试体系

架构上注意四套测试分别由不同运行器驱动（详见 `AGENTS.md`，最容易踩坑）：

| 命令 | 运行器 | 范围 |
|------|--------|------|
| `npm run test` | vitest | `tests/unit/**`、`tests/integration/**` |
| `pytest tests/contracts/` | pytest | 后端 handler 契约测试 |
| `node --test tests/shared-contracts.test.mjs` | node:test | IPC 通道名与 pathConfig 字符串契约 |
| `npx playwright test` | Playwright | `tests/e2e/critical-flows.spec.ts` |

改了后端 handler 或 IPC 通道名后，必须手动跑对应的契约测试（`npm run test` 不会覆盖后两者）。
